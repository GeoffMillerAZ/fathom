# Bench-only oracle instruments (language breadth, ADR-048 D2/D5)

Each directory is one oracle a reading may name, with its tier, install
commands and exact invocation. None of them is a product dependency; all
run as separate processes against clean clones, and their outputs stay out
of the repository. The neutral output shape is `indexbench lang-oracle
-tool-oracle`'s: `{"tool","version","tier","definitions":[{path,name,line,
end,kind}],"calls":[{path,from,to}],"imports":[{path,line,to_path,module}]}`
(repo-relative slash paths, 1-based lines, bare names; `imports` are import
statements resolved to files of the subject, scored as `import_resolution`,
LB-F40).

Route references (LB-F98, wave px) add two fields: `"route_references":
[{path,from,to_path,to,raw}]` — a route, upstream or mesh rule's entity
(`path`, `from`) joined to the provider entity its target host names
(`to_path`, `to`: a Kubernetes Service's or compose service's name), `raw` the
target as written — and `"route_unresolved": [{path,from,raw,reason}]`, a
target that names no provider, `reason` one of `external`, `ip-literal`,
`variable`, `unix-socket`, `ambiguous`, `undeclared`. An optional
`"route_crosscheck": {tool,tier,checked,agree,disagree}` records a stronger
tool's agreement on part of the answer, disclosed in the reading's notes,
never scored. `indexbench lang-routes` reads them and scores the pairs into
`xref_precision`/`xref_recall` at the file's tier (the union with
`cross_references`); `lang-oracle` refuses them (its decode allows no unknown
field), so a file that carries them is measured with `lang-routes`.

design §10) for dialects no tier-A/B tool covers (and, for docker-compose, to convert a tier-A
tool's own JSON, which carries no source lines, into that shape). Each is its own Go module — never
imported by fathom, never a product dependency — and is run from its own directory:

`cargo` is tier A throughout: the tool itself evaluates each workspace (which manifests are members, each
package's name, each package's dependencies with `workspace = true` inheritance, renames and target
tables resolved) and, in the resolving run, draws the graph between packages with every `[patch]`
applied. The tool writes no line, so a package sits at line 1, where the dialect's package entity (the
manifest's root table) does. Name a workspace the root leaves out with `-root` (tokio's two fuzz crates
are each a workspace of their own); the first resolving run needs the network for the workspace's
registry dependencies and a `rustc` on `PATH` (`cargo metadata` without `--no-deps` runs `rustc -vV`),
every later run can use `-offline` on the warm `-home`, and the home is scratch to delete after
measuring. Features and explicit targets are not scored: the tool lists the implicit ones too (a feature
per optional dependency, a target for `src/main.rs`), so what would be scored is what the manifest
declares. The oracle cross-checks them instead (declared-not-in-tool counts on stderr, zero on the
subjects). A tree with fixture manifests (`rust-lang/cargo`: 614 of its 641 `Cargo.toml` under
`tests/testsuite` and the test containers) is measured with `lang-oracle -only
'Cargo.toml,benches/*/Cargo.toml,crates/*/Cargo.toml,credential/*/Cargo.toml'`: the tool builds a
workspace, and the fixtures are manifests it does not attest.

`package-json` is tier A for definitions and references because npm itself loads each manifest (Arborist's
package reader: the bin map normalized, a string bin named after the unscoped package, the four dependency maps
as written) and prints no position, so each line comes from a byte scanner of the oracle's own, and an
`encoding/json` decode of the raw file is the cross-check (disagreement counts on stderr, zero on both subjects;
npm reads an unparseable manifest as an empty package and says nothing, so the decode names the unreadable ones,
two in babel's test fixtures). Run on a scratch copy of the package.json files alone: no `.npmrc`, lockfile or
`node_modules` of the subject reaches npm, which runs offline with an empty user and global config, and nothing is
installed into the subject. The members are npm's own evaluation of the root's `workspaces` globs, listed two ways
(`npm query` and `npm pkg get name --workspaces`) and checked against an independent expansion of the globs. A
`pnpm-workspace.yaml` is read for disclosure only: the directories its patterns name that npm did not list are
counted on stderr, never added to the truth (next.js declares `workspaces` in its root package.json too, so npm lists
its `packages/*` members; the other six pnpm patterns name directories outside the corpus checkout, so that count is
0, and they are not evaluated).

The cross-references are the harder half. npm resolves a dependency edge only against the tree it holds, and an
uninstalled tree has no links between members, so the second scratch copy gets the `node_modules/<name>` symlinks
`npm install` makes for every member npm listed, and `npm ls --json --workspaces` then reports, under each member,
which dependency resolved to a sibling, which npm marked invalid (the written range does not accept the member's
version) and which it lists missing. Yarn's and pnpm's `workspace:` protocol is a spec npm 11.16.0 rejects
(`EUNSUPPORTEDPROTOCOL`: the whole ideal tree fails; `npm ls` lists the edge missing), and babel writes 759 dependency
specs that way (next.js 15), so the copy rewrites `workspace:^`, `~` and `*` to the member's own version and
`workspace:<range>` to the range (the protocol means the workspace package of that name), leaving a path or alias
form as written, and counts each shape on stderr. That makes the join npm's and the input adapted, so the
cross-references file is tier C whenever a rewrite was needed (both subjects) and tier A otherwise.
`-workspace-pm` (wave ox, 2026-10-02) removes the rewrite: the protocol is yarn's and pnpm's, so the subject's own package
manager, the one its `packageManager` names, joins the siblings on a scratch copy, offline. For babel that is the yarn
4.10.3 release and the plugins babel commits under `.yarn/` (its `condition:` protocol is one of them): `yarn workspaces
list -v --json` reports each workspace's `workspaceDependencies` (dependencies and devDependencies the workspace protocol,
or transparent workspaces when enabled, resolve to a workspace) and its mismatched descriptors, and installs nothing. For
next.js it is pnpm 10.33.0 (pnpm 12.8.1 reads no `link-workspace-packages` from `.npmrc`, so it is not the subject's
semantics): `pnpm ls -r --filter '{<project>}...'` selects a project and what pnpm's workspace graph reaches from it,
which is transitive, so the copy empties every other project's dependency maps and restores one project at a time (the
kustomize oracle's ablation rule, run the other way: everything but the entry is removed), and what the filter then adds
is exactly the projects that project's own specs link to. npm's evaluation of the root's `workspaces` still names the
members (each package manager's own listing is the cross-check: 0 disagreements on both subjects). The file is tier A. babel also
writes 46 specs of its own, `condition:BABEL_8_BREAKING ? : workspace:^`, which npm cannot parse and marks invalid:
they are in no truth, and the dialect, which joins by name, draws them. (With `-workspace-pm yarn`, yarn joins 756 sibling
edges where npm's rewritten join listed 718; 8 of babel's `condition:` specs are ones yarn's listing reports as mismatched,
because the plugin picks its branch only when it resolves, and they are the only dialect edges in no truth.) The dialect joins a dependency name to any
manifest of the repository, a vendored copy (next.js's `packages/next/src/compiled/*`) or a test fixture included, and
npm joins only to a workspace member, so `-files-out` names the manifests npm evaluates as a workspace (the root and
each member) and the reading scores the cross-references on those with `lang-oracle -only "$(paste -sd, <file>)"`, as
cargo's and kustomize's are (both corpus subjects keep every member directly under `packages/`, so `-only
'package.json,packages/*/package.json'` names the same files and keeps the reading's note short); measured over every manifest of the subjects the same run reads xref_precision .7984
(babel .9501, next.js .1292: 182 name joins to vendored and fixture manifests that are not workspace members). A
string-valued bin has no entity in the dialect (npm names its one route after the package): the one recall miss in each
subject, counted on stderr. The program empties `<scratch>/npm-oracle`; do not build its binary there.

`go-mod` is tier A because the go command itself parses each file and evaluates each module: module mode
(`GOWORK=off`, the module's own replaces applied) and, where a go.work reaches the module, workspace mode, both
with `-e` so a requirement no proxy serves and nothing redirects (three in kubernetes) is reported unresolved and
the rest is still evaluated. The parse is `golang.org/x/mod/modfile`, the package the dialect reads with, so the
definitions attest what the dialect models (every directive, every block form) and not the parser; the tool prints
no position, so each entry's line comes from an independent line scan (its own tokenizer, no modfile), aligned
entry for entry with the tool's list and cross-checked (scan-mismatch count on stderr, zero on both subjects). The
first run needs the network for the `.mod` files of the modules a go.mod names (3 MB for kubernetes, 12 MB with
cli/cli), every later run can reuse the module cache; the cache is scratch to delete after measuring (it is written
with `-modcacherw`), and both subjects are sparse checkouts of the go.mod family (`calibration/corpus.d/go-mod.yaml`),
so no Go source is read and the tool never builds anything. The tool writes go.sum entries it is missing into the

`maven` is tier A for definitions because the tool itself evaluates the reactor (module discovery,
parent chain, interpolation, profile activation) and rejects one it cannot; the first run needs the
network for the help plugin and the parents a POM names, every later run is offline. The tool writes
no file and no line, so a walk of `<modules>` supplies them and the two project sets are compared
(walk-only and tool-only counts on stderr). A POM outside the reactor (a test project under
`src/test`, an invoker integration test under `src/it`) is not a project the tool builds and is not in
the truth: measure a reactor's own files with `lang-oracle -only` (`apache/maven`:
`'pom.xml,*/pom.xml'`), and pass `-profiles` for a subject whose modules sit in an inactive profile
(`apache/dubbo`: `release`). `-refs` is tier C: the effective POM merges inheritance, so what a file
declares comes from an independent struct decode of the raw POM, kept honest by the cross-checks
(`declared-not-effective`, `parent-mismatch`, the `build/plugins` count); its cross-file edges join by
groupId:artifactId where the dialect joins by artifactId, so the xref metrics measure that shortcut.
`-refs -verbose <file>` (wave ox, 2026-10-02, `verbose.go`) is tier A. `help:effective-pom -Dverbose` (maven-help-plugin
3.2.0 or later; `-goal` pins the coordinate) writes Maven's input location after every element of each project's
effective model: the model that declared it and its line. A POM's own `<parent>` and each top-level dependency are
attested when the effective model holds that element located in the POM's own model at the line the file writes it on
(or, for a dependency an active profile of the same POM re-declares, at the profile's line: one in dubbo). The raw
decode only selects the top-level entries (encoding/xml, the dialect's decoder too, so it names candidates; the
names and lines that attest them are Maven's). A parent or dependency edge joins the effective coordinates to a
reactor project, as before. A `<module>` edge is attested by ablation (`-ablate <scratch>`): every occurrence of the
module in its aggregator (a module two profiles both list is one edge) is cut in a scratch copy of the reactor's POMs,
and the module's project must leave the reactor `help:effective-pom` then builds; the scratch copy's own reactor is
first checked to equal the subject's. Answers are kept by a digest of the copy, so a run stopped by the machine
resumes. The groupId:artifactId versus artifactId join difference is unchanged and stays disclosed.

`msbuild` is tier A throughout: MSBuild itself evaluates each project (its Sdk, every import, every
condition and property) and names, for each item it lists, the file that defined it
(`DefiningProjectFullPath`), so what a file declares is the tool's word and a `Directory.Build.props` is
credited with the references it writes and not the projects that import it. One evaluation sees one
configuration and one target framework, so each project is evaluated for Debug and Release, for its default
framework and for each framework its `TargetFrameworks` lists, and the items are unioned; a condition on
anything else (a Windows-only framework on a macOS run, an environment variable) stays false, and the
independent decode inside the oracle prints what a file writes that no evaluation listed
(`declared-not-in-tool`; 3 over Polly, 0 over aspnetcore) and what the tool lists that no file writes
(`tool-not-declared`), and checks every `<Target Name>` the files declare against the tool's preprocessed
projects. `-preprocess` brackets each imported file with `<Import …>` and `</Import>` markers, which is where
the imported props and targets files (also definitions) come from. The SDK is installed inside the scratch
directory (`dotnet-install.sh --version 10.0.401`, with `DOTNET_ROOT`, `NUGET_PACKAGES` and
`DOTNET_CLI_HOME` under it and `DOTNET_ROLL_FORWARD=Major`; a `global.json` that pins another SDK band does not
stop `dotnet msbuild` run from outside the checkout) and deleted with it. A project the tool cannot evaluate is
listed on stderr and left out (its file is then a dialect-only definition); every project evaluated in both
subjects. `dotnet/aspnetcore` cannot be evaluated from a clean checkout: its root `Directory.Build.props` and
`.targets` import `artifacts/bin/GenerateFiles/Directory.Build.{props,targets}`, which its own first build step
writes, so the run creates both as empty `<Project />` files in the scratch clone (outside git; the corpus
shard's `sparse:` list is the MSBuild files only, plus `eng/` and the internal-testing props a test project
imports) and measures `src/Http` with `lang-oracle -only 'src/Http/**'`. Its Arcade SDK turns `<Reference>`
items into ProjectReferences in `eng/targets/ResolveReferences.targets`, so those edges are that file's,
outside the measured tree. Imports are read but not scored (the dialect draws no Import edge); `.sln` files
are not decoded, so `dotnet sln list` is not an oracle here.

`kustomize` is tier A because the tool itself is the judge of every entry. Kustomize lists nothing of what a
kustomization declares, and its `originAnnotations` name the file a resource came from but not the kustomization
that named it (an overlay of an overlay of a base reads as the base's resources), so the oracle asks the tool one
question of each entry: does the build change when this entry is removed? The entries are proposed by a decode
(`yq`, a reader of its own with line numbers; the dialect's walk over the doc engine is not reused) and each is
removed in turn from a copy of the kustomization (`yq 'del(.resources[3])'`) and the build run again with
`buildMetadata: [originAnnotations]` on. An entry is in the truth when the build fails without it or its output
differs. One that changes nothing (an image that matches no container, a patch whose target matches nothing) is
withheld from the truth and counted on stderr as `unevidenced`, so the dialect that emits it pays in precision; on
both subjects every one of 70 entries was evidenced. A kustomization the tool cannot build contributes nothing and
is left out of `-files-out` with its reason on stderr: a remote base or patch (the run sets a dead proxy and treats
a reference that leaves the subject as cross-repository, never fetched), an entry that names a file the checkout
does not hold (`examples/transformerconfigs/images`, `plugins/kustomized-helm`), an undecodable file, and a
`kind: Component` (not a root the tool builds; none in the subjects). Measure with `lang-oracle -only "$(paste -sd,
<files-out>)"`, and run `lang-parity` on a copy of the subject without the excluded files (it has no `-only`). The
harness scores only edges between files the dialect owns, so a resource that names a manifest is dropped, and
counted, as out of scope: the reading's notes carry the number.

`taskfile` is tier A for what the tool lists: go-task evaluates each Taskfile (its version, its includes, its tasks) and reports every
task with the file, line and column of its key, so a definition is the tool's word and its name is the key written at that position (the tool
lists a task under its `label:` and an included task under its namespace). `--list-all` leaves an `internal: true` task out; the oracle
lists it by running the tool again on a copy with that line blanked, every other line where it was, so the tool's lines are the file's. An
`includes:` entry is in the truth when the tool's listing has a task from the file it names (or from the Taskfile its directory holds, by
the tool's search order), which is the tool attesting that it loaded that file; a file with no tasks and a templated one are counted on stderr and left out, and a Taskfile
with a remote include (`https://`) is rejected by the tool as a whole (remote Taskfiles are an experiment, off by default) and excluded. Its `-refs-out` file is tier
C: the tool lists nothing of what a task depends on, and `--summary` renders (so evaluates) a task, dynamic `sh:` variables included, so the
`deps`, `cmds` `task:` and `defer` entries are decoded (`yq`, anchors and merge keys expanded) and each name is checked against the tool's
(a listed task, an alias, a namespaced task, a wildcard match; the ones it does not know are counted on stderr). A Taskfile the tool rejects is
excluded from `-files-out` and counted; the walk skips `testdata`, `vendor`, `node_modules`, `generated`, `.git` and the editor directories, as
the connector does. A Taskfile's global `sh:` variable may be evaluated by the listing (the subjects' are `pwd` and `git describe`): read a
subject's Taskfiles before pointing the oracle at it.
`-refs-out -ablate` (wave ox, 2026-10-02, `ablate.go`) is tier A by the kustomize oracle's ablation rule. `task --dry --force
<task>` evaluates a task's run plan offline (its deps and its `task:` calls, in order) and prints `task: [<name>] <command>` for
each command of every task it would run. The decoded references are the candidates; each is cut (every deps entry, `task:` call and
deferred call of the task that names the target, by a `yq` edit) from a second scratch copy, and kept when the dry run then names
another set of tasks or refuses the run. The dry run still evaluates variables, preconditions and `if:` conditions, which run shell
(go-task/task's `release:*` task would run `go run ./cmd/release`), so that copy first has every `sh:` and `if:` value set to `true`
(no subject command runs, nothing needs the network), and every variable a task `requires` is passed with a placeholder
(`example.com`, an enum's first value); the comparison is the set of task names, never the commands, which carry templated values
(a build date, a random tag). A reference to a task the file never declares cannot be cut into a change and is not attested
(runtime-radar's one).

`gitlab-ci` is tier A for definitions because the tool itself evaluates each pipeline (includes,
remote templates, `extends`, matrix expansion) and rejects one it cannot; the tool is not offline
(it downloads the remote includes a pipeline names, and a 429 from gitlab.com is retried), and what
it downloads only adds jobs no local file declares. Its `-refs` output alone is tier C: the tool merges a
pipeline and erases `extends`, so those edges come from the raw YAML, gated by the tool's
acceptance of the pipeline, and its cross-file rule is the resolver's own. With `-ablate` (wave ox,
2026-10-02) it is tier A by the kustomize oracle's ablation rule: the raw walk only names the candidates,
and each `needs`, `dependencies` and `extends` entry a job or hidden template writes is cut from a scratch
git copy of its pipeline (yaml.v3 node edit, file re-encoded; the baseline is the same file re-encoded
uncut, and every baseline equals the tool's answer on the original bytes); the reference is attested
when `gitlab-ci-local --preview` (the pipeline with defaults, includes, extends and `!reference`
expanded) changes or the tool rejects the pipeline, a rejection counting only when it repeats. A
cross-file reference also needs its target's declaration cut from the one other file that declares it
to change the answer, which is the tool attesting which file it read that entity from. The job `needs`
`--list-json` evaluates are the cross-check (each written job need it lists). yaml.v3 is the dialect's
decoder too, so it only selects and edits candidates; every attestation is the tool's. The scratch
copy gets `origin/main` at its one commit, so `rules: changes:` compare against no change in every run
alike. A failure of the machine (EPERM, ENOSPC, a timeout) stops the run (exit 3) rather than reading as
a rejection, and each answer is kept by a digest of the copy's files, so a re-run resumes. A pipeline the tool rejects
(`gitlab-org/gitlab-runner`: a `needs:` naming a matrix expansion; `omnibus-gitlab`: a `rules:`
expression it cannot evaluate) contributes nothing and is counted on stderr.

`helm` with `-tier-a` (wave ox, LB-F154) is tier A for definitions and references, relabelled from C with this reason: §1.3 counts "the tool's own evaluation (`helm template`)" and "the format's reference parser" as A, and Helm now decides every entity, for the charts it renders offline. The scope is a chart Helm's own loader loads (`loader.LoadDir` from `helm.sh/helm/v4` v4.3.0, the same code `helm show chart`, `helm show values` and `helm template` run, `.helmignore` applied) whose dependencies are all under `charts/` (vendored, or `file://` and unpacked) and which `helm template` renders with its default values; an `oci://` or URL dependency (never fetched), a library chart and a render error take a chart out, counted by reason on stderr, and a subchart that renders only inside its parent is measured by the parent's render. Chart names and dependencies are Helm's metadata; values keys are Helm's values tree (`loader.LoadValues`, YAML 1.1 through sigs.k8s.io/yaml: a key `y:` is Helm's `true`, so the walk's `y` is counted walk-only, not guessed), one path per key down eight levels into non-empty maps (the dialect's rule, mirrored); template entities are Go's `text/template/parse` nodes, the parser Helm renders with, over the files Helm loaded and rendered. Every define is attested by ablation: in a scratch copy of the chart its name is renamed and a probe template includes the original name, and `helm template` must fail with `no template "<name>" associated` (a define another of the same name shadows does not fail and is unevidenced). An include/template call, and a define-to-callee reference, counts only when a define of its name is attested in the same chart, a subchart or a parent; every other call is unevidenced and counted, and the dialect pays for it in precision. Lines are the parse positions for template entities and, for Chart.yaml and values.yaml, gopkg.in/yaml.v3 by key path (the doc engine's library too: a line is a decoder detail, never an entity decision, as envoy's README argues). The cross-references stay tier C: an `oci://` dependency has no offline truth, and the unique-chart-name join re-implements the dialect's rule. Without `-tier-a`, `helm` is tier C, not A: the oracle's rules are its own. It reads templates with Go's own parser (the one Helm renders with), so a named template, a call and an accessor are the parse tree's; Chart.yaml and values.yaml with the doc engine's own YAML library; and the L3 join re-implements the dialect's unique-chart-name rule, so it attests the implementation, not the rule. With `-helm`, `helm show chart` loads every chart and its name and dependency names are compared with the walk. The stderr summary counts the include/template calls inside and outside a named template and the repository shape (`file://`, `oci://`, URL, none) of every edge.

`openapi` is tier A because the format's reference parser judges every document and every reference: `SwaggerParser.parse`
decides what is a document (a root mapping with an `openapi` or `swagger` key; a file it rejects, a fragment of a split
description or a tool's configuration, is left out and counted), and `resolve` with `$refs.exists` decides which `$ref`s
name something (a pointer to nothing, a missing file and a URL, which `http: false` leaves unfetched, are in no truth).
The parser writes no position, so each key's line comes from the `yaml` package, an independent reader with source
offsets; the document entity needs an `info` (every document has one, and redocly.yaml, a tool's configuration with an
`openapi:` key, has none). The truth names an operation "METHOD /path" and a reference's source by the entity it sits
under, so a `$ref` outside every entity (a path item's shared `parameters`) is counted on stderr and in no truth.
`cross_references` are file-granular `{path, from, to_path}` with `from` the document's root entity (its file name), as
the doc engine's own file-level edge is; the harness scores only edges between files the dialect owns, so a `$ref` to a
fragment file (no `openapi:` key, so not claimed by content) is dropped and counted (design §1.4), which is why the
split descriptions' cross-references are out of scope and Azure's `$ref`s between full Swagger documents are the L3
truth. `-redocly` runs `redocly bundle` on each document that has a file `$ref` and compares the references it cannot
resolve to the oracle's own (disagreements on stderr, zero on all four subjects). The oracle runs on the checkout and
writes nothing into it; install the tools with `npm --prefix`, never globally.
