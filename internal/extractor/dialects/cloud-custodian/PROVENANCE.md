# cloud-custodian — provenance and divergences

LB-Q-cloud-custodian (wave pc), design `docs/design/language-breadth.md` §4, §13. A doc-engine
dialect (no `tags.scm`, no grammar, no incumbent: a policies file was unclassified YAML, never
extracted). The decode is `gopkg.in/yaml.v3` through the doc engine. The format is Cloud
Custodian's policy schema (<https://cloudcustodian.io/docs/>, Apache-2.0); nothing is copied from
a source tree.

## How a file is claimed: by content, never by name

The manifest claims no basename, glob or extension. `detect.content_sniff` matches a column-0
`policies:` key followed by an indented `resource:` key; `fusion.cloudPolicyDispatch` adds a
decode check (a `policies` list entry that is a map carrying a `name` and a `resource`), so a
`policies:` list of anything else (a retention config, a Kubernetes object that carries one) is
not claimed, and never claims a file an earlier signal claims.

## What it models

- **A policy** (`CustodianPolicy`, `policy`): each `policies[]` entry with a `name` and a
  `resource`, named by its `name`, signed by its `resource` as written (`aws.s3`, `ec2`).
- **References** (`Calls`, L2): the `type` of each filter and each action (a bare string names its
  own type; an `or`, `and` or `not` block's members are read at any depth), as written. A filter
  written as the `tag:Name: absent` shorthand has no type and is not a reference.
- **`policy_ref`** (cross-file, emitted, resolved by item k8s's `internal/fusion/policyref.go`):
  `resource: aws.s3`, edge `policy_ref`, strategy `resource-type`, Raw the value as written. Target
  comes only from the committed map `calibration/oracles/custodian/cfn_types.json`, generated by
  `custodian_oracle.py -type-map-out … -doc-json …` from c7n 0.9.53's AWS resource registry
  (`cfn_type`; tier A: 267 resources, each `aws.<name>` and `<name>`), embedded as the cross-file
  rule's `target_map`; a resource with no `cfn_type`, a non-AWS cloud's resource, and a name c7n
  does not know get Target "" (unresolved as unmapped).

## What is not modelled, and why

- **Filters and actions as entities** (the queue's "filters/actions by type"): a policy's filters
  repeat types (many `value` filters), the doc engine names an entity from its own node, and the
  symbol key is `service::package.Name`, so two `value` entries of a file would collide. They are
  carried as the policy's references instead (LB-Q-cloud-custodian-rest).
- **`mode`, `conditions`, `vars` and `{var}` interpolation**, c7n-org's `accounts` and `policies`
  directory layouts, and policies written as JSON.
- **The documentation examples**: they are reStructuredText code blocks, not YAML files.

## Calibration oracle

`calibration/oracles/custodian/custodian_oracle.py` (bench-only), tier A: c7n 0.9.53's own loader
(`c7n.loader.PolicyLoader.load_data`, with c7n-azure, c7n-gcp and c7n-tencentcloud installed so
their resources load) and the schema validator `custodian validate` runs (counted in
`-summary-out`; 4 of 19 files fail it, by design). Names, resources and filter and action types
come from c7n; the lines come from an independent PyYAML composition (tier C for the line, never
for the name; the harness's match tolerates two lines). A file c7n refuses whole is retried
policy by policy. Four fixtures are policies written to fail (an unknown resource, an unknown
filter type, a duplicate `policies:` key, a null resource): c7n refuses them and the dialect
reads them as written, so they are outside the measurement (`-only`) and the reading says so.
