### O728 — tree-sitter-groovy misreads a pipeline without an error node: a command call after a comment, and anything after a top-level pipeline

- **Symptom:** the jenkinsfile dialect's first reading missed 10 of the 156 definitions and 23 of the 127 references the Groovy compiler names on pipeline-examples' declarative examples, in files `files_with_error` counts as clean
- **Evidence:** `indexbench lang-probe -dialect jenkinsfile`: after a comment (its own line, or trailing the statement before), `options { }` reads as the identifier and a sibling closure, `sh 'x'` as the identifier and a sibling string, and `agent any  // c` followed by `steps { }` as the identifier `agent`, a command call `any steps` and the closure; a top-level `pipeline { }` followed by any statement (a helper `def`) either becomes an ERROR around the keyword and its block or stays whole while the trailing method becomes an ERROR of bare identifiers
- **Root cause:** the grammar's newline handling for command expressions, and its `pipeline` rule, which must end the file (the gradle dialect's PROVENANCE.md records the same after-comment reading for build scripts)
- **Fix:** the dialect matches every shape inside a block (never a map entry or an assignment), the closure as the definition's end, and the ERROR-wrapped pipeline (`comments.jenkinsfile`, `trailing.jenkinsfile`); after it the dialect and the compiler agree on all 163 definitions and 133 references of the claim. The trailing method that recovers as bare identifiers stays lost (a ceiling in the reading)
- **Status:** closed for the dialect; open upstream (the grammar)
- **Impact:** without the patterns sym_recall read .9387 and ref_recall .8271 on a clean-looking corpus; `files_with_error` does not see this class
