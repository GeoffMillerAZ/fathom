### O1128 — `test_impact` on a large blast prints its tests in key order and elides the rest, so a test that calls the symbol directly can be cut while far ones are shown

- **Symptom:** `test_impact` on a widely reached symbol reports 1,186 reaching tests, prints 238 and elides 948, and the one test that pins the behaviour under question is among the elided. The elision line says only "narrow the query", and the tool takes no argument that lists the rest.
- **Evidence:**
  - **Tool:** `test_impact` (served through `bin/fathom serve-mcp --store` on a scratch ingest, probed after E3's grading, `docs/bench/readings/decide/exp-e3.md:38`)
  - **Expected:** the tests nearest the symbol first (a test that calls it directly before one that reaches it ten calls away), and an elision line that names how many were cut and the exact argument that lists them.
  - **Actual:** the tests in the order returned, 238 of 1,186, with the pinning test elided.
- **Root cause:** the `test_impact` handler (`registerTestImpact`, `internal/mcp/analysis_tools.go`) returns `callgraph.TestImpact`'s keys, sorted by key (`internal/analysis/callgraph/graph.go` `TestImpact`: "the sorted canonical keys"), although the same handler computes each test's hop count (`callerDepths`) for its summary. The handler does not budget itself, so the dispatch-level backstop (`budgetedResult`, `internal/mcp/budgeted_handler.go`) trims the largest array to a prefix "as returned" with the generic hint "narrow the query": the cut falls alphabetically, whatever each test's distance.
- **Fixed:** `test_impact` ranks its tests by hops from the symbol (the reverse BFS `TestImpact` already walks), then package proximity (path distance between the test's directory and the symbol's), then key; it budgets its own list and the elision line names the count and the exact `offset` argument that lists the next page, so paging lists them all. Test: `TestTestImpact_RanksByDistanceAndPagesTheRest` (`internal/mcp/testimpact_rank_test.go`).
- **Status:** fixed
