### O1304 — the stop hook sends an elision follow-up after a verify_plan partial that verified nothing

- **Symptom:** in RT-M14's harness run, the first measured stop-hook invocation made two `verify_plan` calls, 4,167 ms and 1,876 ms, and both came back as partials with no `verdict_outcome`. The uncounted warm-up invocation did the same (4,168 ms and 2,862 ms). Every later invocation made one call that answered.
- **Evidence:**
  - **Tool:** stop hook → `verifyViaHTTP` → `verifyWithCaller` (`cmd/fathom/verify.go`)
  - **Expected:** a partial that verified no row (stage building, or declined) ends the hook's verify for that plan
  - **Actual:** the response carried `elided_count` 85, so `verifyWithCaller` sent a follow-up batch. That batch could only return the same partial, and it added a daemon call and about 2 s of the hook's 5 s cap.
  - **Repro:** the stop hook with a claimed row while the plan's verify stage is still building; call-log rows for session `hook-path-harness-rtm14-1792424612`, pids 31152 and 31322
- **Root cause:** the follow-up loop is keyed on elision (`hvr.Elided.Count > 0`) and does not check whether the first answer was a stage partial that verified nothing.
- **Fix:** skip the follow-ups when the first answer is a partial with no verified task. Test first: a stub that returns a stage partial with elision is called once.
- **Status:** open
- **Impact:** small. It doubles daemon calls on the invocation that can least afford them, and it put one more "building" row into RT-M14's answered share (49 of 101; it would read 49 of 100 with one call, still under 50%).
