### O1363 — a hand-started managed daemon kept launchd's own instance down

- **Symptom:** On 2026-10-19 an agent session hand-started `fathom serve-http --managed` with the managed label's store and address while launchd's job was down (its parent a Claude Code shell). The owner reloaded the launchd job; its instance found the port held by an answering managed fathom of its own label, logged `port_held` "already served" and exited 0. KeepAlive SuccessfulExit=false never relaunches after exit 0, so the managed daemon stayed a child of a transient session until the owner killed it by hand.
- **Evidence:**
  - **Tool:** `fathom serve-http --managed` (the held-port step, `resolvePortHolder` in cmd/fathom/portholder.go)
  - **Expected:** the supervised job takes the port over once the hand start exits
  - **Actual:** exit 0 "already served"; launchd stays down for good
  - **Repro:** stop the launchd job, start `serve-http --managed` by hand on its address, reload the job
- **Root cause:** the held-port step trusted any same-label managed holder that answers as the supervised daemon; the record did not say whether a supervisor runs it.
- **Fix:** the daemon record and the start row carry `supervised` (darwin `XPC_SERVICE_NAME` equal to the label, linux `INVOCATION_ID`, or init as the parent). A holder recorded `supervised: false` gets exit 75 under `port_held_unsupervised`, which the breaker and RT-M1 do not count, so launchd relaunches every ThrottleInterval and takes over within a minute of the hand start's exit; a record without the field keeps exit 0. An unsupervised managed start logs the restart command (`launchctl kickstart -k gui/<uid>/<label>`, linux `systemctl --user restart <unit>`), and the daemon-down text names it and says not to start `serve-http --managed` by hand. Design: `docs/design/responsible-tenant.md` section 8.4 step 5.
- **Status:** fixed
