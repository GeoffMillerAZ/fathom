### O1422 — `fathom readout fit` on this machine reads 0 readout rows, so the held-out accuracy has no labels yet; the policy step adds 0.054 ms p95

- **Symptom:** `fathom readout fit` (no --write) over both hook-log generations (`~/.fathom/hooks.jsonl` and `.1`, 54 MB and 67 MB) prints `0 labels from 0 readout rows`; both halves and the contested band read `no labels`; cut points stay the built-ins (each rule's own floor, long read 200 lines).
- **Evidence:** `grep -c '"channel":"readout"'` is 0 on both generations; the user config names no `[readouts]` table, so the readout hook ran in mode off and logged no row. Latency: `BenchmarkChoose` 32.5 ns/op; the rich stage's policy step (features, the policy-file stat, `Choose`) over 2,000 runs: p50 0.046 ms, p95 0.054 ms on a 513-byte go build failure, p95 3.1 ms on a 33 KB piped build output (counting protected lines dominates), p95 0.002 ms on a whole read outside a repository. A whole read in a repository whose outline join did not run adds one edited-file check (a git read).
- **Root cause:** the brief assumed a readout-row corpus; none exists until a `[readouts]` mode is set (RO-M1's observe window has not started here).
- **Fix:** none in code. Re-run `fathom readout fit` once observe rows exist; RJ-M1 reads the held-out contested-band accuracy then. Enrichment labels additionally need rich rows (they carry `policy_rule`, the overlaps and the records the fit reads back).
- **Status:** open
- **Impact:** RJ-M1 cannot be read yet; the table answers with its built-in cut points.
