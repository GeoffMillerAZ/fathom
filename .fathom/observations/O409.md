### O409 — the doc-xref resolver's rules shape what an L3 edge can be: same-file, directory and ambiguous targets

- **Symptom:** Flux's `sourceRef` to a GitRepository in the same file, a Kustomization's `spec.path` and a name declared in two files draw no edge
- **Evidence:**
  - **Tool:** internal/fusion/docxref.go resolveDocXrefs (`unique(..., notFile)`, `oneDocFile`) and docengine.go labelMap
  - **Expected:** the brief's `label-selector` join for sourceRef and templateRef
  - **Actual:** `service-name` excludes the referring file and needs exactly one other-file entity of the name; a directory resolves only to the one doc file in it (or the one the referring dialect owns by basename or glob, which no CR dialect has); a label set is a map of scalars and an object's `metadata` holds maps, so no `{kind, name}` selector matches
  - **Repro:** `gotk-sync.yaml` (a GitRepository and its Kustomization); `path: ./apps/staging` over a directory with kustomization.yaml and values files
- **Root cause:** the resolver's rules are the engine's contract (design §4); the CR dialects meet them
- **Fix:** none here: sourceRef, templateRef and compositeTypeRef are `service-name` over the `Kind/<namespace>/<name>` entity name (both namespace forms); the oracles score cross-file edges and name the directory edges as out of scope; mixed files stay Kubernetes whole (a per-document dispatch would need the engine to split a file)
- **Status:** open (the -rest rows name each trigger)
- **Impact:** same-file refs, directory edges, a namespaced WorkflowTemplate and an ambiguous overlay name are ceilings of the CR dialects
