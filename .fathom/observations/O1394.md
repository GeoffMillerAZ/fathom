### O1394 — lang-next offered finished items; a cross-plan need broke the queue test

- **Symptom:** `indexbench lang-next` printed `eligible` for scss, graphql, go and kotlin though each already has a reading and a deferred `-rest` row, so a wave was scoped onto finished or owner-gated work (O1388, O1391). A queue need on a sibling plan's row (`LB-Q-graphql` on `language-breadth.lang5.md#LB-F580`) broke `TestLanguageQueueMatchesPlan`, so f4f424d1 dropped it and graphql read eligible again.
- **Evidence:**
  - **Tool:** `indexbench lang-next -all` at f4f424d1: `graphql eligible`
  - **Tool:** `langbench.CheckQueueAgainstPlan` and `QueueEligibility` read only `language-breadth.md`
- **Root cause:** triage read needs alone, never the reading's `level_met` or the `-rest` row, and every consumer parsed the main plan by itself.
- **Fix:** LB-F581 (`langNextLines` separates `eligible`, `eligible (at L2 of L4)` and `waits:`), LB-F582 (`langbench.LoadBreadthPlan` reads the main plan and its siblings through `support.PlanFiles`; qualified names resolve through `Task.Source`); `LB-Q-graphql` needs LB-F580 again. See `docs/plans/language-breadth.lq1.md`.
- **Integration review:** the worker's rule held an item only at a partial reading, so sass, matlab, conftest and sentinel (no reading), cmake and svelte (level none) and python-packaging (at its target, own row open) still printed `eligible` beside a deferred `-rest` row; a deferred `-rest` row now holds the item whatever its reading.
- **Status:** fixed (lq1)
