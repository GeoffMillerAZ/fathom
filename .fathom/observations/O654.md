### O654 — exec sites outside config.toml whose argv or toolchain a repository's files choose (filed, not fixed)

- **Symptom:** none seen; listed by the SEC-2 audit (2026-10-09) of every `os/exec` site whose argv derives from a repository-controlled file
- **Evidence:** (1) `fathom doctor --stranger` execs the repository's `scripts/stranger-check.sh` (`doctorStrangerRow`); (2) `fathom receipt verify --run-tests` runs `go test -run '^<name>$' <pkg>` for a receipt file's test (`runOneGoTest`); (3) every ingest, the daemon's automatic re-ingest included (RT-99, `daemon.auto_refresh`), runs the typed pass's `packages.Load` with `NeedCompiledGoFiles` in the repository (`internal/fusion/typedcalls.go`), so the go command honors the repository's `go.mod` toolchain line under an inherited `GOTOOLCHAIN=auto` (it downloads and runs that official toolchain) and runs cgo, `cc` and `pkg-config` with the repository's safelisted `#cgo` directives. (1) and (2) are explicit verbs the user types with a flag, which SEC-2 allows; (3) is automatic and bounded by the go command's own threat model (official checksummed toolchains, the cgo flag safelist), not by fathom. Not reproduced with a live exploit
- **Root cause:** none for (1) and (2) (by design); for (3), the typed pass inherits the user's go environment so it can resolve modules at all
- **Fix:** none in SEC-2. Candidate for (3): run the typed pass with `GOTOOLCHAIN=local` and `CGO_ENABLED=0` unless a user-scope setting opts in, measured first on the fleet (a cgo package then loads with fewer types)
- **Status:** open
- **Impact:** a cloned repository can choose which official Go toolchain the daemon downloads and which safelisted flags its C compiler sees during an automatic re-ingest
