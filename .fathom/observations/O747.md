### O747 — TypeScript and JavaScript L4 is capped by object-literal properties: def_mapping cannot reach .85 without a definition per property of every object literal, which the cost gate refuses

- **Symptom:** after the module symbol, module-level consts and members (LB-F381..LB-F383), def_mapping reads TypeScript .5157 and JavaScript .6246 (webpack .7139) against L4's .85 for good, while typed_recall reads .937 and .8856.
- **Evidence:**
  - **Tool:** O746's scratch classifier re-run at b9d25f09 on nest 9ff83d54, zod 1fb56a5c and webpack v5.111.1 `lib/**` against the O441 scip-typescript 0.4.0 indexes; a scratch query (never committed) naming every object literal's `pair`, shorthand property and method as a definition, ingested on zod against b9d25f09, three alternating runs.
  - **Unmapped definitions:** TypeScript 13,189 of 27,587 in-scope definitions, 12,436 of them an object literal's property (scip-typescript's meta descriptor named per file, `success0:`, `success1:`, in any expression, a function body's included), 696 class or interface properties the member patterns leave (a quoted or computed name, a type literal nested in a property's type, an assigned `this.x`), 41 variables; JavaScript (webpack) 4,502 of 16,065, 4,209 object-literal properties and 292 variables (`let`, `var`, CommonJS `exports.x = "…"`).
  - **The ceiling:** with every other definition mapped, def_mapping reads at most .549 (TypeScript) and .738 (webpack); with object-literal properties defined too (synthetic definitions scored by the harness's own ScoreSCIPWith) .9359 on zod, .8985 on nest and .9208 on webpack — but only if the harness also read `success0:` as `success`: scip-typescript's counter is no name a source extractor writes.
  - **The cost:** the scratch query defines 10,509 more symbols on zod (6,697 to 17,206, +157%); store 9,113,600 to 13,447,168 bytes (+47.6%), wall +8.8%, extraction CPU +8.6%, against K17's gate of +20% store and +15% wall. Every `{ success: true }` in a function body would become a symbol of its file.
- **Root cause:** scip-typescript gives every object literal's property a global symbol (the checker can type a property access on the literal), so the index's definition population is half object-literal properties; fathom's definitions are what an agent asks for by name, and an object literal's key is not one.
- **Fix:** none here (the change was measured in scratch and not made). L4 for TypeScript and JavaScript needs an owner decision: either def_mapping leaves scip-typescript's object-literal properties out, as it leaves parameters out (LB-F239), with a counted disclosure, or a definition per object-literal property ships with a cheaper store shape.
- **Status:** open (owner decision)
- **Impact:** LB-Q-typescript and LB-Q-javascript stay at L3 (excellent) with typed_recall near excellent; the remaining L4 gap is this one class.
