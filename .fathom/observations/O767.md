### O767 — symbol_context and references served the secrets beside a Kubernetes object's embedded Alertmanager or Grafana file, and any Kubernetes Secret's values

- **Symptom:** LB-F367 proved no secret value is stored and that symbol_context withholds the snippet of a definition of a sensitive kind. Asked about the same fixture, two read tools still served the planted sentinel from the repository's bytes
- **Evidence:**
  - **Tool:** symbol_context, references (found by SR-76's sweep of the 21 tools on `/rpc/extended`, `internal/mcp/secret_surface_test.go`; c68b5097)
  - **Expected:** no answer holds the sentinel, in the clear or base64-encoded, except the declared raw-bytes readers (`read_source`, `search`'s literal grep mode)
  - **Actual:**
    - `symbol_context {symbol: "am"}` answered `Secret/am` (kind K8sWorkload, not a sensitive kind) with a snippet of `deploy/alertmanager-secret.yaml` from line 1: the embedded Alertmanager configuration's secrets in `stringData` and the Secret's own `slack-token`. `grafana-datasources` served the base64 `data` (the datasource file and `admin-password`, encoded). The same for a ConfigMap embedding a Grafana datasource file, and for any core Secret's `stringData`/`data`
    - `references {query: "am", include_heuristic: true}` served occurrence rows with their line text from those files (`telegram_bot_token: SECRETSENTINEL7…`, `datasources.yaml: YXBpVmVyc2lvbjogMQ…`); with `case_insensitive: true` a query for the secret's value found its 35 occurrences, each with its line
  - **Repro:** `go test -run TestSecretSurface_NoReadToolServesASecret ./internal/mcp/` with `snippetWithheld`'s file rule or the references withholding removed (the revert probes)
- **Root cause:** LB-F367's check was the definition's own kind (`extractor.SensitiveKind`). A Kubernetes object that embeds a sensitive dialect's document (ADR-065 decision 1) sits in the same file as the embedded entities but is not of their kind, and a snippet window starts at its line; a Secret embedding nothing is no dialect's sensitive entity at all. references reads the tree for word occurrences (`ScanSources`) and served each line as found
- **Fix:** the rule is the file's (`internal/mcp/secret_withhold.go`): a file whose values may be secrets holds an entity of a sensitive kind or a core Kubernetes Secret (`Secret/<name>`, apiVersion v1). symbol_context withholds the snippet of every definition in it (`snippetWithheld`, the same `snippet_withheld` reason shape), and references serves its occurrences there with an empty `text` and a `text_withheld` reason (`secretFiles`, from the service's symbol snapshot the tool already holds). Revert-probed: each of the file rule, the Secret rule and the references rule removed fails the test. No leak was found in query's files (`internal/mcp/{safe_delete.go,resolved_nav.go,tools.go,findsymbol.go}`, `internal/query/engine.go`): every tool answering from the store answers without the sentinel, because none is stored
- **Status:** fixed (wave h3, SR-76)
- **Impact:** an agent asking symbol_context about a Kubernetes Secret, or references about a word in one, received its values. Disclosed, not filtered: `read_source` and `search`'s literal grep mode serve a committed secret as committed (`docs/mcp-tools.md` "Secrets")
