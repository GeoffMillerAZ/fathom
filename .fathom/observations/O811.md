### O811 — a go.work-declared module that imports another workspace module without a replace directive fails its typed load

- **Symptom:** EW-62 makes a committed go.work's `use` list declare the repository's own modules, so the typed pass loads each of them; it loads each from its own root under `GOWORK=off` (TypedEdgeEnv, "typed edges are per-service, never workspace-wide"), so an import of another workspace module resolves only through a `replace` directive or the module cache, never the workspace
- **Evidence:** read from the code while building EW-62 (`internal/fusion/typed_nestedmodules.go`, `typedenv.go`); the fixture `internal/fusion/testdata/goworkmods` keeps its modules self-contained, so no test exercises the cross-module case
- **Root cause:** the per-module load forces `GOWORK=off` since the 2026-09-16 incident (a go.work naming sibling checkouts outside the repository); a committed go.work whose every `use` lies inside the repository would be safe to honour, but nothing distinguishes the two today
- **Fix:** not built. Candidate: when the root go.work is committed and every `use` is in-repo, load with `GOWORK=<root>/go.work` from each module's root (its packages only), and keep `GOWORK=off` otherwise; measure the per-module load against the K26 bar first
- **Status:** open
- **Impact:** in a go.work monorepo whose modules import each other with no `replace` (the common reason to keep a go.work), a module whose import resolves to neither the cache nor a replace reads as a disclosed typed-load failure (the ingest reads degraded) and keeps its syntax edges; a proxy-cached published version resolves outside the repository and its edges are dropped as out of scope
