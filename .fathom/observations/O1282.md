### O1282 — GraphQL has no cross-file reference the file resolver can draw: L3 needs a strategy no existing one is

- **Symptom:** LB-Q-graphql targets L3 (xref_precision, xref_recall), but `lang-oracle` reports `L3:not-attempted` ("xref not measured: the dialect is no doc engine and names no import strategy") and the reading stays at L2
- **Evidence:** a GraphQL schema is the union of every file a server loads (gqlgen's `schema:` globs, Apollo's typeDefs list), so a type written in one file names a type another file defines with no import statement; the only link in the wild is the `#import "./a.graphql"` comment of graphql-tag's loader and graphql-import, a `comment` node whose text the tags engine's `@import.module` takes whole (`genericImportSpec`: `unquoteJS(m.Text(src))`), not the path inside it; no strategy in `importStrategies` resolves a name by global lookup; `PackageScoped` needs a `package.strategy: capture` clause GraphQL does not have. The tier-A oracle writes 3 cross-file pairs on the two subjects (all gqlgen) and 430 references to a name two independent schemas define (gqlgen's examples reuse `User`, `Todo`, `Query`)
- **Root cause:** the queue entry's "#import edges" note assumed a captured import path; recipe 13.2 step 13 sends such an item to "stop at L2 and report needs-strategy" (an Opus row adds strategies)
- **Fix (open):** `LB-Q-graphql-rest` (deferred) names the trigger: a global-name resolution strategy (a name binds across the files of one schema) or an `@import.module` that reads a string inside a comment, plus a subject whose files an import convention links
- **Status:** open
- **Impact:** GraphQL reads L2 excellent, not L3; callers and blast_radius across schema files see no edge from a field to a type another file defines
