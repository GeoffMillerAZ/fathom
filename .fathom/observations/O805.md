### O805 — C++'s 617 undrawn file edges, classed: a third are a namespace's first definer, and an include or a file-level macro reached no definition to draw from

- **Symptom:** C++ L3 read file_edge_recall .4355 (476 of 1,093 truth pairs; bar .50) against scip-clang 0.4.0 on fmt 12.2.0, json v3.12.0 (include/) and spdlog v1.17.0 (cpp.json, 2026-10-09). Wave lf4 item fileedge classed the 617 pairs fathom did not draw before changing anything.
- **Evidence:**
  - **Tool:** `indexbench lang-oracle -dialect cpp -scip <index> -tool-oracle preproc.json -tool-oracle clang-calls.json -only <scope> -unmatched <file>` with the harness the reading was taken with (f274aa29^, before K25 ruling 3; O806), then each `oracle_only` pair joined to the index's references from the source document to symbols the target defines, and to the build's include graph (the clang-preprocessor dump's `imports`, transitively).
  - **Actual:** fmt 158, json 94, spdlog 365:

    | class | fmt | json | spdlog | all |
    |---|---|---|---|---|
    | only a namespace's first defining document (`spdlog::`, `fmt::v12::detail::` reopened in every file; the index lists one) | 50 | 8 | 137 | 195 |
    | only the `#include` line (scip-clang's `<file>` symbol): the file names nothing the header defines, or a macro | 21 | 21 | 67 | 109 |
    | a macro, most of them written at file level outside every definition (json's NLOHMANN_JSON_NAMESPACE_BEGIN/END alone on their lines: 44) | 12 | 44 | 12 | 68 |
    | a type, function or constant of a header the includes reach, which crefs did not bind | 31 | 6 | 60 | 97 |
    | a target the includes never reach: a header's declaration to its out-of-line definition (`logger.h` to `logger-inl.h`, compiled mode), one test file to another | 44 | 15 | 89 | 148 |

  - **Repro:** the commands above; the classifier reads the SCIP index and the -unmatched file (worker scratch `tools/scipmiss`).
- **Root cause:** fathom's file edges are reference edges from a definition (refresolve.go: a reference outside every definition has no definition to draw from and is dropped), and an `#include` drew none at all: a C++ file had no symbol of its own. So the include-only class and the file-level macros (the cpp-macros pre-pass blanks a macro alone on its line, leaving the line outside every definition) could not be drawn by any resolver change in resolveIncludePath, compdb or crefs.
- **Fix:** the cpp manifest's `module_symbol` (K18's module symbol, LB-F434): every C++ file is a `<module>` definition spanning the file, an `#include` of a subject file is an edge to that file's module (moduleImportEdges) and a file-level reference is made from it. With the harness's active-lines rule reading a module caller as the file (LB-F435), the reading's own truth reads file_edge_recall .4355 to .7027 (768 of 1,093) and file_edge_precision .9754 to .9624 (oracle-blind 76 of 874 judged pairs, 8.7%, under LB-F203's 10%); L3 excellent. The namespace class is the truth's (O806); the declaration-to-definition class stays (O469).
- **Status:** open (the fix is committed; cpp.json is not re-read, O806)
- **Impact:** the include-path resolver's recall ceiling moves from about .53 (O469) to about .72 on the reading's truth; cost on the three subjects, median of 3 scratch ingests: wall +4.1% (CPU +1.6%), store +5.2%.
