### O1123 — `kindToLang` maps `JSONKey` to javascript, so a service with JSON files and no JavaScript lists javascript

- **Symptom:** `list_services`' `languages` derives a language from each symbol kind by prefix, and the `JS` prefix also matches `JSONKey`, the kind every `.json` key gets; a service with JSON files reads "javascript" on every kind-only path.
- **Evidence:**
  - **Tool:** MCP `list_services` (`internal/mcp/platform_tools.go`)
  - **Expected:** `JSONKey` names no programming language, or names json; javascript and typescript come only from JavaScript and TypeScript sources (O1086).
  - **Actual:** `kindToLang` returns "javascript" for any kind with the prefix `JS` (`internal/mcp/platform_tools.go:504`, `:515-516`), and `core.KindJSONKey` is `"JSONKey"` (`internal/core/model.go:208`), the kind `.json` maps to (`internal/connector/connector.go:241`). `langStringsForSummary` also counts it as a shared JS kind (`platform_tools.go:208`), so with file classes present it is swallowed and with none it falls back to the kind-only answer (`:202-203`), which reads javascript. The kind-only branches of `ServiceSummaries` (`langStringsForKinds`, `langStrings`) reach the same mapping.
  - **Repro:** read from the code at exp0 HEAD (unchanged since fd091c4f): `kindToLang(core.KindJSONKey)` is "javascript". Found while writing E3's reference answers (`docs/bench/readings/decide/exp-e3.md`, Q4).
- **Root cause:** the language is inferred from a kind-name prefix, and `JSONKey` shares the two-letter prefix the JS* kinds use.
- **Fix (proposed shape):** test first: `kindToLang(core.KindJSONKey)` is not "javascript", and a summary with `JSONKey` kinds and no js or ts file class lists no javascript. Then match `JSONKey` (and any `JSON*` kind) before the `JS` case, in `kindToLang` and in `langStringsForSummary`'s shared-JS test.
- **Status:** open
