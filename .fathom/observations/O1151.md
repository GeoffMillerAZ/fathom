### O1151 — no client sends `session=` in X-Fathom-Caller, so the daemon's per-session `killed` line (KS-14) separates sites but not sessions in practice

- **Symptom:** KS-14 keys a live kill's `killed` line by (session, site), the session read from `X-Fathom-Caller`'s `session=` by `rpcContext` and `/route`. Every header fathom sends leaves it empty, so under a kill every hook session on one daemon shares the empty session and hears of the kill once per site, not once per session.
- **Evidence:**
  - **Tool:** `pkg/client` (`CallerHeader`), read while fixing O1131
  - **Expected:** a hook or MCP proxy that knows its agent session (the hook payload's `session_id`) names it in `session=`.
  - **Actual:** the only callers, `pkg/client/caller_transport.go` (`CallerTransport.RoundTrip`) and `cmd/fathom/origin.go`, pass `CallerHeader(origin, "")`; nothing else builds the header. `mcp.CallerInfo.Session` is consequently empty on every `/rpc` call, and `console_work_signals.go` falls back to one row per entry for the same reason.
  - **Repro:** `grep -rn 'CallerHeader(' --include=*.go cmd pkg internal | grep -v _test`.
- **Root cause:** the header carries a session field (ADR-047) that no hook client fills.
- **Fix (proposed shape):** the hook clients (edit, prompt, test-run) pass the hook payload's `session_id` through to `CallerHeader`, so `/rpc` and `/route` see a session with no daemon change; KS-14's keying already reads it.
- **Status:** fixed (wave fx3): `originHeader` stamps `rpcSession`, which the edit, prompt and test-run hooks set from the decoded payload's `session_id`; `TestHookClients_SendPayloadSessionInCallerHeader` drives two sessions through edit-hook and prompt-hook against a daemon handler and reads distinct `session=` values, `TestOriginHeader_CarriesRPCSession` pins the stamp. No daemon change. The stop and session hooks do not set it (not in the fix's scope).
