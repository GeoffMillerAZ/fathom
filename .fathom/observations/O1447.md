### O1447 — A literal search on a cold service waits for the whole symbol snapshot before it answers: 31 s cold, 4 s warm, 2.9 s for ripgrep alone

- **Symptom:** a literal `search` on app-kit is abandoned at the 60 s tree-class deadline with no partial answer, while ripgrep in the same tree answers in seconds. Adopters filed 12 reports of this between 2026-10-01 and 2026-10-18 (theme T02 in docs/bench/readings/feedback/adopter-triage-2026-10-20.md).
- **Evidence:**
  - **Reports:** app-kit O64, O78, O86, O89, O95, O96, O100, O113, O118, O122, O129, O130. Each describes a literal or exact-path search that was abandoned at the deadline with no partial result, then a direct `rg` or source read that found the text.
  - **Call log (the fleet daemon):** app-kit `search` succeeded 591 times, at 668 ms p50, 8.9 s p90 and 36.9 s p99. It was abandoned 23 times, every time at 60.0 to 60.3 s with `queued_ms` 0 to 5, so admission did not hold it. 16 of the 23 fell on 10-16 to 10-18, the days of the restart loop and 41 to 80 app-kit refreshes a day (O1446).
  - **Probe, 2026-10-20, deployed binary 909ea5c2e, about 2 minutes after a daemon restart:** `search {service: app-kit, pattern: "ARCH251|ARCH252|G7|G8|G9|G10|G11", context: 2, limit: 30}` took 30.9 s, then 4.2 s for the identical second call. `rg` alone over the same tree took 2.9 s.
- **Root cause:** a service-scoped search builds its receipts (the enclosing `sym`/`kind` of each hit) from `serviceSymbols` (internal/mcp/resolved_nav.go). That is the service's whole memoized snapshot, copied with `NodesCopy` on every call. The search loads it before it renders any hit (internal/mcp/search_tool.go, the `byFile` load in the handler). Every ingest and every restart evicts the snapshot (O1446), so the first search after either one pays a full snapshot load. On app-kit the cold call took about 27 s longer than the warm one. The snapshot is the only memoized state the handler reads, so that is its likely cost, though the call was not profiled. Under load it runs longer and reaches the deadline. The receipt is optional by the tool's own contract ("each omitted rather than guessed when it cannot be determined"), yet the search waits for it.
- **Fix:** proposed, not built (small, inside the table freeze). Peek the snapshot. When it is resident, read it in place: `groupSymbolsByFile` only reads, so the per-call `NodesCopy` is not needed. When it is not resident, render the hits without `sym`/`kind` and add one field that says the receipts were omitted while the index loads. No new cache or job is needed.
- **Status:** fixed (90700acc0). A service search peeks the snapshot (`memo.PeekSnapshot`). Resident, it reads `Snapshot.Nodes` in place (no `NodesCopy`). Not resident, it starts or joins the load and stays `memo.NavKeepAfter` plus 100 ms (so the load is kept for the next caller; skipped when the deadline is shorter), runs the engine, peeks again, and renders the hits without `sym`/`kind` when the index is still loading, with `receipts_omitted` saying why. `searchByService` (the references route) does the same. Test: `TestSearchColdServiceAnswersWithoutSnapshot`. Fixed (86dbae5bb), the deployed gap: ripgrep ran with `--sort path`, which makes it read one file at a time, so on a cold page cache it was about five times slower, and the fleet daemon's host evicts the tree between searches (it swaps). The first run is now parallel and `searchRipgrep` orders the hits by path, then line; only a run stopped at the 1 MiB output cap is repeated in path order, so a capped answer does not depend on read order. Tests: `TestSearchRipgrepOrdersHitsWithoutSortingTheRun`, `TestSearchRipgrepCappedOutputStaysDeterministic`. The rest of the deployed cost is the host's memory level, not this path (O1485).
- **Answers:** app-kit O64, O78, O86, O89, O95, O96, O100, O113, O118, O122, O129, O130.
- **Measured:** before, on the deployed daemon (2026-10-20 11:42Z): `search {service: app-kit, pattern: "ARCH251|ARCH252|G7|G8", context: 2, limit: 30}` 11.45 s cold, 0.68 s warm. After, scratch serve-http of f6db5e73b over a scratch app-kit store: 2.34 s and 0.29 s cold across two restarts, 0.24 to 0.27 s warm; the origin/main binary on the same store 2.24 s cold, 0.30 s warm. That store's snapshot loads inside the 1.1 s hold, so receipts were present on every call there; the omitted-receipts path is shown by the test, not this probe. After, on the deployed daemon (21fc4b309, 2026-10-20 13:33Z, first calls after the deploy restart, the daemon shedding refreshes): `search` 10.06 s cold and 0.76 s warm, with receipts on both. The cold figure barely moved, so the cold cost there is not the symbol index wait. Where it went, read-only on the deployed daemon (21fc4b309, 2026-10-20 14:03 to 14:12Z, level normal, footprint 1.37 GB of which 430 MB resident, host 105 MB free and 5.1 GB of swap used): the same search took 6.72, 3.39, 8.30, 6.67 and 3.28 s; a bare `root` search of the same tree, which reads no symbol index, 4.25 and 2.38 s; a search with no hits 2.08 and 2.21 s. Watching the daemon's child processes during the 3.28 s call: `git` (the freshness check) at 0.30 s, `rg` alive from 0.34 to 3.22 s, the answer at 3.28 s; so rg was 2.9 s of it and the receipts and rendering 0.06 s. rg alone over app-kit (9,266 files), page cache dropped before each run: 2.03 to 2.09 s with `--sort path`, 0.37 to 0.43 s without. After, scratch serve-http over app-kit and agentic-kit, restarted with the tree dropped from the page cache, origin/main 7794f805f against 86dbae5bb: 2.32 and 2.36 s against 0.62 and 0.64 s cold, 0.24 to 0.27 s against 0.12 to 0.13 s warm, receipts on every call. After, on the deployed daemon (2caec6fc8, 2026-10-20 14:55Z, minutes after the deploy restart and its index refresh request): `search {service: app-kit, pattern: "ARCH251|ARCH252|G7|G8", context: 2, limit: 30}` 1.96, 1.45 and 0.70 s, against 10.06 s cold and 0.76 s warm at 21fc4b309; the first two answered with `receipts_omitted` while the symbol index loaded, the third with receipts.
- **Impact:** literal search, the tool agents fall back to when `symbol_context` fails, fails on the same cold service. An agent on app-kit then has no fathom answer left and greps.
