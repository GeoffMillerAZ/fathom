### O390 — `lang-oracle` scores a subject it could only partly read as complete: a file an EPERM wedge hid left the reading's counts equal, and the only sign is a "left out of scope" note

- **Symptom:** three measurements of tenchi-security/camp (4,713 policy documents) at the same commit read `fathom_defs` 28,328, 34,302 and 38,569; every run reported `matched == oracle_defs` and `sym_recall` 1
- **Evidence:**
  - **Tool:** `indexbench lang-oracle -dialect aws-iam-policy -tool-oracle parliament` on a checkout on an external volume, fathom d8216dd4, during a TCC "Operation not permitted" wedge
  - **Expected:** a file the harness cannot read fails the run, or is counted as a miss
  - **Actual:** `ownedSourceRefs` and the extraction loop skip a file whose `os.ReadFile` errors, and scoreToolOracle drops the oracle's entries on any file fathom did not read ("N tool-oracle entries on files fathom does not read", 72,288 and 158,681 in two runs), so recall stays 1 on the files that were read
  - **Repro:** wedge the volume (or `chmod 000` a subject file) and run lang-oracle: no error, a smaller denominator
- **Root cause:** the out-of-scope rule (§1.4) is right for ingest's own exclusions (testdata, generated, size caps) and the same code path takes an unreadable file
- **Fix:** none here (the harness is not this item's); the worker re-ran each reading until `oracle_defs` equalled the oracle file's definition count (the three final readings do: 38,581, 55,711 of 55,711 scored, 27 with the disclosed -only restriction)
- **Status:** open
- **Impact:** a reading taken in a wedge can look excellent on a fraction of its subject; the "does not read" note is the only guard
