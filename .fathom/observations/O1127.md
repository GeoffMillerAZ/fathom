### O1127 — `blast_radius` `kind: "delete"` on a Go type misses every function that takes the type in a signature, and its referents carry no symbol key

- **Symptom:** asked whether a shared Go type can go, `blast_radius` with `kind: "delete"` answers with call-shaped uses only. Functions that take the type as a parameter or return it, structs with a field of the type, and composite literals or conversions the syntax pass did not record are never listed, so a type with many signature uses reads as nearly free to delete. Every referent row carries a file, a line and a bare name, so an agent that wants to act on a row must rebuild its key by hand.
- **Evidence:**
  - **Tool:** `blast_radius` `kind: "delete"` (served through `bin/fathom serve-mcp --store` on a scratch ingest, E3 Q4, `docs/bench/readings/decide/exp-e3.md:36-37`)
  - **Expected:** one referent per symbol that uses the type (a parameter, a result, a field type, a composite literal, a conversion), each with the symbol key `find_symbol` resolves.
  - **Actual:** 32 referents and only one of the seven reference sites, under `checked_edges: typed` with 0 typed referents; the agent's first two dry runs pruned all 32 and then 18 of the 32 rows as not in the index, since a bare name does not resolve.
- **Root cause:** `safeDeleteCheckAnswer` (`internal/mcp/safe_delete.go`) builds referents from three sources: the syntax engine's `FindCallers` (a symbol whose `Calls` list names the type), the typed pass's resolved callers, and file-resolved typed callers. `goextract.collectCalls` (`internal/extractor/goextract.go:430`) inspects a function's body only, so a type written in a signature or a struct field is never in any `Calls` list; the typed pass emits call, func-value, dispatch and instantiation edges, and the delete path reads the caller views, which skip instantiation facts and have no type-use edge to read. The row type `safeDeleteReferent` has `file`, `line`, `symbol` (the bare name) and `tier`: no key field.
- **Fix:** for a Go type or interface, the delete answer scans the service's Go sources that contain the type's name (the same bounded `ScanSources` read `references` uses, no new table or cache), parses each with `go/parser`, and records every reference to the type (the bare name inside its package, `pkg.T` through an import of its directory elsewhere), attributed to the indexed symbol whose span encloses it; the type's own declaration and methods are not referents. Every referent row gains `key`, the enclosing symbol's key. A scan that stops at its budget says so (`type_scan`). Test: `TestSafeDelete_TypeReferentsInSignaturesFieldsAndLiterals` (`internal/mcp/safe_delete_typeref_test.go`).
- **Status:** open
