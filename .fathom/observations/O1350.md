### O1350 — the json-schema dialect draws 28 pointers the reference resolver calls unresolvable (ref_precision .9993)

- **Symptom:** the json-schema reading's ref_precision is .9993 (40,883 of 40,911 pairs on SchemaStore and the JSON-Schema-Test-Suite remotes), not 1: the dialect draws a `$ref` edge the oracle leaves out of the truth.
- **Evidence:**
  - **Tool:** `@apidevtools/json-schema-ref-parser` 16.0.5 `$refs.exists()` (oracle `calibration/oracles/json-schema/json_schema_oracle.mjs`), 47 local pointers it calls unresolvable on SchemaStore (summary `unresolvedRefs`), e.g. `#/definitions/moduleType` in azure-iot-edge-deployment-template-1.0.json, `#/definitions/item/properties/content_html` in feed.json
  - **Expected:** an edge only for a pointer that resolves
  - **Actual:** the doc engine's `pointer` rule names an entity by the first segment after the prefix (`localPointerTarget`) and never walks the rest, so a pointer whose first segment is declared draws the edge whether or not the deeper path resolves; an independent walk of the JSON found every one of these pointers resolvable, so the tool's `exists()` is the stricter side (its cause is not isolated)
  - **Repro:** `bash /Volumes/m2ext/tmp/fathom-build/w-lang4-jss/measure.sh` (lang4 wave scratch), then the reading's `counts.ref_fathom` less `ref_fathom_in_truth`
- **Root cause:** first-segment pointer naming (docengine.go `localPointerTarget`), shared by every dialect that writes `pointer`.
- **Fix:** none. 28 of 40,911 is under the excellent bar and the edge points at the entity the pointer names. Revisit if a dialect needs a resolved deep pointer.
- **Status:** open (accepted at excellent)
