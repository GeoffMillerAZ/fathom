### O1450 — symbol_context reads its snippet from the working tree at the index's line numbers, so after an edit it pairs a definition with someone else's code

- **Symptom:** in a checkout with uncommitted edits, `symbol_context` returns a definition range from the index (`def` lines 291-316, tier verified) and a snippet that is a different function now standing at those lines. Adopters filed 3 reports on 2026-10-01 (theme T06 in docs/bench/readings/feedback/adopter-triage-2026-10-20.md).
- **Evidence:**
  - **Reports:** app-kit O69 ("stale definition range paired with unrelated current … snippet"), O72 (stale coordinates with current unrelated text), O75 ("def line 19 two arguments, tier verified; snippet current line 32 four arguments; index_commit matches HEAD").
  - **Code:** the snippet is `readSourceRange(ctx, backend, service, def.FilePath, def.Line, …)` (internal/mcp/nav_tools.go, the symbol_context handler). `readSourceLines` (internal/mcp/readsource.go) opens the current file under the corpus root. Nothing compares that file with what the index read. The obligations path had the same fault and fixed it under J2 (O88: a stale rule's snippet stops re-reading the current file). symbol_context did not get that fix.
- **Root cause:** the definition comes from the index (the last ingest or refresh) and the snippet from disk (now). When the file has changed in between, the two disagree, and the answer presents both as one verified fact.
- **Fix:** proposed, not built (small). Before serving a snippet, compare the file's current size and mtime, or its hash when those differ, with the indexed `file_stats` row that the stat gate already reads (9d4da27b2). When the file differs, withhold the snippet with `snippet_withheld: "file changed since the index (<index_commit>); read_source serves the current text"`, or search the current text for the definition's signature line and serve that span labeled `relocated`.
- **Status:** fixed (1f08d5875). Answers app-kit O69, O72, O75.
- **Impact:** a verified-tier answer shows the wrong code, and an agent editing from it edits the wrong function.
