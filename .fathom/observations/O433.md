### O433 — two clean scratch ingests of one commit typed 233 and 410 Go packages, and verify --strict differed

- **Symptom:** `fathom verify --strict` on a fresh scratch ingest of the same HEAD reported 3 claimed rows failing once and 0 the next time; the failing run's ingest typed fewer packages, so three rows lost their product-reachability proof
- **Evidence:**
  - **Tool:** `fathom ingest --store <scratch>/final.sqlite --service fathom --path .` then `fathom verify --strict --store <same> --service fathom --plan docs/plans/language-breadth.md` (wave ox worker clone at 2cc6c50e, 2026-10-02; binary built from that clone)
  - **Expected:** a clean ingest (exit 0, no "operation not permitted" in its log) types the same packages every time
  - **Actual:** run 1: `typed-edges: 160/233 pkg(s) processed (0 failed)`, verify: LB-F136 (`enrichPolicyRefEdges`), LB-F97 (`enrichRouteRefEdges`) and LB-X-docker-image-ref (`DockerfileDocFile`) unknown, "wired: no product entry point reaches it"; run 2, same tree, same environment: `typed-edges: 281/410 pkg(s) processed (0 failed)`, verify: 182 of 182 claimed rows proven
  - **Repro:** ingest the same tree twice into fresh stores on the external volume under the intermittent EPERM wedge and compare the `typed-edges:` line
- **Root cause:** not traced; the package list the typed pass loads appears to shrink without an error (a `go list` that cannot read some files, under the EPERM wedge, is the likeliest cause), and nothing reports the shortfall
- **Fix:** open: report the typed pass's package count against the module's and fail (or warn loudly) when a clean ingest loads fewer, so a strict verify never runs on a partial graph
- **Status:** open
- **Impact:** a worker's or integrator's `verify --strict` can fail claimed rows for want of call-graph edges, or prove a row on a graph that differs from the next run's
