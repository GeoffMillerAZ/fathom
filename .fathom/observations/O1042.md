### O1042 — Ingest never reads a pipeline named <x>.Jenkinsfile: dispatch keys the extension case-sensitively

- **Symptom:** jenkinsfile.json (wave lf8) reads linkki-framework/linkki 0 of 1 L3 edges, and its notes say the Jenkins pass read 1 file there, while `-only` measured 7 pipelines at L1.
- **Evidence:** `ExtractForBench` on `ci/main.Jenkinsfile` and `ci/MAIN.JENKINSFILE` returns `no-extractor`, on `ci/main.jenkinsfile` and `Jenkinsfile` the dialect's nodes. linkki's pipelines are `.ci/*.Jenkinsfile`; the spelling is common (coreos/fedora-coreos-pipeline `jobs/*.Jenkinsfile`, tutao/tutanota `ci/*.Jenkinsfile`).
- **Root cause:** `resolveExtractor` looks up `p.exts[filepath.Ext(relPath)]` as written, and the manifest's extension is `.jenkinsfile`; `connector.ClassifyDialect` matches extensions case-insensitively, but `sniffedExtractor` consults it only for an extension in `p.sniffExt`. lang-oracle's L1 runs the dialect's own extractor on the `-only` files, so the reading's L1 did not show the gap.
- **Fix:** `waves/lf8/handoff/cifmt-register.go.patch` (register.go is the integrator's): a case variant of a registered extension goes to the classifier, and only a dialect `sniffExts` holds (a glob or sniff dialect, jenkinsfile among them) is dispatched by it, so `.PY` and `.TS` stay unread; with TestIngest_JenkinsfileCaseVariantExtension (red without the hunk). An ExtractorEpoch bump (every `*.Jenkinsfile` newly extracted) and a jenkinsfile.json re-read under K29 follow it.
- **Status:** fixed at wave lf8's integration (LB-F562, ExtractorEpoch 64); jenkinsfile.json re-read under K29 at 3ead4c19: linkki 1 of 1, xref_recall 1
- **Impact:** every `*.Jenkinsfile` of an indexed repository is unread today: no definitions, no calls, no edges; jenkinsfile.json's xref_recall is .9792 (47 of 48) for this one miss.
