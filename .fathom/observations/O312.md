### O312 — a registry dispatching through a func field leaves `run` reaching no verb handler

- **Symptom:** the hd-verbs brief prescribed `verb.Run func(args, stdin, stdout, stderr) int` registered from each file's init(); dispatching through that field would leave `runWithStdin` statically reaching no handler
- **Evidence:**
  - **Tool:** typed-edge pass (internal/fusion/typedcalls.go `classifyCall`) and the call graph behind `test_reaches`/`edge_wired` (internal/analysis/callgraph TestImpactDetail, Reachable)
  - **Expected:** a verb registered in init() and dispatched by `main` stays reached from `run`, so every test that drives a verb through `run([]string{...})` keeps reaching its handler, and rows such as h1's `{symbol: cmdVerify, reachable_from: runWithStdin}` stay proven
  - **Actual:** a call through a func-typed struct field is classified unresolved (an EdgeUnresolved `<unresolved:N>` edge), so the only path to a handler would run from `<pkg>.init`, which no test calls: the product wired check would pass (init is an entry point) while test_reaches and edge_wired from `runWithStdin` would fail
  - **Repro:** read `classifyCall`'s `targetUnresolved` branch for a call whose Fun is a field selector of func type; then grep docs/plans/h1-coding-agent-excellence.md for `reachable_from: runWithStdin`
- **Root cause:** the typed pass resolves direct calls, interface dispatch and func-value references, not calls through a func-typed field to the values stored into it
- **Fix:** EW-45: `verb.Run` is a `verbRunner` interface; each verb declares a one-method runner type, so `v.Run.execVerb(...)` is an iface-dispatch edge to every runner and each runner calls its handler directly; init() instantiating the runner satisfies the product walk's rapid type analysis
- **Status:** worked around in EW-45; a field-sensitive func-value resolution in the typed pass would let a plain func field work, not built
- **Impact:** without the workaround the zero-behaviour-change migration would have lost proven rows across the plans
