### O733 — a component's props are named after their type, not linked to the component, and inline props have no owner

- **Symptom:** a prop is a JSProp named after the `*Props` interface or type alias that declares it (`ButtonProps.label`); nothing stored joins `Button` to `ButtonProps` in one file, and a props type written inline on a parameter or as a type argument (`({ a }: { a: string })`, `forwardRef<HTMLElement, { inset?: boolean }>`) yields no prop
- **Evidence:** LB-Q-react-rest: 11 of react.json's 16 L1 misses are such props (9 inline or type-argument literals, 2 in a union inside an intersection); 3 more are method signatures (`onClose(): void`) the method pattern names `IProps.onClose`, a JSMethod
- **Root cause:** a query names a definition after its structural container only (`@member`); a component is a callable, not a container, and making it one would rename every function declared inside it; the file resolver keeps a reference only when an import binds its head (`refKeeper`), and `@reference.type` is counted, never stored (design §3.4)
- **Fix:** proposed, engine: store a definition's reference to a type of its own file (a component's first-parameter type), which gives a component-to-props edge, and a member mark that names a parameter's type literal after the enclosing callable
- **Status:** open
- **Impact:** "what props does Button take" needs a hop through the signature; inline props are invisible
