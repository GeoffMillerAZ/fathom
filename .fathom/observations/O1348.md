### O1348 — a macro that takes `name =` and creates no target (`grpc_package`) reads as a target, and ingest stores no edge from a BUILD, WORKSPACE or MODULE.bazel file

- **Symptom:** the bazel dialect's L1 is good, not excellent, on grpc/grpc: sym_precision .9554 against the tool format's .98, from 117 definitions Bazel never instantiated.
- **Evidence:**
  - **Tool:** `indexbench lang-oracle -dialect bazel -only <scope globs> -unmatched` on grpc/grpc v1.84.0
  - **Expected:** every `name = "x"` call at the top of a BUILD file is a target
  - **Actual:** 110 of the 117 are `grpc_package(name = ...)`, a macro that declares package defaults and creates no rule; 7 are WORKSPACE and MODULE.bazel repository rules whose function (`python_register_toolchains`, `bind`, `system_pip_parse`, ...) is not on the dialect's list of repository rules
  - **Repro:** `jq` over the `dialect_only` list of the `-unmatched` file
- **Root cause:** whether a call creates a target is decided by evaluating the macro. A tags query reads the call's text, and the connector gives it no file name to separate BUILD from WORKSPACE. A project-specific skip list would break org-agnosticism (ADR-011).
- **Fix:** none in the dialect. The reading keeps the number and the cause. Separately, ingest's file-resolve pass is keyed by file extension (O379), so `BUILD`, `WORKSPACE` and `MODULE.bazel` store no load edge at ingest while lang-oracle's resolver draws them (xref precision .9435, recall .9971 on 2,077 edges); only a `.bzl` file's own loads are stored. `//pkg:target` dependency edges between BUILD files are in the oracle's `rule_input` and are not scored: no strategy resolves a label to the package's BUILD file.
- **Status:** open
