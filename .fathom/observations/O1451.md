### O1451 — symbol_context answers a name it cannot resolve with `def: null` and empty lists, which reads as "exists, nobody calls it", and it drops the qualified key its own candidate list hands out unless the service prefix is kept

- **Symptom:** a qualified `symbol_context` (`dir/file.Name`, the key an ambiguous answer lists, without its `service::` prefix) returns `{"callers":[],"callees":[],"def":null,"related_tests":[]}`. A name that does not exist gets the same shape. No error, no "not found", no candidates. Adopters read this as a missing definition or an untested symbol (theme T07 in docs/bench/readings/feedback/adopter-triage-2026-10-20.md, plus the `def:null` cases in T05).
- **Evidence:**
  - **Reports:** app-kit O59 ("Qualified Go symbol_context returned no definition though bare-name discovery found it"). app-kit O65 and O70 show the same `def:null` shape for a symbol missing from a stale index (O1449).
  - **Probe, 2026-10-20, deployed binary 909ea5c2e, agentic-kit:** `symbol_context main` answered `ambiguous` with candidates such as `symbol_key: agentic-kit::cmd/constitution-lint/main.main`. `symbol_context agentic-kit::cmd/constitution-lint/main.main` resolved (def at cmd/constitution-lint/main.go). `symbol_context cmd/constitution-lint/main.main` answered `def: null` with empty lists in 0 s. `symbol_context zzzNoSuchSymbolQ` answered the identical shape.
- **Root cause:** when the handler's resolution finds nothing, it still renders the full neighbourhood shape, with a null `def` and empty arrays. That is a falsely-empty answer, the I38 class: "no definition found" and "no callers" look the same. Name resolution also accepts the candidate key only with its service prefix.
- **Fix:** proposed, not built (small). (1) When `def` resolves to nothing, answer `resolution: "not_found"` with the nearest `find_symbol` candidates (case-insensitive and substring, the tiers it already has) and omit the empty `callers`/`callees`/`related_tests`. (2) Accept `dir/file.Name` by prefixing the call's own service before resolving.
- **Status:** fixed (90700acc0). (1) A name no tier resolves answers `not_found: true` with `candidates` (`symbol_key`, `file`, `line`; find_symbol's case-insensitive, then substring, then edit-distance tiers, capped at 10), `count` and a `hint`, and no `def`, `callers`, `callees` or `related_tests`. The field is `not_found: true`, not the proposed `resolution: "not_found"`: `resolution` is already the typed/heuristic count object on symbol_context and ten other tools, and a string there would break its schema; `not_found` mirrors the existing `ambiguous: true` answer. (2) A name with no `::` that resolves to nothing is retried as `<service>::<name>`, so `dir/file.Name` resolves. Test: `TestSymbolContextUnresolvedNamesCandidates`.
- **Answers:** app-kit O59 (the qualified-key miss) and the `def: null` shape of app-kit O65 and O70 (their stale index is O1449's).
- **Impact:** an agent told "def: null, no callers" decides the symbol is absent or dead. The fault is the lookup, not the code.
