### O1233 — On macOS, every deploy changes the agent's binary hash, and after enough of them Background Task Management stops issuing the launch constraint, so launchd refuses to start the daemon

- **Symptom:** after a routine `task deploy` on 2026-10-19 00:39Z the managed daemon drained, exited 0 and never came back: `launchctl print` reads `state = spawn scheduled`, `job state = spawn failed`, `last exit code = 78: EX_CONFIG`, and three deploy attempts each waited out 110 health polls; every fathom tool in every session answers connection refused.
- **Evidence:**
  - **Tool:** `/usr/bin/log show --predicate 'eventMessage CONTAINS "fathom-http"'` (zsh's builtin `log` shadows it and prints nothing)
  - **Expected:** a re-signed binary under the same `fathom-dev` identity starts as the last 177 runs did
  - **Actual:** `backgroundtaskmanagementd: Exceeded max notifications for fathom. Please file a Feedback report or contact the developer. item=... name=fathom, type=legacy agent, disposition=[enabled, allowed, not notified], identifier=8.com.geoffmilleraz.fathom-http` at 00:40:18Z, then from 00:40:46Z once a minute `launchd: Service could not initialize: Unable to get updated LWCR for (<BTM uuid>, ~/Library/LaunchAgents/com.geoffmilleraz.fathom-http.plist, 501), error 0x3 - No such process`; `launchctl print` shows the job's launch constraint (`LWCR`) keyed on `cdhash`
  - **Repro:** macOS 27 (Darwin 27.0.0), the launchd agent installed by `fathom daemon install`, many deploys of a re-signed binary at one path (runs = 177 before the failure)
- **Root cause:** inferred, not proven: Background Task Management tracks the legacy agent with a launch constraint on its program's cdhash; each deploy's new cdhash makes it re-evaluate the item and post a notification, and once its per-item notification cap is exceeded it stops producing the updated constraint, so launchd cannot initialize the service. The binary itself is sound (it runs from a shell, signed `fathom-dev`).
- **Fix:** open. The owner restores the service (re-register the agent, or toggle it in Login Items). The product fix to design: a program path whose hash does not change on deploy (a stable launcher that execs the current binary), so a deploy never re-triggers Background Task Management; ground what reads `ProgramArguments[0]` (`cmd/fathom/plist_posture.go`, `daemon.go`, `scripts/deploy-wait.sh`) and confirm the daemon's file-access grant follows the exec'd binary before changing it.
- **Status:** open
- **Impact:** every fathom tool and daemon-backed hook in every session is down until the owner acts (hooks fail open); RT-M1's 2026-10-19 day log is thin while the daemon is down; on this dogfood machine every wave's deploy can re-exhaust the cap. An adopter who upgrades rarely is unlikely to hit it.
