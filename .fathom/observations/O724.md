### O724 — Terraform CloudWatch modules are variable-driven, so a literal identity join finds nothing in them

- **Symptom:** terraform-aws-modules/terraform-aws-cloudwatch v5.7.3 (82e51437): 3 metric alarms and 2 log metric filters, 0 identity joins; its one Lambda function's code is an archive_file `source` block written inline
- **Evidence:** every `namespace`, `metric_name` and `metric_transformation` attribute is `var.*`, and the examples pass `local.*` values through module inputs (examples/complete-log-metric-filter-and-alarm/main.tf: `namespace = local.metric_transformation_namespace` into modules/metric-alarm)
- **Root cause:** the join reads literals only (a value from a variable, a local or an interpolation is decided at plan time); following a value through a module input is value flow, which no tier-C rule reads
- **Fix:** none (a written ceiling, LB-F371-rest): the join and the handler binding are measured where Terraform writes literals — serverless-patterns' Terraform patterns, where every function whose archive_file packages repository code under a literal handler binds (39 of the 96 functions, each of the 39 confirmed in its file by an independent check; the 57 unbound by reason: artifact 27, a zip no archive_file builds; module 9, a registry Lambda module call; templated 7, a variable handler or source; remote 5 and image 2; runtime 4, a go or java package or no code file the rules find under a variable runtime; inline 3)
- **Status:** open (revisit when a value-flow reading of module inputs exists)
- **Impact:** a module library's alarms join nothing; an application's literal ones do
