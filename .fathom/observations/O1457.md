### O1457 — In a sandboxed agent session fathom reports a blocked socket as "daemon not responding" and a blocked write as a raw EPERM, never naming the sandbox

- **Symptom:** in a harness sandbox that confines network and writes to the workspace (a Codex `workspace-write` session), `fathom prime` says the daemon at its address is not responding, and `fathom thread note` fails with `open ~/.fathom/threads.jsonl: operation not permitted`. The daemon was up both times. Adopters filed 2 reports, on 2026-10-01 (theme T16 in docs/bench/readings/feedback/adopter-triage-2026-10-20.md).
- **Evidence:**
  - **Reports:** adopter repository A O18 ("prime reports the daemon unreachable in the restricted session"; the agent used the documented grep fallback). app-kit O61 ("Thread continuity note cannot be persisted from workspace-write sessions … operation not permitted").
  - **Not probed:** this wave ran no sandboxed session. The cause is read from the two reports and from where fathom keeps its state (the daemon on a loopback port, threads under `~/.fathom`, both outside a workspace-confined sandbox).
- **Root cause:** fathom's client paths treat every failed connection as a down daemon and pass a write's EPERM through raw. A sandbox deny can be told apart from a down daemon (EPERM against connection refused), and fathom does not try.
- **Fix:** proposed, not built (small). In `prime`, doctor and the hooks' daemon probe, report a connect that fails with EPERM as `blocked by the session's sandbox (the daemon may be up); allow loopback network for this session or run outside it`. `thread note` names the same cause for a write EPERM under `~/.fathom`. No state moves into the repository.
- **Status:** open
- **Impact:** a sandboxed agent drops fathom for the session and files a daemon outage that did not happen.
