### O457 — the Roslyn and JavaParser dumps date a definition from its first attribute or annotation, not its name, and that alone refuses C#'s dispatch and costs Java's L1

- **Symptom:** `indexbench lang-parity` refuses the C# tags dialect against csharpextract.go on sym_precision alone (0.985 < 0.9952) and reads the Java dialect's sym_precision 0.9773 against javaextract.go's 1.0, while both dialects are far ahead on sym_recall
- **Evidence:**
  - **Tool:** `indexbench lang-parity -dialect csharp -incumbent csharpextract` (Polly 9ad5ae9b, Newtonsoft.Json 4e13299d; the reading's Roslyn 5.9.0 dump and scip-dotnet indexes of 2026-09-28) and `-dialect java -incumbent javaextract` (guava v33.7.1 module dir, retrofit 3.0.0; JavaParser 3.28.2 definitions dump, scip-java 0.12.3 indexes rebuilt by the recipe), wave ld, 2026-10-02, `docs/bench/readings/lang/parity/{csharp,java}.json`; each side's L1 misses written through lang-oracle's `-unmatched` shape for diagnosis
  - **Expected:** an oracle definition's `line` is its name's line, the convention of SCIP, universal-ctags and the php-parser, kotlin-psi and swift-parse dumps (`line` "is the name's line", their READMEs), which every dialect follows
  - **Actual:** `calibration/oracles/roslyn/Program.cs` `Mk` takes `n.GetLocation()`'s start line and `calibration/oracles/javaparser/JavaParserDump.java` takes `n.getBegin()` (a field `fd.getBegin()`): the node's first line, which is its first attribute list or annotation. `ScoreL1` pairs a definition within two lines, so a declaration with three or more attribute or annotation lines is unpaired both ways for the dialect, which reports the name's line, and paired for the CGO incumbents, which report the node's first line. C#: 217 of the 237 definitions only the dialect leaves unpaired (Polly 156 of 162, `[Theory]`/`[InlineData]` test methods; Newtonsoft.Json 61 of 75), the other 20 being six conversion operators the dialect names by their target type's tail (`ValueTask<bool>>`) and 14 not classified. Java: all 489 (guava 455, retrofit 34: `@SuppressWarnings` `@CanIgnoreReturnValue` `@ParametricNullness` stacks, annotation types under `@Documented @Target @Retention`)
  - **Repro:** a copy of each dump that dates a definition from its name (Roslyn: the identifier token, a namespace's name, an operator's token, a conversion operator's type, an indexer's `this`, a field's first declarator; JavaParser: `NodeWithSimpleName.getName().getBegin()`, a field's `VariableDeclarator.getName()`), `end` unchanged, re-run with the same subjects, indexes and flags: C# reads MERGE (sym_recall 0.8283 to 0.9996, sym_precision 0.9823 to 0.9958, range_agreement 0.9519 to 0.9601, kind_agreement 0.9997 both); Java reads sym_recall 0.9004 to 1, sym_precision 0.9787 to 1, and stays refused on its call and file-edge metrics (O458)
- **Root cause:** the two dumps date a definition by its syntax node, whose span includes leading attribute lists and annotations; the harness and every other oracle date it by its name
- **Fix:** none here (calibration/oracles is wave ox's): change the two dumps' `line` to the name's line as above (Program.cs `Mk`, JavaParserDump.java's two `Def` constructions), keep `end`, regenerate `out/csharp-*.json` and `out/java-*.json`, then re-read csharp.json and java.json (L1 rises: a name-line Java dump reads sym_recall and sym_precision 1) and re-run lang-parity for both; C#'s then reads MERGE on the reading's own subjects, so the `.cs` switch follows (LB-Q-csharp-rest, item calls)
- **Status:** open
- **Impact:** C# stays on the CGO csharpextract.go (no signatures, no properties, file_edge_recall .0023 against the dialect's .4346) only because of the oracle's line convention; C#'s and Java's committed L1 readings understate the dialects (Java's .9773 is 1.0 by name)
