### O365 — the header router sends libuv's uv.h and curl's curl.h and curl_setup.h to C++ because a C++ keyword is written in a comment

- **Symptom:** the header router sends libuv's uv.h and curl's curl.h and curl_setup.h to C++ because a C++ keyword is written in a comment, so the C file resolver and the C measurement do not see the project's central headers
- **Evidence:**
  - **Tool:** `extractor.LooksLikeCppHeader` (internal/extractor/cheaderextract.go, CT-3) over the pinned subjects, wave cx item cinc, fathom 32afe369
  - **Expected:** a header with no C++ construct reads as C: uv.h is the plain C API of a C library
  - **Actual:** libuv 1 of 38 headers (include/uv.h: "class" in the comments at lines 441, 478, 531 and 533, "virtual" at 844) and curl 5 of 258 (include/curl/curl.h, include/curl/curlver.h, lib/curl_setup.h, lib/easy_lock.h, lib/vtls/x509asn1.h) route to C++; nearly every .c file of both subjects includes one of them
  - **Repro:** `python3` word-boundary scan of the keyword list (class, namespace, template, virtual, constexpr, public:, private:, protected:, `::`) over the headers, or `indexbench lang-probe` on the header under -dialect cpp
- **Root cause:** looksLikeCpp is a token scan of the raw text, comments and string literals included (its own comment says false positives are bounded; here they are the headers every file includes)
- **Fix:** none here (the file is item calls'); the change is to skip comments and string and character literals before the scan, and an ExtractorEpoch bump (the routed language of these headers, so their symbols' kinds, change). Meanwhile the include-path resolver reads a header the router sent to the other language as a foreign header for its includes and prototypes (internal/fusion/cproto.go), so the file edges through them are drawn
- **Status:** open
- **Impact:** the symbols of these headers (macros, inline functions, types) are outside the C universe, so no edge binds to them and the C measurement scopes them out of the file-edge truth; the central headers' include closure is still followed
