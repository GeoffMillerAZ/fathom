### O725 — the harness scored ResolveDocXrefs alone, not every doc-xref edge ingest stores

- **Symptom:** a tool format's L3 (xref_precision, xref_recall) read only `fusion.ResolveDocXrefs`; the edges the doc-xref pass adds beside it (a GitHub Actions run step's target, LB-F310; a build-push step's image, LB-F311) are stored by ingest and scored by no reading
- **Evidence:** cmd/indexbench/langoracle_xref.go called `fusion.ResolveDocXrefs(docs)` only, and an oracle entry whose referenced file the dialect does not read was always dropped as out of scope
- **Root cause:** the scoring predates the pass's code-reading halves
- **Fix:** partial, wave c3: the identity joins (`fusion.ResolveIdentityXrefs`) and the Lambda handler bindings (`fusion.ResolveLambdaHandlers`, over the subject's files as ingest dispatches them) are scored in the xref family, and an oracle entry with `edge: handler` stays in scope when the subject holds its file; the run-step and build-push edges remain unscored
- **Status:** open (the run-step and build-push halves)
- **Impact:** github-actions' L3 says nothing about LB-F310 and LB-F311's edges
