### O1169 — the CLI paid the agent's dispatch budget, so one plan cost one verify_plan call per few dozen rows

- **Symptom:** daemon-mode `fathom verify --plan docs/plans/language-breadth.md` (768 rows) took 54 to 63 verify_plan calls, and `fathom plans status --service fathom` took 559 calls for 76 plans. On a large index each call is graph-backed (O1014).
- **Evidence:**
  - **Tool:** `fathom verify` and `fathom plans status` in daemon mode (`callVerifyPlan`, cmd/fathom/verify.go), posting to `/rpc` (the full surface).
  - **Expected:** a machine caller that reads up to 4 MiB and renders the verdicts itself gets a whole plan in one call when the daemon computes it inside its deadline.
  - **Actual:** every tool's answer passed the 16,000-byte dispatch budget (`budgetedHandler`, defaultCharBudget, internal/mcp/budgeted_handler.go). The call log's 32 KB per call is that 16,000-byte result sent twice, as the text block and as structuredContent. No caller-declared budget existed: BA-5's `budgets` block sizes only query_symbols, references, pack_context and repo_map, verify_plan took no budget argument, and no X-Fathom-* header carried one.
  - **Repro:** `fathom verify --url <daemon> --service fathom --plan docs/plans/language-breadth.md`, then count `"tool":"verify_plan"` rows in the daemon's call log.
- **Root cause:** the budget that protects an agent's context applied to machine callers too.
- **Fix:** wave fx6, vbatch, 2026-10-17. A caller declares a dispatch budget with `X-Fathom-Max-Bytes` (capped at 4 MiB, `mcp.MaxDeclaredBudget`), honoured by tools that opt in (verify_plan). The CLI declares a third of its 4 MiB read limit and asks again at the default when an answer is still too long, so the follow-up loop stays the fallback. It is a header, so no agent surface's schema or default answer changes (TestVerifyPlan_AgentSurfaceDefaultAnswerUnchanged, TestAgentSurfaceArgSchemaUnchanged). Measured in O1014's fx6 evidence: language-breadth in 1 call, `plans status` in one call per plan.
- **Status:** fixed. The console's in-process plans portfolio (`verifyPlanInProcess`) still calls at the default budget.
- **Impact:** a long plan cost its row count over about 13 in graph-backed calls, so `plans status` left big plans unmeasured whenever the daemon was loaded.
