### O534 — a Dart part file reads its library's imports, and the file resolver gives it none: about 10 file-edge pairs and the calls a part makes into the library's imports

- **Symptom:** `lib/src/frames/frame_reader.dart` (`part of 'frames.dart'`) calls `readInt24` and constructs `FrameSizeException`; fathom draws no edge to byte_utils.dart or sync_errors.dart, which frames.dart imports
- **Evidence:**
  - **Tool:** the scratch classifier, http2 and bloc, fathom cd4c1e9e
  - **Expected:** a part's names resolve against its library's imports as well as the library's own names
  - **Actual:** since LB-F246 a part's `part of` is a wildcard import of the library, which brings the library's and its parts' names but not what the library imports
  - **Repro:** frame_reader.dart:158 `var length = readInt24(bytes, offset);`
- **Root cause:** a dialect query cannot say "this file's imports are another file's"
- **Fix:** none this wave (internal/fusion/{fileresolve,exports}.go are wave lh's): when a file has a wildcard import produced by a `part of` statement, add the library file's own import specs to the part's scope (the same resolution, one hop, no re-export following of those imports). The dialect side is done: the `part of` import is already extracted
- **Status:** open
- **Impact:** about 10 of Dart's 133 missing file-edge pairs, and the call edges from parts into the library's imports (L2 reads excellent without them)
