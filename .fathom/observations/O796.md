### O796 — a large SQL data dump faults the sql tags dialect where the regex read its DDL

- **Symptom:** with `.sql` dispatched to the sql tags dialect (O794), a file of DDL followed by many INSERT rows faults in the tree-sitter engine (`tsengine: call fathom_parse_bounded: wasm error: unreachable`) and yields no symbol, where sqlextract.go returned its CREATE TABLE
- **Evidence:** a generated dump (one CREATE TABLE, then N single-row INSERTs) through `extractor.NewTSExtractor("sql")`: 2,000 rows (158 KB) and 5,000 rows (398 KB) extract 3 symbols; 10,000 rows (798 KB) and 20,000 rows (1.6 MB) fault, 0 symbols. The same class kept chinook-database's 400-600 KB dumps out of the sql reading's subjects (owner decision D2, 2026-09-28: their trees exceed the 64 MiB module cap, RT-107)
- **Root cause:** the parse tree of a large flat file passes the per-module memory cap; the engine faults rather than truncating
- **Fix:** none here, disclosed: the fault is counted on the ingest report (`TSEngineFaults`), named on stderr, and the file fingerprinted, never silent; files over 2 MiB were never extracted (MaxExtractSize)
- **Status:** open. Trigger: a tags-engine change that parses a file statement by statement (or bounds a tree by top-level node) under the cap, or an owner call for a dialect fallback to the regex on a fault; then re-measure the sql reading with a dump subject
- **Impact:** a repository whose schema lives in a single 0.5-2 MiB dump with data loses that file's tables from the index; schema and migration files (pagila's 96 KB schema, sqitch's fixtures) are read in full
