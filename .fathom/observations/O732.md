### O732 — a JSX-only query cannot be written for TSX, and React's text predicates cost extraction CPU

- **Symptom:** the typescript dialect's tags query serves both the typescript and tsx entry points, so it cannot name `jsx_element` (the typescript grammar has none and the query fails to compile); a component is found by a predicate over its body's text (`</` or `/>`), a JSX call by a wildcard node with a `<` token and a name field
- **Evidence:** LB-F377's patterns split each function node into five structural patterns whose host-side predicates pick one; extraction CPU per file (min of four runs, `NewTSExtractor("javascript")` over every file) zod 0.82 s to 1.14 s (+39%), nest 1.06 s to 1.04 s; typescript.json's CPU throughput 2.76 to 2.22 MB/s; the query's one-time compile 0.31 s to 0.56 s. Guarding the React patterns with one `#requires-text!` regex (LB-F180) made zod 3.6x slower per file in the same runs, so no guard is used
- **Root cause:** one query per dialect (`compileDialectRules`, no per-variant query), and predicates evaluated host-side after every structural match crosses the wasm boundary (`filterByPredicates`)
- **Fix:** proposed, engine (tsextract*.go, tsengine; not this item's): a variant's own query file (`variants[].queries`), so tsx names JSX nodes structurally, and guest-side `#match?` on short captures, so a rejected match never crosses; then the React patterns collapse to one per shape
- **Status:** open
- **Impact:** ingest cost on code with many module-level functions (LB-M5's guard); precision of a component found by text (a `</` in a string)
