### O492 — L4 is SCIP-only: a language whose own toolchain answers definition with file and line (cue lsp) still has no L4 oracle in the harness

- **Symptom:** CUE's L4 (def_mapping, typed_recall) is not attempted although the cue binary's language server resolves every reference, typed ones included (a field reached through a definition another package embeds), to a file and line.
- **Evidence:**
  - **Tool:** the cue oracle's probe (calibration/oracles/cue): `textDocument/definition` on `cond: web.ports[0].port` answers both `web.ports.port` and `#Kit.ports.port` (unification), and on `repo.writeWorkflows` answers base/write.cue (repo embeds base).
  - **Expected:** a tier-A typed-reference truth can be measured.
  - **Actual:** `recompute` sets def_mapping and typed_recall only from a SCIP index (`ScoreSCIPWith`'s scip_defs and the SCIP import's direct edges); a tool oracle has no field for them.
  - **Repro:** docs/bench/readings/lang/cue.json, L4 not-attempted.
- **Root cause:** the harness's L4 is defined over SCIP (design §14 table: "a SCIP producer run on ≥ 1 subject").
- **Fix:** none here; the trigger (LB-Q-cue-rest) is a SCIP writer over the language server's definition answers, or an upstream CUE SCIP producer.
- **Status:** open
- **Impact:** CUE's L4 target stays out of reach until a SCIP index exists, whatever the extractor resolves.
