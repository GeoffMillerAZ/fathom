### O406 — the dialect registry allows one dialect per source kind, so a CR dialect cannot reuse K8sWorkload

- **Symptom:** `fusion.New` panics: `source_kind "K8sWorkload" already emitted by dialect "flux"`
- **Evidence:**
  - **Tool:** any indexbench or fathom command that builds a Pipeline, after adding a doc dialect whose entity uses source_kind K8sWorkload
  - **Expected:** the brief: a dispatched CR "must still emit its object entity with the Name the kubernetes dialect gives it"
  - **Actual:** the registry (extractor.LoadDialects) refuses a second dialect emitting K8sWorkload; the name can be kept (`Kind/<namespace>/<name>`), the source kind cannot
  - **Repro:** give a new dialect's `$` entity `"source_kind": "K8sWorkload"`
- **Root cause:** a SourceKind identifies one dialect's output (TSExtractor's registry)
- **Fix:** FluxResource, ArgoResource and CrossplaneResource carry the object entity; fusion/routeref.go keys a Kubernetes namespace on core.KindK8sWorkload, which no CR entity needs (none is a routing referrer)
- **Status:** worked around
- **Impact:** a CR object read by its dialect is no longer a K8sWorkload for any consumer that filters on that kind
