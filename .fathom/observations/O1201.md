### O1201 — the status line's CPU bound measures the run, not the process start

- **Symptom:** MOD-8's `TestStatuslineCPUTimeP95AtMost100ms` reads p95 under 0.1 ms of CPU per run, three orders under its 100 ms bound, because it drives `cmdStatusline` in process.
- **Evidence:** the test's log line `status line CPU over 200 runs: p50 69µs, p95 88µs` (wave mods1, 2026-10-18); the status line that Claude Code runs is a fresh `fathom` process per refresh.
- **Root cause:** an in-process run leaves out the binary's start-up: exec, the runtime, and every package `init` in cmd/fathom (verb, page and rule registries). A subprocess loop under `-race` would measure the race runtime's start-up instead, and flip the gate.
- **Fix:** measure one built binary's start-up CPU apart (outside `-race`, from `bin/fathom statusline` against a fake daemon) and fold it into the bound, or record it in the readout of MOD-8.
- **Status:** open. Measured once by hand: `bin/fathom statusline` against a refused port took user 0.01 s and sys 0.00-0.01 s per run (`time -p`, warm), under the bound; no test holds it.
- **Impact:** the 100 ms bound is held for the run itself; the start-up share of a real refresh is checked by hand only.
