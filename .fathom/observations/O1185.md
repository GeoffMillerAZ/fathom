### O1185 — the readout hook wires the ro1a library rows, and ParseCommand with them

- **Symptom:** O1173's four library rows stayed `[ ]` after wave ro1a because no product entry point reached them.
- **Evidence:**
  - **Tool:** `bin/fathom verify --strict --json` on a fresh scratch ingest of ro1b-hook's HEAD, `docs/plans/readouts.md`.
  - **Expected:** once `fathom readout-hook` (RO-16) calls `readout.LoadRules` and `readout.Render`, RO-5, RO-6 (reached through LoadRules, which computes `Lossiness` at load) and RO-7 read `wired: pass`.
  - **Actual:** all four read `wired: pass` ("product entry point fathom::cmd/fathom/main.main reaches it"); `runtime_pass` reads unknown (informational, never blocks).
  - **Repro:** check out ro1b-hook, `go build -o bin/fathom ./cmd/fathom`, ingest to a scratch store, run the verify above.
- **Root cause:** as O1173: product reach arrives with the first caller, a later row than the library's.
- **Fix:** ro1b-hook flips RO-5, RO-6, RO-7 and RO-16. `cmdReadoutHook` also calls `shellcmd.ParseCommand` directly, so RO-3 is product-reached now too; its box belongs to the RO-4 item and is left `[ ]` here.
- **Status:** open for RO-3 only (flip it with RO-4, or on its own once re-verified).
- **Impact:** computed progress catches up with the ro1a code.
