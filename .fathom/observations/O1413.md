### O1413 — scip-clang 0.4.0 cannot index Objective-C, and not for want of an Xcode toolchain

- **Symptom:** the Objective-C row names scip-clang as its tier-A oracle; a compile database of `.m` and `.mm` entries makes it exit with nothing to index, and a `.c` copy of a `.m` indexes only the C declarations.
- **Evidence:**
  - **Tool:** `scip-clang --compdb-path compile_commands.json` 0.4.0 (sourcegraph/scip-clang v0.4.0, arm64-darwin, sha256 ff042fbc), Command Line Tools 27.0 SDK (no Xcode installed, Foundation and UIKit headers present)
  - **Expected:** an index with the classes, methods and message sends of AFNetworking's `AFURLResponseSerialization.m`
  - **Actual:** `error driver : compilation database has no entries that could be processed` for `-x objective-c` entries on `.m`; with the same file copied to `.c` (`-x objective-c`, `-isysroot` the SDK) the index holds 183 mentions, all C: `AFErrorWithUnderlyingError(<hash>).`, `AFURLResponseSerializationErrorDomain.`, macros and the SDK's own typedefs; no interface, implementation, method or message-send symbol
  - **Repro:** `scip-clang --compdb-path <db> --index-output-path x.scip` over a database of one `.m` entry, then of its `.c` copy, `strings x.scip | grep AF`
- **Root cause:** the indexer's frontend visits C and C++ declarations (`cxx . . $` symbols) and its driver filters the database by C and C++ extensions; it has no Objective-C visitor. The host's toolchain is not the limit (the `.c` copy parses with 0 errored units against the CLT SDK).
- **Fix:** none here. The L1 oracle is ctags (tier B, `ObjectiveC` parser) and the L2 and L3 oracle is the compiler's own front end through libclang (calibration/oracles/clang-objc, tier B because the include roots are the run's, the subjects shipping no compile database). A tier-A Objective-C reading needs an Objective-C-capable SCIP or index-store producer: LB-Q-objective-c-rest.
- **Status:** open
