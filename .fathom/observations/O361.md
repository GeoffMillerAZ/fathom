### O361 — a dispatched tags dialect is parsed twice per file: once to extract, once for the file-resolved pass

- **Symptom:** after the C dispatch switch (LB-F119) libuv's ingest costs 42.1 G instructions against 33.5 G before it (+26%), the only subject of the LB-M5 polyglot set that moves (docs/bench/readings/lang/footprint.md, 2026-10-01).
- **Evidence:**
  - **Tool:** `/usr/bin/time -l fathom ingest --json --store <fresh> --path <one subject, nested>` at 32afe369 (main) and 5556eb84 (head), fresh stores and caches.
  - **Expected:** serving `.c` from the tags dialect replaces the CGO parse; the wasm parse the file-resolved pass already ran is the only one left.
  - **Actual:** the pipeline extracts each `.c` file with `TSExtractor.Extract` (one wasm parse), then `enrichFileResolvedEdges` -> `resolveLang` -> `extractImports` calls `TSExtractor.ExtractFileSpecs` on the same file (internal/fusion/fileresolve.go), a second wasm parse; before the switch the first parse was the CGO walker's, faster than wasm. The same held for every tags-dispatched file-resolve language, and the CGO incumbents (C#, Java, Rust, PHP, C++) were parsed natively to extract and again in wasm for their file specs.
  - **Repro:** the per-subject runs in the footprint section.
- **Root cause:** extraction and the file-resolved pass are separate stages that each parse; `fileResolveExtractor` already shared the dispatched `TSExtractor` instance, but not its tree.
- **Fix:** wave ic, item oneparse. `TSExtractor.ExtractWithFileSpecs` returns a file's symbols and its `FileSpecs` from one parse and one tags-query run (EW-52); the extract stage keeps the specs in a per-ingest in-memory map keyed by path, language and content hash (internal/fusion/specmemo.go) and `resolveLang` takes them before parsing, parsing only a file the stage did not see; the incumbents run the dialect's tags and references queries over the go-tree-sitter tree they already hold (`nativeFileSpecs`, same grammar commit), so none of their files is parsed in wasm (EW-53; all five matched the wasm path on every file of the polyglot subjects). A header the router sent to the other language keeps its parse. No table, cache or job; no `ExtractorEpoch` bump. Reading: docs/bench/readings/efficiency-wave/one-parse.md.
- **Status:** fixed (EW-52, EW-53, EW-54). Instructions fell 16 to 45% per polyglot subject (libuv 54.1 G to 38.7 G, Polly 85.6 G to 51.2 G, ripgrep 36.9 G to 22.6 G, retrofit 183.8 G to 117.6 G; seven summed 582.0 G to 401.8 G) and the whole tree 1,415.3 G to 1,180.7 G, with `typed_edges`, `file_imports` and `observations` byte-identical and peak RSS +1.2%.
- **Impact:** LB-M5 (1.9% of the polyglot set's instructions from C alone; more for every language that switches under D1). Not the reason LB-M5 fails: the whole tree still costs 2.94 times its subjects summed (O362).
