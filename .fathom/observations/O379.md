### O379 — ingest's file-resolve pass is keyed by file extension, so a dialect claimed by basename (meson.build, CMakeLists.txt) stores no file-resolved edge: Meson's subdir() imports resolve in lang-oracle and nowhere in ingest

- **Symptom:** `meson.build`, `meson.options`, `meson_options.txt` and `CMakeLists.txt` are in no file-resolve language's extension set; only `*.cmake` is
- **Evidence:**
  - **Tool:** `internal/fusion/fileresolve.go` fileResolveIndex and fileResolveLangFor (`path.Ext` against `FileResolveLang.Extensions`), `internal/extractor/fileresolvelangs.go` FileResolveLangs (extensions from `dialectExtensions`), `TestResolveFileEdges_MesonSubdirs`
  - **Expected:** an ingest of a repository whose root meson.build calls `subdir('src')` and links a target defined in src/meson.build stores a file-resolved edge, as `ResolveFileEdges` draws it on the same files
  - **Actual:** `ResolveFileEdges("meson", ...)` called directly draws `meson.build|app -> src/meson.build|core`; ingest never offers a `.build` or `meson.build` path to it
  - **Repro:** `go test ./internal/fusion -run TestResolveFileEdges_MesonSubdirs` (strategy) against an Ingest of the same fixture (no edge)
- **Root cause:** the pass maps a path to its language by extension alone
- **Fix:** none here (`fileresolve.go` is item cinc's this wave): `FileResolveLang` gains `Basenames` from the manifest's `match.basenames`, `fileResolveIndex` indexes them and `fileResolveLangFor` tries `path.Base(relPath)` before `path.Ext`; `typededges.go`'s meson and cmake entries move to "file" once it lands, with the tracker row
- **Status:** open
- **Impact:** Meson's and CMake's L3 is not product-reached even where the strategy resolves a name (a parent to its child); LB-F128 does not help until this lands too
