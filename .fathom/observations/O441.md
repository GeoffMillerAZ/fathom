### O441 — scip-typescript was run without the subject's tsconfig paths and with no dependency installed: nest's `@nestjs/*` imports resolved to nothing, and fixing it moves TypeScript's L3 from good to unmet

- **Symptom:** of nest's 3,573 fathom-only call pairs, 771 were calls through an import scip-typescript recorded as a `local` (an unresolved binding) and 1,747 members of receivers it gave no occurrence at all (O440's b, a, c, d); `NestFactory.create`, `this.httpAdapter.initHttpServer`, `res.send` and `of(...)` had no symbol.
- **Evidence:**
  - **Tool:** calibration/oracles/scip-typescript/run.sh (scip-typescript 0.4.0, node v26.10.0) re-run on clean clones at the readings' SHAs, then `indexbench lang-oracle` and the O440 classifier on each index.
  - **Expected:** the index resolves the subject's own imports the way its compiler does (nest's root tsconfig maps `@nestjs/common` to `./packages/common`; zod resolves `zod/v4/core` through its `@zod/source` condition).
  - **Actual:** run.sh wrote a tsconfig.json of its own over the subject's (allowJs, CommonJS, no `paths`, no `customConditions`) and the clone had no node_modules. Re-running the old recipe reproduces the 2026-09-28 index's counts exactly; with the subject's options extended and its lockfile installed (`npm ci --ignore-scripts`, `pnpm install --frozen-lockfile --ignore-scripts`; express by `npm install --before` its commit date), nest's call truth under the same call-site rules grows 6,501 -> 7,972, its pairs with no occurrence at any call site fall 1,833 -> 410, and zod's 142 -> 19. axios's own tsconfig.json is its d.ts type test's (no allowJs, module node16, types []): extending it, 39 of lib/'s relative imports stopped resolving, so axios runs with run.sh's own options (OWN_TSCONFIG=no).
  - **Repro:** the old run.sh from git history versus calibration/oracles/scip-typescript/{run.sh,README.md} at 43c90bb4, on nest 9ff83d54; `lang-oracle -scip` on each.
- **Root cause:** the recipe replaced the subject's compiler options to widen the file set (nest's tsconfig leaves sample/ out) and never installed dependencies; the Python oracle had the same environment fault (O263).
- **Fix:** run.sh extends the subject's own tsconfig.json (its `include` replaced by the measured globs) and the README installs each subject's dependencies in an oracle checkout apart from the measured one (43c90bb4). TypeScript L2 is measured on it (O440).
- **Consequence, L3 (not fixed here):** the oracle now resolves 3,292 in-repo imports fathom's TypeScript resolver does not (nest 3,069 `@nestjs/*` path-mapped imports, zod 223 `zod/...` workspace self-references): import_resolution 1 -> .5342 (3,775 of 7,067), file_edge_recall .3872 -> .1781 (1,841 of 10,336), L3 good -> unmet. The earlier "good" was measured where the oracle resolved none of these either. JavaScript's L3 is unchanged (axios runs with the old options; express has no tsconfig): import_resolution 1 (387 of 387), file_edge_recall .1795 (70 of 390), as before.
- **Status:** fixed (oracle recipe); open (fathom's TypeScript resolver: tsconfig `paths`/`baseUrl` and a workspace package's own name)
- **Impact:** every TypeScript reading taken with the old recipe under-counted both the oracle's truth and fathom's resolution gap; a resolver for tsconfig `paths` and workspace package names is TypeScript's L3 trigger (LB-Q-typescript-rest).
