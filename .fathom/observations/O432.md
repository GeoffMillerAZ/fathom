### O432 — lang-oracle drops a file it cannot read as if ingest's gates had skipped it

- **Symptom:** the same `indexbench lang-oracle` command on the same subject and oracle measured 4,713, 4,469, 3,218, 2,877 and 4,560 files in five runs; a short run still writes a reading with level and grades, and says only "N tool-oracle entries on files fathom does not read (ingest's gates, discovery's exclusions) were left out of scope (§1.4)"
- **Evidence:**
  - **Tool:** `indexbench lang-oracle -dialect aws-iam-policy -subject <tenchi-security/camp d18c5e08> -tool-oracle <iam-camp.json> -out <reading>` (wave ox, 2026-10-02), on the external volume while macOS TCC intermittently refuses reads ("operation not permitted")
  - **Expected:** a file that cannot be read fails the measurement, or is counted under its own reason, never folded into the §1.4 out-of-scope count
  - **Actual:** the run exits 0 with a reading over a subset (camp: 2,877 of 4,713 files, 125,966 oracle entries "out of scope"), nothing on stderr names a read error; only comparing `subjects[].files` with an earlier reading shows it
  - **Repro:** run the command above while reads under the subject fail intermittently; compare `subjects[].files` across runs
- **Root cause:** not traced (cmd/indexbench is out of this item's files); the measured-file list appears to come from reads whose errors are treated as "not read"
- **Fix:** open: fail the subject (or count `unreadable` apart) when a discovered file cannot be read; until then a worker checks `subjects[].files` against the previous reading before committing one (wave ox did: every reading it committed measured the full file count)
- **Status:** open
- **Impact:** a reading can silently shrink its scope and still grade excellent; on this machine the EPERM wedge makes it frequent
