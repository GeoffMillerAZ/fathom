### O1173 — a library row whose wiring is a later row cannot flip in its own wave under verify --strict

- **Symptom:** wave ro1a built RO-3 (`shellcmd.ParseCommand`), RO-5 (`readout.Render`), RO-6 (`readout.Lossiness`) and RO-7 (`readout.LoadRules`) with their named `reachable_from` tests green, and `bin/fathom verify --strict` on a fresh scratch ingest of the committed HEAD still refused all four.
- **Evidence:**
  - **Tool:** `fathom verify --strict --store <scratch>/verify.sqlite --service fathom --plan docs/plans/readouts.md`.
  - **Expected:** a row whose `{symbol, package, reachable_from}` tag holds (the symbol exists and the named test reaches it) verifies.
  - **Actual:** each row printed `wired: no product entry point reaches it (no main, and no init of a package a main links)` and `runtime_pass: no attested run in test_runs for <test> (reachable_from)`.
  - **Repro:** check out ro1a-core, `go build -o bin/fathom ./cmd/fathom`, ingest to a scratch store, then mark RO-3/5/6/7 `[x]` and run the verify above.
- **Root cause:** the plan puts the library rows (phase 0) in one wave and their first product caller (RO-16, `fathom readout-hook`, which calls Render and LoadRules; RO-4 for ParseCommand) in a later one, while `--strict` requires product reach (ADR-018 amendment 2026-09-28) and an attested run (a test-kit envelope through `fathom tests ingest --results`, which the worker contract does not name). The rows' tags cannot be satisfied by their own wave without `library: true`, which the wave contract forbids.
- **Fix:** none yet. Either the RO-16 and RO-4 waves flip RO-3/5/6/7 when they wire them (re-verifying the four rows), or the plan states that dependency on each row; and the worker contract names the runtime_pass attestation step if `--strict` needs it.
- **Status:** open. RO-3, RO-5, RO-6 and RO-7 stay `[ ]` with the code on ro1a-core.
- **Impact:** a wave reads as zero rows proven while its code is done and tested, so computed progress lags the work until the wiring wave.
