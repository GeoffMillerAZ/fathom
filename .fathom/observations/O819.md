### O819 — the rule-outcome ledger wrote nothing for nine days: the tracker keyed on the top row, and the daemon serves raw rows first (INC-27)

- **Symptom:** `~/.fathom/rule-outcomes.jsonl` held 67 rows, the last at 2026-10-01T04:14Z from build fa1e1d16 (schema 1, the pre-JF-1 names), while JF-1 and GL-10 read `[x]` and the edit hook answered 21,247 times from 2026-10-03 to 2026-10-10, 90 of them with rules
- **Root cause:** three gaps, all silent. (1) `trackRuleOutcome` was called with `govRules[0].ClaimID` only (edithook.go:195). Wave O1's raw-section fallback serves an uncompiled governing section (Tier `raw`, no claim id) AHEAD of the compiled rows, and with the compiled layer frozen since the 2026-09-29 spend hold while AGENTS.md and ADR.md kept changing, a raw row topped the served set everywhere: on the deployed daemon (7863e4c3, 2026-10-10) the top governing row was raw on 64 of 64 sampled files across fathom, app-kit and conjure, with claim-bearing rows at index 2. `recordRuleOutcome` drops an empty rule id without a trace, so every served answer recorded nothing. (2) The Bash-write path (84 of the 90 emissions since 10-03) never called the tracker. (3) A guarded edit's post call skipped the tracker with the SR-48 ask (PR-11), and the pre hook writes no row. Hypotheses tested and ruled out: a refactor moving serving off the branch (`git log -S` over ruleoutcome*.go and edithook*.go since fa1e1d16 shows none; no serving code changed between fa1e1d16 and the 10-01T06:01Z daemon restart either), FATHOM_HOME or path resolution (the deployed hooks run `fathom edit-hook` from ~/.local/bin, FATHOM_HOME unset, the ledger path is ~/.fathom), and a swallowed write error: a build of 7863e4c3, run as the hook with a scratch FATHOM_HOME and fresh memos, writes one served row when the daemon's first rule carries a claim id and none when two raw rows come first; the fixed build writes one in both orders (the hooks log, same directory, is written on every call, so no TCC or permission error either). The unit tests that proved JF-1 and GL-10 fed the tracker a claim id directly, or a fake daemon whose FIRST rule carried one: an oracle the deployed daemon never matched
- **Fix:** the tracker keys a file's turn on the first served rule that is a claim (`topServedClaimID`); the Bash-write path records per written file (`mergedObligations.topClaims`); the paired post call records (PR-11). `TestDeployedEditHookWritesRuleOutcomeRowsAndSilenceReasons` drives the hook as deployed (re-exec through `main`, the settings.json command lines, a scratch FATHOM_HOME, a daemon answering raw rows first). Doctor's `rule_outcome_writer` row names a ledger silent 72 h while the hook served claims (GL-24)
- **Evidence:** ledger tail and line count; hooks.jsonl answered beats by phase since 10-03 (21,124 pre/command, 2,566 post-bash seen, 537 post seen; emitted: 84 post-bash, 5 post, 1 pre); `obligations` against the live daemon with `X-Fathom-Origin: edit-hook`
- **Status:** fixed (GL-24, PR-11); GL-M6 reads the deployed ledger for 7 days
