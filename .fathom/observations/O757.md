### O757 — a `gone: pattern` keeps its backslashes as written: LB-F358's `\\(` could never match the prose it proved gone

- **Symptom:** LB-F358 read proven with `gone: pattern "heuristic \\(.(javaextract|cppextract|phpextract)\\.go.\\) dispatched"`, but that regexp asks for a literal backslash before each parenthesis and dot, so it matches nothing even in the tree that still held the stale cells; a row written the same way with an unbalanced `\\(` (wave lf3's first LB-F392 and LB-F393) is refused instead: `gone: pattern does not compile: error parsing regexp: missing closing )`
- **Evidence:** `git grep -P` of the row's pattern at 869db1b0~1, where `docs/languages.md` L34, L39 and L47 and the template still read "heuristic (`javaextract.go`) dispatched", finds 0 lines; the character-class form `heuristic [(].(javaextract|cppextract|phpextract)[.]go.[)] dispatched` finds all six at 869db1b0~1 and none at e186fbc3; `fathom verify --strict` on wave lf3 item cgo's scratch ingest printed the compile error with the doubled backslashes intact
- **Root cause:** a `gone: pattern` value is used as the regexp verbatim (only `(?m)` is prepended), while an `oracle: lexical` row's `pattern:` is written with single backslashes (`\.`, `\s*`, `\{`), so a row that doubles them, as JSON or Go string habit suggests, compiles to a different regexp and a balanced one passes vacuously
- **Fix:** LB-F358's pattern is the character-class form (wave lf3, item cgo; it still verifies: the prose is gone); LB-F392 and LB-F393 use `[(]`. Proposed (internal/verify, not this item's): refuse a `gone: pattern` that matches nothing in the row's base revision, or at least warn on `\\` in one, and say in docs/plans/README.md's `gone` row that the regexp is taken as written
