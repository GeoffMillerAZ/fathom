### O1420 — the Prisma oracle cannot be prisma-ast or a 7.x/8.x engine

- **Symptom:** the brief's fallback (`@mrleebo/prisma-ast`, tier C) and the newest engine both fail on real schemas.
- **Evidence:**
  - **Tool:** `@prisma/prisma-schema-wasm` 8.1.0 `get_dmmf` on a schema with `url = env(...)`: `P1012 The datasource property url is no longer supported`; the 6.19.0 build accepts it, and every schema in both calibration subjects carries `url`
  - **Tool:** `@mrleebo/prisma-ast` 0.16.0 `getSchema`: `location` is null on every block, no member has a position, and a field whose `@relation(` spans lines throws `Expecting ')'`
  - **Tool:** `get_dmmf` omits an `Unsupported("point")` column and validates the datasource provider (composite types need mongodb, views need the `views` preview feature)
  - **Tool:** `get_dmmf` runs offline; no query-engine binary is downloaded
- **Root cause:** getDMMF attests names and relations but carries no position, and the only JS AST parser has no positions and a weaker grammar than the engine.
- **Fix:** `calibration/oracles/prisma-dmmf` takes names, fields, kinds and `@relation` lists from the 6.19 engine (tier A) and positions from its own bracket-depth line scan, cross-checked both ways (`name_disagreements`, 0 on both subjects). A schema the engine rejects falls back to the scan (tier C, `engine_rejected`). Prisma 6.19 itself rejects a field attribute spanning lines, so no fixture has one.
- **Status:** open (revisit when a calibration subject needs the 7.x engine)
