# 0.10.0 — the rule-outcome events say what they measure

**Breaking:** the edit hook's rule-outcome events `complied` and `violated` are
renamed `top_changed` and `still_served`, and the JSON fields and printed words
that counted them follow. Nothing is lost: rows already in
`~/.fathom/rule-outcomes.jsonl` are read under the new names.

| Before | From 0.10.0 |
|---|---|
| ledger event `violated`: the same rule topped the file's served set on the previous edit too | `still_served` (schema_version 2 rows); an old `violated` row is read as `still_served` |
| ledger event `complied`: another rule topped the file this time | `top_changed`; an old `complied` row is read as `top_changed` |
| `fathom obligations` and `/explain`: `served 3 · complied 1 · violated 1` | `served 3 · top changed 1 · still served 1` |
| `fathom obligations --json` and `/explain` JSON: `outcomes.v.rules[].complied`, `.violated` | `.top_changed`, `.still_served` |
| `fathom claim effectiveness --json` and `/rules`: `complied_30d`, `violated_30d`, `compliance_rate`, `violation_rate` | `top_changed_30d`, `still_served_30d`, `top_changed_rate`, `still_served_rate` |
| `fathom claim effectiveness` text: `complied N violated N` | `top_changed N still_served N` |

`violated` is no longer an event: nothing writes it. A checkable rule denies the
edit and records `blocked` (PR-10), which is the one place a violation is
measured.

## What to do

- **A script that reads the ledger or the JSON fields above:** read the new
  names. To read a ledger that spans the upgrade, treat `complied` as
  `top_changed` and `violated` as `still_served`; both generations are in the
  same file.
- **A script that read `compliance_rate` or `violation_rate` as how well edits
  followed a rule:** it never measured that. Rules are served by glob scope, so a
  prose rule reads `still_served` on every repeat edit of the same file whether or
  not the edit complied. `top_changed_rate` and `still_served_rate` carry the same
  arithmetic under names that say what it is.
- **Nothing to migrate on disk:** the ledger is not rewritten, and the class a
  rule falls in (`ignored`, `effective`, ...) is computed from the same counts as
  before.

## Why

The tracker evaluates no check. `docs/design/judgment-foundations.md` section 5
and the correction note in `docs/design/governance-learning.md` record that the
two events measured scope persistence and churn, and ADR-057 settled that a
checkable rule records `blocked`. Keeping the old names would keep reporting a
repeat edit as a violation.
