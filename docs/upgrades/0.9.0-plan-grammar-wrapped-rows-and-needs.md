# 0.9.0 — a wrapped plan row keeps its contract, and a deferred `needs:` target blocks

**Breaking:** two items of plan grammar v2 change, and both are on the compatibility surface
(`docs/intent/scope.md`: "the checkbox-line rule" and the annotation keys).

| Item | Before | From 0.9.0 |
|---|---|---|
| The checkbox-line rule (G2-5) | the `{…}` block had to sit on the checkbox line; a row whose block sat on a continuation line was read as a positional `md-NNN` row with no contract and verified `no-contract` | when the checkbox line carries no `{…}` block, the row's **indented** continuation lines (up to a blank line, a list item, an HTML comment or a code fence) are part of it: title text, spec ids and a block that may itself span lines. A row whose checkbox line carries its block reads that line alone. An annotation on an unindented line under a row is still not read, and `fathom verify` names it |
| `needs:` (G2-6) | a claimed or dispositioned target satisfied it | only a claimed target satisfies it. A deferred `[-]` target keeps the dependent blocked until it revives; a refused one (or any disposition but deferred) names the dependent as needing re-planning (`replan` in `plans next --json`) |

## What changes for you

- **A claimed wrapped row is now checked.** It used to pass the gate unchecked. It now carries its
  declared id and contract, and `fathom verify --strict` (the pre-push gate) can fail it. Measured on
  20 wrapped rows (`docs/bench/readings/plan-grammar/wrapped-rows.md`): all 20 were `no-contract`
  before; after, 3 proven, 13 disproven, 3 unproven and 1 still `no-contract`. Of nine claimed rows
  in one adopter's plan, three now prove, five fail the gate and one stays `no-contract`.
- **Its id changes** from `md-NNN` to the id in its block. Anything keyed on the positional id (a
  lease, a thread route, a `plan_row_checked` condition) names the declared id instead.
- **An older fathom still reads one line.** A plan read by a fathom older than 0.9.0 (a pinned
  binary in another clone's hook, say) sees a wrapped row as `no-contract`. Keep rows on one line
  where both versions read the plan.
- **`plans next --eligible-only` stops offering a row that waits on a deferred row.** In this
  repository JF-14 (needs JF-13, deferred) moved from eligible to blocked, and feature-map's wrapped
  rows now dispatch by their real `needs:` (FM-1 and FM-6 eligible, the rest blocked).

## What to do

- After upgrading, run `fathom verify --strict` on every plan. A wrapped row that now fails gets its
  evidence, or its box is unchecked; never add `library: true` or `skip_test` to keep it passing.
- A `needs:` that names a deferred row: revive the target, drop the need, or re-plan the dependent. A
  row `plans next` marks as needing re-planning waits on a refused target and will never be
  eligible as written.

## Why

A wrapped row was the gate's blind spot: the parser read the checkbox line only, so a claimed row
with its annotation on the next line was never checked. And "deferred" satisfying `needs:` let
dispatch offer rows whose prerequisites were not built (`docs/plans/efficiency-wave.md`, stage 1).
