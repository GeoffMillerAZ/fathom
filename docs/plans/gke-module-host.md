# GKE Module Host — read-only federation over N conforming stores

Design (normative — see `docs/vision/12-governed-knowledge-engine.md` §3 for
the architecture decision this plan implements, and §1 for the owner
decision that pulls this forward ahead of `docs/design/product-vision.md`
§4 H3's external-adoption entry condition; that entry condition is
**unmet** and this plan does not claim otherwise):

- **What "module host" means.** `fathom serve-http` mounting N conforming
  module stores (`docs/spec/store-format-v0.md` + `docs/spec/
  expert-module-v0.md`) **read-only**, as one surface. Not a new binary,
  not a second engine — `docs/design/expert-modules.md` §1's "there is no
  second engine, no second schema" extended across store boundaries. Every
  answer carries per-module identity + evidence tier + staleness
  (`store-format-v0.md` §3 Server conformance, generalized to N stores
  instead of one).
- **Mounting mechanism.** A multi-store query layer behind `pkg/platform`'s
  existing cross-service graph machinery (`pkg/platform.Build`,
  `pkg/platform.BuildFromStore`, the primitive
  `pkg/platform.CrossRepoBlastRadius` already generalizes) — this is
  `ATTACH`-shaped in spirit (`store-format-v0.md` §11 names exactly this
  shape as living "at a layer *above* this format"), not a rewrite of the
  store engine and not the DuckDB-specific `ATTACH` mechanism
  `product-vision.md` §4 H3 describes (that description predates ADR-025's
  SQLite-only reality — this plan targets SQLite multi-store query
  composition, the technical re-check `product-vision.md`'s engine-
  assumption note already calls for).
- **Conformance at mount, not at query time.** A store is checked against
  `store-format-v0.md`'s file-identity markers (`application_id =
  0x46415448`) and the conformance level the host requires (at minimum L0 +
  Server) the moment it is mounted — never lazily discovered mid-query. A
  store that fails this check is refused loudly; it is never silently
  served as if it were empty or partially trusted (doctrine 3, "never
  silent").
- **Surface exposure — the doctrine-4 argument (decided here, not
  deferred).** Two options were on the table: (a) extend the existing
  `/rpc/agent` 16-tool allowlist (`docs/mcp-tools.md`) with module-scoped
  variants of `obligations`/`staleness_report`, or (b) a new scoped surface,
  `/rpc/modules`, serving a small, module-host-specific tool set. **This
  plan picks (b), a new scoped surface, not new tools on `/rpc/agent`.**
  Reasoning: `/rpc/agent`'s allowlist is a single-store-per-call contract
  today (every tool takes one `service`) — bending it to mean "one module,
  chosen from a federated set" would be a silent behavior change on an
  already-registered, already-in-use surface (the same class of risk the
  `read_source` addition (T5-4, `docs/plans/trust-and-tokenomics.md`)
  deliberately avoided by adding a new tool rather than overloading an
  existing one). A new surface, gated behind its own explicit opt-in
  (nobody's `~/.claude.json` points at `/rpc/modules` until they choose to),
  costs zero regression risk to `/rpc/agent`'s existing 16-tool contract and
  keeps doctrine 4's "no net tool growth" honest: `/rpc/modules` reuses the
  *same* tool shapes (`obligations`-pattern scope lookup, staleness report)
  federation-wrapped, not new tool verbs — the net-new surface is a scoping
  boundary, the same kind of move `/rpc/agent` itself already was
  (ADR-014), not a new capability contract. No tool ships under this plan
  without this paragraph's reasoning holding; if a reviewer finds it doesn't
  hold, `/rpc/agent` extension is the fallback, not silently taken as the
  default.
- **Auth + read-only hardening are launch requirements for hosted, not
  later hardening** (`docs/vision/12-governed-knowledge-engine.md` §2 law
  9). The local, loopback-only, unauthenticated daemon (`docs/mcp-tools.md`)
  stays exactly as it is — this plan's hardening rows apply only to a
  network-reachable deployment, which does not exist until they are proven.

## Tasks

- [x] Mount N conforming module stores read-only; each mount conformance-checked at mount time against the store-format-v0 markers (`application_id`/`user_version`) and required-schema tables for the level the host requires {id: GKE-MH-1, symbol: MountReadOnly, package: internal/store}
  - **Amendment:** the row's original anchor (`BuildFromStore`, `pkg/platform`) was a placeholder — `BuildFromStore` is a pure computation over an already-open `store.Store`, not a mount/lifecycle primitive. Re-anchored to what was actually built: `store.MountReadOnly(path, level)` (`internal/store/conformance.go`) does the conformance check + genuinely read-only open in one refuse-or-return call, and `modulehost.Host.Mount` (`internal/modulehost/host.go`) is the stateful registry wrapping it (name collision check, then `MountReadOnly`, then register — any failure leaves the mounted set untouched). Markers: `application_id == 0x46415448` AND `user_version >= 1` (stricter than store-format-v0.md §2's own general-reader fallback for `user_version == 0` — a mount requires the explicit signal, see `ReasonUnversioned`'s doc comment). Schema: `checkRequiredSchema` walks `requiredTablesForLevel(level)` against live `sqlite_master`/`PRAGMA table_info`. Tests: `TestMountReadOnly_SucceedsAndIsGenuinelyReadOnly`, `TestHost_MountAndList`, `TestHost_MountRefusesLoudlyAndLeavesSetUnchanged`, `TestHost_MountDuplicateNameRefused` (internal/store, internal/modulehost).
- [x] Unmount a module cleanly (host continues serving the remaining set; no stale reference to the unmounted store's connection survives the call) {id: GKE-MH-2, symbol: Unmount, package: internal/modulehost}
  - **Amendment:** re-anchored from `pkg/platform.BuildFromStore` (no unmount concept exists there) to `modulehost.Host.Unmount`, the actual lifecycle method. Test: `TestHost_UnmountRemovesAndClosesNoStaleReference` (mounts two modules, unmounts one, asserts `ListModules` sees only the survivor, and a repeat `Unmount` errors).

- [x] Staleness honesty per module: a federated answer's reported freshness is never fresher than its least-fresh contributing module; each module's own watermark drift is independently detectable from stored data alone (store-format-v0.md §6, L1 conformance, generalized) {id: GKE-MH-6, symbol: ModuleStaleness, package: internal/modulehost}
  - **Amendment:** same `pkg/platform.Graph` → `internal/modulehost` re-anchor as GKE-MH-3/4. `Host.ModuleStaleness` reports each (module, service) pair INDEPENDENTLY (`StatusUnknownDetached | StatusFresh | StatusDrifted`) rather than collapsing N modules into one aggregate number — "never fresher than the least-fresh contributor" falls out structurally, since nothing ever averages or takes a best-case across modules. Default is `StatusUnknownDetached`: a mounted module is a detached corpus (`store.MountReadOnly` opens a bare file, no live connector) — `store-format-v0.md` §6's watermark comparison needs a CURRENT watermark to compare against, so v0's honest default per the design section's own wording ("unknown-detached unless the module's corpus path is locally present and re-checkable") is refusal, not a guess. Opportunistic upgrade to fresh/drifted only when `service_meta.path` resolves locally AND is a git working tree (`localGitHead`) — a spec-silent case (expert-module-v0.md §4.3 requires the floor answer be derivable WITHOUT a live connection; it doesn't forbid a bonus recheck when available) resolved toward the honest-refusal default first, live-recheck second. Tests: `TestModuleStaleness_UnknownDetachedWhenPathAbsent`, `TestModuleStaleness_NotMounted`, `TestModuleStaleness_FreshAndDriftedWhenCorpusLocallyPresent` (real scratch git repo, one module pinned at current HEAD → fresh, one pinned at a bogus SHA → drifted).
- [x] Auth for the hosted deployment mode: a network-reachable module host refuses an unauthenticated request, mirroring the local daemon's loopback-only trust boundary being replaced with an explicit one {id: GKE-MH-7, symbol: modulesAuthMiddleware, package: cmd/fathom}
  - **Un-skipped** (the auth code path this row's `skip_test` said didn't exist yet is now built). `--modules-token-env <NAME>` (serve-http flag) names an environment variable holding the bearer token; the token itself is never a flag/config value, only the var NAME (`cmd/fathom/servehttp.go`). An empty/unset named variable aborts startup loudly (misconfiguration, not silent-disabled auth). `modulesAuthMiddleware` gates ONLY `/rpc/modules` (and sub-paths) — bare `/rpc` and every other named surface stay exactly as unauthenticated as before; constant-time compare via `crypto/subtle.ConstantTimeCompare`; the token is never logged, and a 401 body never echoes the caller-supplied credential. Default OFF (empty token = middleware is a passthrough), matching the design section's "launch requirement for hosted, not local loopback." Tests: `TestServeHTTPModulesAuth_401WithoutToken200With` (no header → 401; wrong token → 401; correct token → 200; response body never contains the token), `TestServeHTTPModulesAuth_OnlyGatesModulesPath` (bare `/rpc` and `/rpc/agent` stay 200 with no `Authorization` header even when a modules token is configured), `TestModulesAuthMiddleware_DisabledWhenTokenEmpty`, `TestRunServeHTTP_RefusesEmptyModulesTokenEnv`.
- [x] Read-only mode enforced at the store-open layer for the hosted deployment: a mounted module store cannot be written by the hosting process under any code path reachable from the module-host surface (law 9) {id: GKE-MH-8, symbol: MountReadOnly, package: internal/store}
  - **Un-skipped** (this row's blocking gap — "`store.Open` always runs `createSchema`, no genuine read-only open path exists" — is now closed). `store.MountReadOnly` opens via `sqliteReadOnlyDSN` (`file:<path>?mode=ro&_pragma=busy_timeout(5000)`): the `file:` prefix is required for `modernc.org/sqlite`'s `newConn` to preserve the query string into the name passed to `sqlite3_open_v2`, and `mode=ro` is honored by SQLite's OWN URI parser (the driver's flags are hardcoded `READWRITE|CREATE`, but `mode=ro` is MORE restrictive, which SQLite's URI rules permit) — verified directly against `modernc.org/sqlite` v1.52.0 before writing any product code (a throwaway probe: read succeeds, a write returns `SQLITE_READONLY (8)`, and opening a MISSING path fails rather than creating one). `MountReadOnly` never calls `createSchema`/`stampFormatMarkers` — no code path from a mount can write. Test: `TestMountReadOnly_SucceedsAndIsGenuinelyReadOnly` (seeds via the writer path, closes, `MountReadOnly`s the same file, asserts a read succeeds AND `PutObservations` through the mounted handle errors).
- [x] Conformance refusal tests: a non-conforming store (wrong `application_id`, missing required table, `.duckdb` extension) is refused loudly at mount — never silently degraded to an empty or partial module {id: GKE-MH-9, symbol: MountReadOnly, package: internal/store}
  - **Amendment:** re-anchored from `BackendForPath` (the pre-existing WRITE-path dispatcher, unrelated to mount-time conformance) to `MountReadOnly`, the function actually being tested. Every refusal returns a typed `*store.ConformanceError{Path, Reason, Detail}` with a stable `Reason` code (`ReasonDuckDBUnsupported`, `ReasonUnsupportedExtension`, `ReasonOpenFailed`, `ReasonBadApplicationID`, `ReasonMissingTable`) — never a generic wrapped error. Tests: `TestMountReadOnly_RefusesDuckDBExtension`, `TestMountReadOnly_RefusesUnsupportedExtension`, `TestMountReadOnly_RefusesMissingFile`, `TestMountReadOnly_RefusesBadApplicationID`, `TestMountReadOnly_RefusesMissingTable` — each asserts both the exact `Reason` and a non-empty `Path`.
- [x] Conformance refusal tests: a conforming-but-insufficient-level store (e.g. L0 only, mounted where the host requires Server conformance) is refused with a named reason, not silently served at a lower honesty bar than the host's contract promises {id: GKE-MH-10, symbol: MountReadOnly, package: internal/store}
  - **Amendment (wording + anchor):** re-anchored from `BackendForPath` to `MountReadOnly`, same as GKE-MH-9. Wording note: store-format-v0.md §3 states Server conformance "adds no new table over L0/Writer" — it is a BEHAVIORAL requirement on the serving layer, not a schema fact `MountReadOnly` can check. The testable schema-level escalation the row's own example anticipates ("L0 only, mounted where the host requires [a stricter level]") is `LevelL0` vs `LevelWriter` (`claim_events`/`compile_runs`) — `ConformanceLevel`'s doc comment states this reconciliation explicitly. `checkRequiredSchema` returns a DISTINCT reason (`ReasonInsufficientLevel`) for a table/column required only above `LevelL0`, separate from `ReasonMissingTable`/`ReasonMissingColumn` for an L0-baseline gap (GKE-MH-9) — so a caller (or a reviewer) can tell "not a fathom store at all" apart from "a real module, just not compiled to the level this mount demands." Test: `TestMountReadOnly_LevelEscalation_InsufficientLevel` (a hand-built store with every L0 table present but neither Writer table: `MountReadOnly(path, LevelL0)` succeeds, `MountReadOnly(path, LevelWriter)` refuses with `ReasonInsufficientLevel`).
