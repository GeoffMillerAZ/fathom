Claude Code tokenomics — and how Fathom bends the curve

For people who use Claude Code but have never thought about where the tokens go. New here? Read What is Fathom? first. Every claim is tagged OBSERVED or SPECULATIVE.

1 · What tokens actually buy in Claude Code

A token is ~¾ of a word. Every turn, the model re-reads its entire context: the system prompt, the whole conversation, and every file and tool result loaded so far — then produces a little new output. Two consequences follow:

① Whatever enters context stays expensive forever — a 5,000-token file read is re-paid on every subsequent turn of that session.
② When context fills up, Claude Code compacts (summarizes) the session — and details lost to compaction often get re-read, paying the cost again.

2 · Why this matters on the $200/mo Max 20× plan

Subscribers don't pay per token — you get capacity windows (a 5-hour rolling allowance plus a weekly ceiling). When the window is spent, you wait. So for a Max 20× user, tokenomics isn't a bill — it's a throughput limit:

shipped work per window = window capacity ÷ tokens per unit of work

Halve the tokens a feature costs and you ship twice as many features before hitting the limit — or stop hitting the limit at all. Heavy multi-agent users (the people who bought 20×) feel this hardest, because every subagent carries its own context and burns from the same allowance.

5 · Effectiveness & correctness — the part tokenomics charts miss

Designs grounded in the spec, automatically. OBSERVED Querying a concern returns the design-doc section ranked alongside the code it governs — both recent milestones were architected directly from that fused view, which is structural protection against spec drift.

Correct who-calls answers when the language server lies. OBSERVED gopls is chronically stale in our multi-module workspace; the index answered every caller query correctly, including across the Go→HTML-template boundary — a relationship LSPs don't even model.

Honesty semantics. OBSERVED Empty means empty (no fabricated relevance), staleness is reported, results carry evidence tiers. An agent that trusts its tools less wastes turns double-checking; an agent whose tools refuse to bluff doesn't have to.

What it doesn't fix. OBSERVED Inter-agent contract drift (a worker quietly deviating from a pinned interface) is a coordination failure — we caught one both before and after. The cure was procedural (a stop-and-report rule), not the index.

6 · Does it make work faster?

OBSERVED Wave wall-clock roughly halved (~105 → ~46 min). Three mechanisms: agents stop wandering (⅓ the tool calls), the discovery tier disappears entirely (no waiting on Explore agents before planning), and smaller contexts mean faster turns.

SPECULATIVE Expect a second-order speedup over long sessions: less context bloat → later/fewer compactions → fewer “re-read what the summary dropped” detours. We haven't instrumented compaction frequency yet; it's on the benchmark list.

8 · The bottom line for a $200/mo Max 20× user

Blended across a realistic month of multi-agent development, our best guess is ~1.5–2× more shipped work per capacity window SPECULATIVE, with the high end on days dominated by understanding code rather than typing it — plus the measured 2× wall-clock improvement on orchestrated waves, which compounds with the window math (you finish before the window does).

Where it can still go

① Line numbers in every result — just shipped. ② Spec-drift queries: “which files implement M18.2” as a tool call, drift as a report. ③ Brief generator: one call that assembles the architect's pre-packed worker context. ④ Hybrid embeddings for fuzzy recall on top of exact structure. ⑤ Watch mode for mid-session freshness without discipline. ⑥ Compaction instrumentation to turn the speculative second-order win into a measured one.

The honest excitement: nothing here is magic — it's the boring, compounding move of never paying for the same discovery twice, applied to every agent in every session, with measurement built into the culture.

9 · Putting it all together: a heavy Max 20× month SPECULATIVE

The persona (modeled on our own usage): ~20 orchestrated feature waves a month (multi-agent: architect + 2–3 workers + verification), ~8 exploration-heavy days (audits, onboarding new areas, “where does X live” work), daily Q&A and small edits. This is exactly who buys the $200/mo tier — and who collides with the 5-hour and weekly capacity windows.
