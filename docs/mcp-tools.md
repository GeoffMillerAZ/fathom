# MCP Tools Reference

Fathom exposes a JSON-RPC 2.0 MCP server (stdio or HTTP). This page documents every
registered tool, prompt, and resource.

See [usage.md](usage.md) for how to connect a client and select a surface.
See [architecture.md](architecture.md) for how the tool groups map to the three-layer design.
Registry size: 54 tools after the 2026-08-23 surface prune plus `memory_search` (55),
plus `localize` (56, wave G, plan VB-26);
`TestMcpToolsDocMatchesRegistry` keeps the tables below in step with the registry.

---

## Tool groups, profiles, and surfaces

Tools are divided into five groups (`GroupShared`, `GroupCoding`, `GroupInvestigation`,
`GroupPlatform`, `GroupModules`) that describe fathom's internal taxonomy. `set_profile` — the old,
process-global way to filter `tools/list` on stdio — was **removed entirely**
(docs/plans/surfaces-week1.md SW-2; amends ADR-014's stdio clause): no production caller
reaches it any more, so a **stdio** session always sees the full registry. Scoping now
lives entirely over HTTP.

**Which harness reaches these tools, and how, is registry data** (ADR-029): every
harness descriptor carries its MCP config path, HTTP key name, `mcp add` command and
tool-name pattern. `fathom harness list` names the registered harnesses and
`fathom harness capabilities [--harness ID]` prints the per-capability vehicle table
(the `ladder` subcommand, `fathom harness ladder`, prints the tier B/C/D rows — stanza +
MCP + skills, no injection) —
including the `mcp-tools` row, which is the only channel by which a tier-C/D harness
(no hooks, no injection) reaches anything on this page. An unverified descriptor
renders every row as `unverified on this machine` — Claude Code and Codex are verified
against real sessions on this machine, the rest are not; the catalog below is
unaffected by the harness in use. Each descriptor also carries the harness's full
EVENT catalogue with a reason per unwired event, which `fathom doctor`'s advisory
`hooks_coverage` row prints. `fathom intent render --playbook` is the one verb that
writes outside `.fathom/` and the instruction files: a root `INTENT.md` inside fathom
markers, rendered as pointers into `docs/intent/`. `fathom harness matrix` renders the per-harness adoption matrix
(tier, instruction file, skills path, MCP config + `mcp add` line, verified-against)
that `docs/adoption/other-harnesses.md` pins, `fathom harness hooks --harness ID`
prints that harness's hook entries as paste-ready JSON for the cases where fathom
refuses to write the file itself (Codex loads hooks only from its user-global
`$CODEX_HOME/hooks.json`, and user-global configuration is ask-first), and
`fathom plugin render` packages
the registration for two plugin loaders at once — Claude Code's `.mcp.json`
(`type: http`) and the Agent Plugins 1.0 `mcp.json` (`streamable-http`, loopback) —
over one `skills/` tree.

### Path-scoped surfaces (HTTP)

Over **HTTP** (`serve-http`, the shared daemon — default `127.0.0.1:7575`, loopback
only) each request selects an immutable **surface** via the path:

| Surface | Endpoint | Contents |
|---|---|---|
| *(full)* | `POST /rpc` | Every registered tool, unauthenticated — the default for schema-deferring clients such as Claude Code; includes `ingest` (writes) and `compile_layer` (LLM spend). Hides the four module tools instead when the daemon is in hosted-modules mode (see below) |
| `agent` | `POST /rpc/agent` | The primary agent surface (see below) — the user-scope MCP registration points here |
| `companion` | `POST /rpc/companion` | Compatible alias for `agent`: identical allowlist |
| ~~`coding` / `investigation` / `shared` / `platform`~~ | *(deleted)* | The four group surfaces were removed 2026-08-26 (ADR-014 amendment 2, `docs/plans/honesty-fixes.md` HF-5): no client registration, stanza, skill, or doc ever pointed at one, so their zero traffic proved exposure-zero, not demand-zero (law 8) — they go on law 4's ground, a surface with no reachable consumer. The group **taxonomy** (`GroupCoding`, `GroupInvestigation`, …) still classifies every tool. Use `POST /rpc` for everything, `POST /rpc/agent` for the curated hot loop. |
| `modules` | `POST /rpc/modules` | The module host's floor tool set (docs/plans/gke-module-host.md) — see "Module host tools" below for the tool list and the hosted-mode restriction |

**Agent/companion allowlist (19 tools):** `capabilities`, `discoveries`, `entrypoints`,
`find_callers`, `find_symbol`, `ingest`, `list_services`, `memory_search`, `obligations`,
`outline`, `pack_context`, `query_symbols`, `read_source`, `references`, `repo_map`,
`search`, `staleness_report`, `symbol_context`, `verify_plan`. `search` (RC-24) and
`discoveries` (RC-27, docs/vision/28-receipts.md §4) are the two deliberate exceptions
to the 19-tool diet cap (`surface_diet_test.go`, TD-2) — each added with a
pre-registered kill criterion, not a hunch.
`memory_search` (AM-8,
docs/design/anchored-memory.md §4) is the third net-new tool on this allowlist — the
one direct query over anchored memories, every answer labeled with tier and state;
injection through the edit hook stays the primary path. `read_source` (T5-4, docs/plans/trust-and-tokenomics.md)
is the program's second net-new tool added to this allowlist since its founding 15
(surfaces-week1, ADR-014 amendment) — justified by measured evidence, not added
speculatively: the home-bench H3-1 row found the surface had no raw-text read, costing
16 turns / 601k tokens on a single task that a plain `sed -n` would have answered in one
(docs/plans/home-bench.md).

**Gate semantics: execute-and-flag, not hard-gate** (ADR-014 amendment, 2026-07-16,
surfaces week-1). An off-surface `tools/call` — or `batch` sub-call — still **executes**;
a rejection only teaches an agent to abandon the surface, which looks identical to
no-demand in the call log. The JSONL call log (`serve-http --call-log`, default
`logs/mcp-calls.jsonl` under the repo's state directory — outside the repo tree by
default, O63 item 5, `internal/statedir`) records the pass-through with `off_surface:true`
(`batch` sub-calls are logged individually with `via:"batch"`, each with its own
`off_surface` flag) so demand is measurable instead of argued. Surfaces are **ergonomics
and measurement, never a security boundary** — bare `/rpc` already serves the full,
unauthenticated registry. The pre-amendment hard gate (an off-surface call returns an
error naming the surface) stays available for any future multi-tenant shape, behind the
server's `strictSurfaces` option.

**Budgeted answers (BA-5/BA-9, `docs/design/budgeted-answers.md`; the project-settable
block is experimental).** Class-budgeted tools size their answer in tokens and disclose
elision and per-call response cost: `list` = `query_symbols`, `references`; `composite`
= `pack_context`; `map` = `repo_map` (`find_symbol`, `find_callers`, `symbol_context`,
`outline` are not class-budgeted). Defaults resolve project → user → built-in from the
`budgets: {list, composite, map}` block of `.fathom/capabilities.cue` /
`~/.fathom/capabilities.cue` (closed schema; an unknown key such as `lists` is refused
with a did-you-mean) — honoured by `serve-http`; stdio `serve-mcp` still uses the
built-ins (documented gap). The observatory's Cost panel renders the same figures.

Surface boundaries apply to tools and prompts, not resources: canned prompts are hidden
on surfaces that reference tools not on that surface (prompts are pre-declared
workflows, so they stay hidden rather than execute-and-flag), while `resources/read`
(manifest, per-service summaries) stays available everywhere — it is data, not
capability.

**Suppression disclosure (phase V, `fathom scope`).** When a service has
active scope suppressions, any tool response whose results were narrowed by
them carries a `suppressed` block in its envelope — count, reason, and the
`fathom scope` command to inspect or reverse. Hidden is disclosed, never
silent (law 3): a reader can always tell "no results" from "results
withheld by a suppression someone registered". `read_source` refuses
suppressed and service-ignored paths by name, with the unsuppress command
in the refusal.

### Plain HTTP endpoints (non-MCP)

The separate CLI command `fathom theme-guide` provides an opt-in synthetic
Observatory appearance review at loopback `/dev/theme`; it adds no MCP tool or
daemon route. [App-kit adoption](app-kit.md#local-theme-guide-integration-2026-09-22)
owns its selected kit identity and experimental preview/reset/export boundary.

`serve-http` also answers a handful of plain (non-JSON-RPC) POST/GET routes
outside the tool registry — hooks call these directly rather than through
`tools/call`:

- `POST /refresh-file` — `{service, file}` re-extracts one file's
  observations/syntax edges and fingerprint (SU-5/SU-6, ADR-041 decisions 3
  and 4); the pre-edit hook's per-file freshness check.
- `GET /findings/summary?service=NAME` — repo-wide open finding-kind claim
  count plus the oldest compiled-at (FL-21, `docs/vision/30-findings-loop.md`
  §3.4).
- `POST /route` — `{"prompt": "..."}` suggests which MCP tool's
  question-shape best fits a prompt (DP-9, ADR-042 decision 2,
  `docs/vision/32-decision-port.md` §2 item 3). One decision-port `choice`
  question over the fixed verb set (`localize`, `find_symbol`, `references`,
  `find_callers`, `obligations`, `staleness_report`, `search`, `none`)
  answers `{"shape", "verb", "confidence", "band", "provider"}` — `provider`
  names the configured `[decide]` provider that answered (`none` | `llm` |
  `typesafe`). Provider `none`, a decider error, or an invalid answer all degrade to
  `{"shape":"","verb":"","confidence":0,"band":"unsure","provider":"none"}`
  (plus an `"error"` field on a genuine failure) rather than a non-200
  status — **this route is a SUGGESTION about the prompt's shape, never a
  code fact**: it never asserts that a symbol exists, a caller calls, or a
  rule is binding, only which lookup verb a question shaped like this one
  usually wants. Every answered decision is appended to `decisions.jsonl`
  (`internal/decide.DefaultRecorderPath`, beside the configured call log)
  under site `"route"`. `fathom prompt-hook` is this route's only caller
  today (DP-10, amended 2026-09-24 — ADR-042 decision 8/CV-M11: route's own
  calibration reading found its `proceed`-band choice right only 45.7% of the
  time, well under the 0.9-right-nine-times-in-ten bar, with no confidence
  cutoff that fixes it): at or above the `proceed` band OR in the `confirm`
  band it injects the SAME hedged line — never a firm instruction, at any
  confidence — and nothing below the confirm floor (0.5) or on any
  failure. **A decision-port call that hard-fails (no answer at all —
  `/route`'s own decider error, a `compile_layer` pre-filter chunk, or an
  `obligations` re-rank chunk) is ALSO logged** (DP-22/DP-23, O109): a row
  naming `site`/`provider`/`questions`/`latency_ms`/`error`,
  `applied:false` — so silence in `decisions.jsonl` means "never asked",
  never "asked and failed".
- `GET /metrics` — text exposition (`fathom_uptime_seconds`,
  `fathom_requests_total`, plus O108's `go_memstats_heap_inuse_bytes`/
  `_heap_sys_bytes`/`_sys_bytes`, `go_goroutines`, `process_uptime_seconds`,
  `fathom_graph_memo_entries`/`_hits_total`/`_misses_total`,
  `fathom_open_stores`, `fathom_autorefresh_total`,
  `fathom_typed_pass_total`) — `fathom doctor`'s `daemon_footprint` row reads
  it.
- `GET /debug/pprof/*` (O108) — the stdlib `net/http/pprof` handlers
  (`heap`, `goroutine`, `allocs`, `profile`, `cmdline`, `symbol`, `trace`),
  mounted on the daemon's own mux. Loopback-only, same unauthenticated trust
  boundary as every other route (ADR-014 amendment: surfaces are not a
  security boundary) — never gated behind the `/rpc/modules` bearer token
  even in hosted-modules mode. `curl -s localhost:7575/debug/pprof/heap -o
  heap.pb.gz && go tool pprof -top heap.pb.gz` reads a live snapshot;
  `docs/guides/fleet-index.md`'s daemon-ops section has the operational
  playbook.

## Protocol contract

What a client that never reads `CLAUDE.md` can learn from the wire alone
(`docs/plans/reach-parity.md` RP-9..RP-13, `docs/vision/25-harness-port.md` §1).
Served by `serve-http` and `serve-mcp` alike; the contract lives in
`internal/mcp/protocol.go` and `outputschema.go`.

- **Protocol versions.** `initialize` echoes the client's `protocolVersion`
  when it is in the supported table — `2025-11-25`, `2025-06-18`, `2025-03-26`,
  `2024-11-05`, newest first — and otherwise answers with the newest supported
  (`negotiateProtocolVersion`; the 2025-11-25 lifecycle rule). All four are
  legacy-era revisions (the `initialize` handshake, one JSON response per
  POST): fathom does not claim `2026-07-28` (per-request `_meta`,
  `server/discover`, SSE streaming), so a modern-only client is told
  `2025-11-25` and decides for itself. Over HTTP the `MCP-Protocol-Version`
  request header is tolerated — never a 400 — and every response carries the
  revision the server negotiates for it. Proven end to end by
  `TestServeHTTPNegotiatesWithKitClient` (`cmd/fathom`), which drives
  `POST /rpc/agent` through agentic-kit's `mcp-client` Streamable-HTTP
  transport — a client fathom did not write — initialize → tools/list →
  tools/call.
- **Descriptions (RP-9, diet O101).** Every agent-surface description
  carries a "Reach for it when …" sentence and a `Required: a, b.` sentence
  naming exactly the arguments its own `inputSchema` marks required —
  per-tool truth, not a blanket rule (ADR-006 as amended: the concern is
  the engine's parameter, not every tool's).
  `TestAgentSurfaceDescriptionsNameRequiredArgs` iterates the agent-surface
  allowlist. O101 (the wave-diet brief) caps every description at 260
  bytes and every `inputSchema` property description at 120 bytes, flat —
  no per-tool exception (`surface_description_caps_test.go`); alias/history
  prose was dropped from argument descriptions (the aliases themselves are
  unchanged) and moved to this document where it was not already here.
- **Annotations (RP-10).** Every agent-surface tool serves MCP
  `ToolAnnotations`: `readOnlyHint`, `destructiveHint`, `idempotentHint`,
  `openWorldHint`. Sixteen are read-only; `ingest` (re-indexes: not read-only,
  idempotent, never destructive) and `obligations` (its `action:"refute"|
  "corroborate"` path writes a claim's status: not read-only, idempotent, not
  destructive) are the two writers. Nothing on the surface is open-world. The
  long tail on bare `/rpc` serves no annotations rather than guessed ones.
- **Output schemas (RP-11, off by default since O101).** Every
  agent-surface tool still HAS a generated `outputSchema` (`outputSchemaFor`,
  `internal/mcp/outputschema.go`'s `agentResultTypes` registry; root
  `type: object`, additional properties permitted because fields are
  additive by contract) and `tools/call` still returns the result as
  `structuredContent` beside the text block, unconditionally. What changed
  (O101, the wave-diet brief, bench evidence: the wired arm carried a
  median 15,219 cache-read tokens/turn vs 5,165 for grep, and `outputSchema`
  was 18,827 of the 48,341-byte `tools/list` payload — 39%) is whether
  `outputSchema` rides on `tools/list` itself: **off by default**, so the
  schema tax every connected session pays before its first call drops by
  that much. A client that validates `structuredContent` against the
  advertised schema asks for it back with `?contracts=true` on the HTTP
  surface (`POST /rpc/agent?contracts=true`, `POST /rpc?contracts=true`, …;
  `internal/mcp/surface.go`'s `WithContracts`, read from the query string in
  `cmd/fathom/servehttp.go`) — a stdio session gets the diet unconditionally
  (no query string to opt in from). `TestOutputSchemasMatchLiveResults`
  requests `WithContracts(ctx, true)` to get schemas back onto the wire, then
  validates every live result against the schema it advertised — the
  generated schemas themselves, and the fact that a request can still ask
  for them, are unchanged; only the served default moved.
- **Order and cost (RP-12).** `tools/list` is sorted by name, byte-stable
  across calls, so a client that pins per-tool hashes (the kit client does)
  or diffs the list sees no spurious change. `capabilities` reports
  `schema_bytes` — the serialised size of the request surface's `tools/list`,
  the context every session pays before its first call (TD-2's diet is a
  measured number, not a hunch).
- **Answer-first `summary` (wave L1).** Two home-bench readings
  (`docs/bench/readings/vs-pilot-6-second-reading.md`, `vs-pilot-5`) found the
  tools handing the agent the right evidence and the model reasoning past
  it: `find_callers(RenderMarkdown, depth=2)` listed the direct caller
  first, and the final answer named a depth-2 caller three hops out; a
  `search` hit landed on the right line, and the answer cited a different
  document. The fix is presentation, not more data. `find_callers`,
  `references`, `blast_radius`, `rename_impact`, `safe_delete_check`,
  `test_impact`, `localize`, `search`, and `obligations` each lead their
  JSON with a `summary` string (`internal/mcp/summary.go`'s
  `summaryEnvelope` splices it in ahead of every other key — plain
  `encoding/json` on a `map[string]any` would otherwise sort it
  alphabetically wherever `"s"` falls) — one sentence, ≤ 200 chars, naming
  the direct answer in the question's own terms (e.g. `find_callers`: "3
  direct callers of X: a (file:12), b (file:9), c (file:3); 5 more at
  depth 2"). `summary` is built from the SAME sorted, post-budget data the
  rest of the body carries — never from a wider pre-elision set — so it can
  never claim a row the body does not actually return, and it rides outside
  every truncating tool's item-slicing entirely (it is never itself cut).
  For the callers/references family specifically: `depth` on each row and
  the `by_depth` summary mean a direct (depth-1) result and a transitive
  (depth 2+) one are never conflated — `summary` only ever names depth-1
  rows as "direct".

## Shared tools (GroupShared)

These tools are visible on the full registry and under every group surface. One
exception: the `agent`/`companion` surface shows only its explicit allowlist (see above)
— other shared tools are still callable there, execute-and-flagged rather than hidden.

| Tool | Arguments | Returns | Purpose |
|---|---|---|---|

the byte-length "keyword score" this replaced now only breaks a tie INSIDE one proximity tier — with one narrow exception, wave O3's `crossTierCloser`, ADR-037 addendum: a farther-tier rule that STRONGLY names the file — a hit on its own package path, stem, or a resolved symbol/behaviour token — leapfrogs a nearer-tier rule that is a total lexical blank about the file; any hit on the nearer rule, however weak, keeps proximity's own order) — then, inside that same tier (wave O2, `.fathom/observations.md` O73/O75, ADR-037 addendum), a deterministic lexical **relevance score** (path-derived tokens plus optional resolved symbol/import names — and, wave O3, a small fixed table of behaviour signals scanned from the file's own source: writing output (`os.WriteFile`, `os.MkdirAll`, …) adds `"workspace"`, running the test/build gate or a shell command adds `"gate"`/`"validate"` — weighted stem > package > ancestor > extension, heading hits doubled, no length normalisation) so a nested guide's several same-tier sections are no longer served in mere document order — then rule text (D5 — both payloads in the stopped replicated run led with a stale rule, and a stale rule is demoted below the budget line by this same fresh-first ordering, never served first); the cap is filled by `role:"governs"` layers (`obligations`, `adr-rules`) FIRST and `role:"claims"` layers (`spec-bindings`, `findings`) take only the slots left (D1), with `displaced` still counting both; and a claims-layer rule citing a gated plan row is scoped at serve time by that row's own `{package, symbol}` contract — a row naming no contract binds to nothing (D2, O23: six plan rows about C++, CUE and tree-sitter bound to one Go file by the word "extractor" in their prose and displaced 65 more). ## Module host tools (GroupModules)

The GKE **module host** (docs/plans/gke-module-host.md; docs/spec/store-format-v0.md;
docs/spec/expert-module-v0.md) mounts N conforming expert-module stores **READ-ONLY**
beside the main fleet store, via `serve-http --module <path>` (repeatable). Every
result carries per-module provenance — never merged into an ambiguous unattributed
set — and every claim keeps its citation, evidence tier, and non-fresh status
(store-format-v0.md §3 Server conformance, generalized to N stores).

| Tool | Arguments | Returns | Purpose |
|---|---|---|---|
| `list_modules` | — | `{modules: [{module, path, service?, indexed_commit?, indexed_at?, error?}]}` | Enumerate every mounted module's (module, corpus/service) pairs and the ingest-time watermark each was compiled at (expert-module-v0.md §4.1). A module whose own discovery failed contributes one `error`-carrying row rather than aborting the whole call. |
| `module_obligations` | `module` (opt — omit to fan out across every mounted module), `file` (req), `max` (opt) | `{results: [{module, service, obligations, error?}]}` | Scope-lookup query (expert-module-v0.md §4.2, the `obligations`-shaped pattern): claims governing `file`, each still carrying citation/tier/status, tagged with the module and service that served it. |
| `module_query` | `module` (opt), `text` (req; alias `concern`), `max` (opt) | `{results: [{module, service, watermark, nodes?, staleness, claims?, error?}]}` | Free-text query — `module_obligations` alone requires a scope-glob `file` and cannot answer a free-text question. Fans out the concern-scoped symbol engine (`query_symbols`' own engine) AND a claim-text substring match per (module, service) pair; a pair answers via ranked symbols, matched claims, both, or neither (omitted when neither). `watermark` (that pair's `service_meta.indexed_commit`) rides on every entry regardless of whether it answered. Each `claims[]` entry is `{claim_id, text, src, anchor, tier, status?, kind?}` — a **wire shape distinct from `module_obligations`'** (`{rule, src, tier, status?, kind?}`, unchanged): `claim_id` is the durable `core.SemanticClaim.ClaimID` (the same identity `fathom claim refute`/`claim_events` key on — a consumer's cite tokens and feedback path need this, not just the rule text), and `anchor` is the literal cited text from `claim_links.anchor_text` (`""` for a legacy hash-only citation that predates it, never a guess). |
| `module_staleness` | `module` (req) | `{module, corpora: [{module, service, indexed_commit?, current_commit?, status}]}` | Per-(module, service) staleness (expert-module-v0.md §4.3). A mounted module is a **detached corpus** by default: `status` reads `"unknown-detached"` unless the module's `service_meta.path` is present and re-checkable on THIS machine — `"fresh"`/`"drifted"` only then. A `manifest:`-watermarked module is re-checked via the same content-addressed algorithm it was compiled under, **never** a live git HEAD (a corpus nested inside some unrelated enclosing git checkout would otherwise false-drift permanently). |

**Mount conformance (`--module <path>`, repeatable):** checked at mount time against
store-format-v0.md §2's markers (`application_id == 0x46415448` AND `user_version >= 1`)
and the required-schema tables for the level the host requires (`L0` by default). A
non-conforming or unreadable store **aborts serve-http startup loudly** — never a
partial mount. Every mount opens the store file genuinely read-only at the SQLite/VFS
layer (`file:<path>?mode=ro`) — there is no write path to a mounted module, structurally
(docs/vision/12-governed-knowledge-engine.md law 9).

**Hosted mode (`--modules-token-env <NAME>`):** names an environment variable holding a
bearer token required on `POST /rpc/modules` (constant-time compare; the token itself is
never a flag/config value, never logged). **Default off** — the local, loopback-only,
unauthenticated daemon is unaffected. When a token IS configured, hosted mode is a
strictly narrower surface, not merely an auth check bolted onto the existing one:

- `/rpc/modules` serves **only** `list_modules`, `module_obligations`, `module_query`,
  `module_staleness`, `capabilities`, `server_stats` — never the rest of `GroupShared`
  (no `ingest`, no `compile_layer`, no `batch`, no fleet-backed reads like `repo_map` /
  `find_symbol` / `staleness_report` that a modules-token holder could otherwise pivot
  through to read the fleet's own indexed services).
- Off-allowlist calls on `/rpc/modules` are **hard-gated** (a named error), never
  execute-and-flag — the one surface in this server where that ADR-014 ergonomics
  choice is deliberately overridden.
- The four module tools become unreachable from **every other path** — bare `/rpc`,
  any other named surface, or a `batch` sub-call — so there is never an unauthenticated
  route to module data once a token is configured.

## SymbolNode shape

Queries and navigation tools return `SymbolNode` objects:

```json
{
  "service":   "payment-service",
  "name":      "ValidateToken",
  "kind":      "GoFunc",
  "file_path": "internal/auth/token.go",
  "line":      42,
  "end_line":  46,
  "signature": "func ValidateToken(ctx context.Context, tok string) error",
  "tier":      "verified"
}
```

`tier` is the evidence tier: `verified`, `pre-scan`, `doc-claimed`, `sme-stated`, or
`assumed`. See [architecture.md](architecture.md#evidence-tiers-adr-007-adr-009).

`end_line` (T5-5, docs/plans/trust-and-tokenomics.md) is the last line covered by this
symbol, when its extractor computed a real extent — `DocChunk` headings (line before the
next heading, or EOF for the last one); the Go extractor, for every func/method/type/
const/var (the declaration's own end position); most tree-sitter/AST-backed extractors
(C, C++, C#, Java, Lua, PHP, Rust, Scala, CUE, HCL/Terraform, CMake, Templ). Omitted
(zero) for a symbol from an extractor that doesn't compute it yet — see
`core.SymbolNode.EndLine`'s doc comment for the current list. Pair it with `read_source`
(`start_line: line, end_line: end_line`) to pull a symbol's or doc section's real,
line-numbered text instead of guessing its extent by arithmetic off the start line — the
fix for the T08 class in `docs/plans/home-bench.md`'s H3-1 row.

## Prompts

Fathom registers four canned prompts (via `prompts/list` and `prompts/get`). Each prompt
returns a structured sequence of instructions that guides an AI agent to use the
appropriate fathom tools for the task.

| Prompt | Arguments | Purpose |
|---|---|---|
| `investigate_incident` | `service` (req), `symptom` (req) | Guide an investigation into a production incident: entrypoints → complexity hotspots → find callers → community → staleness check |
| `review_change` | `service` (req), `changed_files` (req), `change` (opt), `concern` (opt) | Review a code change for safety by calling the composed `review_diff` verb (C3-1, `docs/plans/review-verb.md`) — one cited verdict instead of a manual tool sequence |
| `onboard_service` | `service` (req) | Generate an onboarding tour for a new engineer: entrypoints → sources → god objects |
| `plan_requirement` | `service` (req), `requirement` (req) | Plan implementation of a new requirement: entrypoints → complexity → dead code |

### Using a prompt

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "prompts/get",
  "params": {
    "name": "investigate_incident",
    "arguments": {
      "service": "payment-service",
      "symptom": "POST /checkout returning 500 after deploy"
    }
  }
}
```

## Resources

Fathom registers two MCP resource types (via `resources/list` and `resources/read`).

| URI | MIME type | Contents |
|---|---|---|
| `fathom:///manifest` | `application/json` | Server manifest: registered tools, active profile, known service IDs, server version |
| `fathom:///service/<id>` | `application/json` | Per-service symbol summary: symbol count, file count, file list, kind breakdown |

### Reading the manifest

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "resources/read",
  "params": { "uri": "fathom:///manifest" }
}
```

Response `contents[0].text` is a JSON object:
```json
{
  "server": "fathom",
  "version": "1.0.0",
  "tools": ["query_symbols", "find_callers", ...],
  "active_profile": "coding",
  "services": ["auth-service", "payment-service"]
}
```

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "resources/read",
  "params": { "uri": "fathom:///service/payment-service" }
}
```

Response `contents[0].text` is a JSON object:
```json
{
  "service": "payment-service",
  "symbol_count": 891,

  "files": ["internal/auth/token.go", ...],
```
