# RT-M14: the hook path on the managed daemon, 2026-10-19

**Verdict, in plain words.** The hooks no longer lose work on the managed daemon. None of the 451 measured hook
calls was abandoned, and the daemon's call-graph cache abandoned no build during the run. EW-76's loaded re-reading
had 72% of pre-edit blast-radius calls and every stop-hook plan verification abandoned. Here both are at 0%, and the
stop hook's wall time fell from p50 5.5 s to 1.4 to 1.7 s. The bar the run misses is answers. The pre-edit blast
radius was declined on all 50 calls: the service's call graph was not resident, and a 500 ms hook can never start
that build. So the only graph-backed call that answered on the hook path was the stop hook's `verify_plan`. Its first
measured invocation got two "still building" partials, which puts the answered share at 48.5% (49 of 101), under the
50% bar. The harness half fails on that share alone. The call-log half needs seven complete UTC days and cannot be
read before 2026-10-27.

## Method

- **Daemon.** The managed `serve-http` on 127.0.0.1:7575, fathom v0.15.6 @ 4823561d, which carries RT-188, RT-190,
  RT-191 and RT-192. It was up since 15:23Z, serving the fleet store with `FATHOM_CACHE_MAX_MIB=8192`. Every row of
  this run carries `fathom_version` 4823561d4993. Its tenancy level read 0 at every snapshot.
- **Harness.** `docs/bench/readings/efficiency-wave/hook-path-harness.py --url` drives the running daemon read only.
  No daemon is started, stopped or restarted, so EW-76's cold half (8 restarts) is not run. Every hook gets `--url`
  and `FATHOM_HTTP`, and a private `FATHOM_HOME` and `TMPDIR`, so the hooks' breaker starts closed and their ledgers
  stay in scratch. The run's rows are read from the daemon's own call log (read only, from its size at the start) by
  `X-Fathom-Caller`: session `hook-path-harness-rtm14-1792424612`, or the harness as the parent process. Each row is
  attributed to its hook invocation by the hook's pid. Before the run, and before each pre-edit invocation, the
  harness reads `obligations` on the guarded file and stops if it reads `index_stale`, because the pre-edit hook would
  ask the daemon to refresh that file (a store write). The guard never fired. graphstore counters
  (`fathom_cache_events_total`, RT-188) are read from `/metrics` at the start and after each condition.
- **Hooks.** The deployed binary (4823561d), with EW-76's six hooks and payloads, 25 invocations each per condition,
  after one uncounted warm-up of each. The stop hook's claim is EW-76's open row, flipped in the subject's working
  tree for the run and restored after it.
- **Subject.** A detached worktree of e98ce79e, the commit of the checkout the daemon serves, under the run's scratch
  directory.
- **Conditions.** Unloaded is the machine as it was. Loaded runs the same loop beside a scratch ingest of the subject
  into a scratch store inside the run's `--home`, with `FATHOM_HTTP` unset. One ingest ran
  through the whole loaded loop and was stopped unfinished at its end. The harness's "ingest runs started" line counts
  finished runs, so it reads 0.
- **No direct probes** (`--probes 0`). A direct probe carries no deadline, so on the managed daemon it would start a
  full call-graph build of the service, and the unloaded probes would leave that graph resident for the loaded hooks.
  The row reads the hooks.
- **Run and host.** 2026-10-19T15:43:32Z to 15:47:20Z. The load average was 16.3 / 33.8 / 37.8 at the start and
  8.7 / 21.2 / 31.4 at the end. Other wave work shared the host: 1 to 2 test binaries and 2 to 4 ingest, gate or
  `go test` processes at the two snapshots. Swap was 25.1 of 26.6 GB used. The internal disk (the swap volume) had 5.4
  to 5.5 GiB free, above RT-M1's 5 GiB floor. It read 4.7 GiB at 15:36Z and 4.6 GiB at 15:51Z, when the daemon was at
  tenancy level 2.
- **Not counted.** An earlier start at 11:08Z drove the daemon then serving e98ce79e. The daemon was down from about
  11:13Z to 15:23Z, so that run is not this reading.
- **Reproduce:** `python3 -I docs/bench/readings/efficiency-wave/hook-path-harness.py --bin <fathom> --load-bin
  <fathom> --subject <checkout> --home <scratch> --url http://127.0.0.1:7575 --call-log <daemon call log> --ingest-store
  <scratch>/load.sqlite --n 25 --probes 0 --label rtm14`.

## What it means

K1 and K3 do not trip: no build was abandoned, and every abandonment rate is 0%. K2 trips on the answered share, and
its reading of `evictions{reason}` finds a case the clause does not name. The only graphstore eviction since the
daemon started was a refuse drop (`evicted_refuse` 1 before the run, a second by 15:51Z). Budget, shed, idle and
watermark evictions were 0. The internal disk read under the 5 GiB floor at 15:36Z, so the swap-volume floor is the
likely source of that refuse. The run itself saw level 0 throughout.

The decline itself is RT-191 working as written. The pre-edit cap is 500 ms. That is under half of graphstore's 2 s
expected cost and under any build of this graph measured so far (7 to 20 s in EW-75), so the hook can never start the
build. On the hook path, `blast_radius` answers only when another caller has
built the graph at the current watermark and it is still resident. Under the current shape, the answered share is
`verify_plan`'s share of the calls, about 50%, and one partial puts it under the bar (O1303).

**What a PASS needs.** Some pre-edit `blast_radius` calls must find the graph resident, or the pre-edit trailer must
leave the hook path, so that the share is `verify_plan`'s alone. A rerun until one run lands at exactly 50.0% is not a
reading.
