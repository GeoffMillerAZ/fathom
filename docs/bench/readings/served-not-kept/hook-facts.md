# PR-V1: what PostToolUse carries for a shell command, and whether hook-added context reaches the model

PR-V1 reading: Claude Code 2.1.284 PostToolUse(Bash) carries the command's stdout (`tool_response.stdout`) and, for a foreground commit, a structured `tool_response.gitOperation.commit.sha` that Claude Code itself parses out of git's `[branch sha]` summary line, so the summary line is on the hook input whenever git prints it, which `git commit -q` does not (1,744 of 2,446 successful commit results scanned, 71 percent, were `-q`; 537 of the 546 that were plain carried it). Context a PostToolUse hook adds (`hookSpecificOutput.additionalContext`) reaches the model in Claude Code as a `PostToolUse:<tool> hook additional context:` message (bundle conversion; 9,347 recorded in transcripts) and in Codex 0.158.0 as a developer-role message (2,530 observed for `apply_patch` in 7 sessions, 0.154.0 to 0.158.0). Codex's PostToolUse `tool_response` for a shell command is undetermined at $0: no captured input exists for it and the documentation does not say.

Plain summary: three of the four facts settle, and the one that does not is the Codex shell input. On Claude Code the commit pin line's premise holds (the hook input carries stdout and the summary line), but its coverage does not: agents here write `git commit -q`, which prints no summary line, so ADR-057 decision 4 ("no summary line, no check") leaves most commit results unchecked. That is a fired revisit trigger on ADR-057 (a PR-V1 read), recorded below. Context added by a PostToolUse hook is delivered on both harnesses, so a feedback line is not lost in transit; the open question there is only whether the model acts on it, which is PR-M2's, not this reading's.

Date: 2026-09-29. Versions read: Claude Code 2.1.284 (the installed `@anthropic-ai/claude-code` package, `bin/claude.exe`); codex-cli 0.158.0 (the installed Homebrew `codex` binary); Codex hooks documentation fetched 2026-09-29 (`developers.openai.com/codex/hooks.md`, no version stamp on the page). $0: no Claude Code or Codex session was started and no model was called; every source is a shipped binary, a stored transcript or rollout, a checked-in fixture, or the documentation page. Statistics only; no command text, output or hook context is stored here.

## Fact 1 (a): Claude Code's PostToolUse(Bash) input carries stdout, and the commit summary when git prints it

The bundle builds the PostToolUse input as `{...common, hook_event_name: "PostToolUse", tool_name, tool_input, tool_response, tool_use_id, duration_ms}` (the same construction TR-V1 read; `docs/bench/readings/test-run-hook/hook-facts.md`), and `tool_response` is the Bash tool's own result object: `stdout`, `stderr`, `interrupted`, `isImage`, `returnCodeInterpretation`, `noOutputExpected`, the background-task fields, `persistedOutputPath`, `persistedOutputSize`, `staleReadFileStateHint`, `ghRateLimitHint`, `gitOperation` and `bashEditDiff`. TR-V1's list did not name the last four. `gitOperation` matters here: for a foreground command the tool classifies git activity from the command text and the combined stdout and stderr, and for `git commit` (and `cherry-pick`) it sets `commit: {sha, kind: committed | amended | cherry-picked, branch?}`, with the sha and branch taken from the first line matching `^\[(<branch>|detached HEAD)( \(root-commit\))? <hex, 4 or more>\]` (multi-line). That is git's summary line. A Claude Code built-in PostToolUse callback reads `tool_response.gitOperation` from the same hook input, which is what puts the field on the input a hook receives.

Transcript cross-check (6,454 session and subagent files under `~/.claude/projects`; 2,504 Bash calls whose command holds a `git commit` invocation, 2,501 paired with their result):

| Population | Count |
|---|---|
| Tool errors (a failed commit; none held the summary line) | 55 |
| Successful results | 2,446 |
| ... with the summary line in the result text | 668 (27 percent) |
| ... from a commit invoked with `-q` or `--quiet`, no summary line | 1,744 (71 percent) |
| ... piped through `tail`, `head`, `grep` or similar, no summary line | 22 |
| ... `--dry-run` | 3 |
| ... plain commits (none of the above) | 546, of which 537 carry the summary line (98.4 percent) and 9 do not |

Of the 668 with the summary line, 418 also carry the stored result object (`toolUseResult`), with `stdout` a string holding the line and `gitOperation.commit.sha` equal to the summary line's sha in all 418; the other 250 are read from the model-facing result text, because transcripts of the newest versions mostly no longer store the result object (2.1.284: 6 of 397 commit results). The stored objects come from versions 2.1.225 to 2.1.284. So on the hook input stdout is present, git prints the summary line after any pre-commit hook output, and the same sha is offered pre-parsed; a `-q` commit prints neither, and the `-q` share is a property of how agents on this machine write the command, not of Claude Code.

Not measured: a plain commit whose pre-commit hook output is large enough for `persistedOutputPath` to replace the inline stdout (TR-V1: 30,000 characters by default). The summary line comes after the hook output, so that is the case where a plain commit would lose it.

## Fact 2 (b): context a PostToolUse hook adds reaches the model in Claude Code

The bundle's PostToolUse pipeline collects each hook's `additionalContext` (a JSON hook's `hookSpecificOutput.additionalContext`), passes it through the hook-output limiter (over 10,000 characters it is persisted to disk and replaced by a preview and a path), and yields an attachment `{type: "hook_additional_context", content: [...], hookName: "PostToolUse:<tool>", toolUseID, hookEvent: "PostToolUse"}`. The message builder turns that attachment into a meta user message whose text is `PostToolUse:<tool> hook additional context: <content joined by newlines>`. The same path serves PostToolUseFailure, PreToolUse, SessionStart and the rest. A hook that stops continuation gets a separate `hook_stopped_continuation` message instead.

Transcript cross-check: 9,347 `hook_additional_context` attachments with `hookEvent` PostToolUse (Bash 6,754, Edit 1,996, Write 597), from versions 2.1.245 to 2.1.284 (1,739 at 2.1.284); every one has a string payload and appears after the `tool_result` of its own `toolUseID` in the same file (9,347 of 9,347). The attachments are recorded and the bundle converts them to model-visible messages; the API request body itself is not observable at $0, so "reaches the model" rests on the bundle's conversion, not on a wire capture.

## Fact 3 (c): Codex's PostToolUse input for a shell command: undetermined at $0

- Documentation (fetched today): PostToolUse runs for shell commands and unified exec (`exec_command`), both matched as `Bash`, including after a non-zero exit. The `tool_response` row reads "Tool-specific output. MCP tools send the MCP call result. Other local function tools normally send their model-facing output." It names no shape for Bash.
- The 0.158.0 binary embeds the hook schemas: `post-tool-use.command.input` requires `tool_response` and types it as any JSON value (`true`). It does not say what a shell command puts there.
- The only live capture is `internal/harness/testdata/codecs/codex/post-tool.live.in.json` (codex-cli 0.153.1, 2026-09-12): an `apply_patch` call whose `tool_response` is one string, `Exit code: N`, `Wall time: N seconds`, `Output:` and then the tool's text. A shell command may use the same wrapper with its output after `Output:`, but that is another tool and is not a fact about it. `post-tool.in.json` is constructed from the field list and proves nothing.
- The 345 rollouts under `~/.codex/sessions` do not store hook inputs. The direct `shell` and `exec_command` calls in them are from versions 0.45.0 to 0.130.0; sessions from 0.154 on reach the shell through the code-mode `exec` tool, and no Codex PostToolUse(Bash) hook is wired on this machine (`~/.codex/hooks.json` matches `apply_patch` only), so fathom has no beat of one either.

What would settle it: capture the stdin of a wired PostToolUse(Bash) hook once, as HP-33 did for `apply_patch` (a tee wrapper on the hook command), for a shell call and for a `git commit`. That needs a Codex session; a local stub model endpoint would avoid model spend if Codex accepts one through its provider configuration (not tried), but it is still a live session, which this reading excluded, so it needs the owner's leave.

## Fact 4 (d): Codex delivers PostToolUse context to the model

- Documentation: PostToolUse `hookSpecificOutput.additionalContext` "is added as extra developer context"; output over about 2,500 tokens per handler spills to a file with a head-and-tail preview (`additionalContextLimit` sets the threshold).
- Binary strings (0.158.0): the `PostToolUseHookSpecificOutputWire` shape with `additionalContext`, the per-handler `additionalContextLimit`, and a `HookPrompt` thread item. Names only; they show the mechanism exists, not which event feeds it.
- Rollouts, the observation: fathom's Codex PostToolUse(`apply_patch`) hook logged 3,422 beats with `emitted: true` in 7 sessions, and each of the 7 rollouts holds developer-role `response_item` messages headed `fathom obligations - <path>:`, a header only the post-edit hook writes (the pre-edit guard's header differs). There are 2,530 such messages: 2,022 at 0.154.0, 115 at 0.155.1, 333 at 0.157.0 and 60 at 0.158.0. All 2,530 sit between a code-mode `exec` call and that same call's output (the patch was made inside `exec`), so the model receives the context before it sees the result.
- Scope: observed for `apply_patch` made through code-mode `exec`. Delivery for Bash is documented, not observed, because no Bash PostToolUse hook is wired here. The 2,530 messages against 3,422 beats (74 percent) is a gap this reading cannot explain at $0.

## What the build does with these facts

- The commit pin line (PR-3) on Claude Code may rely on `tool_response.stdout` and on `gitOperation.commit.sha`; both come from the summary line, so a `git commit -q` gives the hook neither, and ADR-057 decision 4 ("no summary line, no check") then skips it. On this machine that is 71 percent of successful commit results. This fires ADR-057's `Revisit when` (a PR-V1 read). The decision to take is the owner's: also check a `-q` commit by reading `HEAD` in the hook's cwd after a `git commit` (one more git call in a hook that already forks `git cat-file`), or accept the coverage and let the beat say how many commits were skipped for lack of a summary. This reading does not choose.
- Other harnesses stay record-only: Codex's shell input is undetermined (Fact 3), so the pin line for Codex needs the capture named there and a wired Bash PostToolUse entry (`CapObligationsPostShell` is absent for Codex).
- Feedback delivery is not the risk on either harness (Facts 2 and 4). The hook still has to fit each harness's cap: 10,000 characters on Claude Code, about 2,500 tokens on Codex.
- No harness descriptor fact is contradicted by these readings, so no observation is filed against `internal/harness`.

## Reproduce

- Claude Code bundle: `bin/claude.exe` of the installed package; search for `hook_event_name:"PostToolUse"`, `gitOperation`, `hook_additional_context:(e)=>`, `function rle(` and the regex beginning `^\[(?:([\w./-]+)|detached HEAD)` (the minified names are those of 2.1.284 and change between releases). A memory-mapped byte search prints the context around a needle; the plain `grep -a -o` with a long prefix is too slow on a 227 MB binary.
- Transcript statistics: a standard-library Python scan over `~/.claude/projects/**/*.jsonl`, pairing each Bash `tool_use` whose command matches `git ... commit` with its `tool_result` and counting `is_error`, the summary-line regex over `toolUseResult.stdout` (or the result text when the object is absent), whether the commit invocation's own flags hold `-q` or `--quiet`, and `gitOperation.commit.sha` against the summary sha. A second scan counts `attachment.type == "hook_additional_context"` by `hookEvent` and `hookName` and checks each follows a `tool_result` with its `toolUseID`. Scripts kept outside the tree (`<scratch>/wf-ledger-scan.py`, `<scratch>/wf-ledger-scan2.py`); they print counts only. The numbers move by a handful as live sessions write more lines.
- Codex: `strings -a -n 8` over `/opt/homebrew/Caskroom/codex/0.158.0/bin/codex` and search for `post-tool-use.command.input`, `additionalContextLimit` and `HookPrompt`; the documentation is `curl -sL https://developers.openai.com/codex/hooks.md`; rollouts are `~/.codex/sessions/**/rollout-*.jsonl`. The Codex sessions in Fact 4 come from `~/.fathom/hooks.jsonl*` (`channel: edit-hook`, `kind: answered`, `phase: post`, `emitted: true`, `harness` starting `codex`), whose session ids name the rollout files; count `response_item` messages with `role: developer` whose text starts with the `fathom obligations` post-edit header.
