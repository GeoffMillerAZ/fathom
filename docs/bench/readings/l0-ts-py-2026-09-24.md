# The L0 oracle beyond Go: TypeScript and Python (CV-M7, SU-11/SU-12)

## Verdict, plainly

**The file-resolved tier (SU-11) is real and accurate: 26 of 26 hand-verified
edges, stride-sampled across the whole set, were correct for both languages
— 13/13 on zod (TypeScript) and 13/13 on flask (Python), 0 wrong calls, 0
wrong resolution targets, including one case where the resolver correctly
told apart two same-named nested functions in the same file by which one
actually referenced the target.** No precision/recall number against an
independent SCIP truth could be computed as planned, for a concrete,
verified reason that turned out to be the more important finding of this
reading: **`fathom ingest -scip` is silently non-functional against the
real, currently-published scip-typescript and scip-python releases** — every
edge it imports is keyed by the raw SCIP symbol string, which never matches
fathom's own symbol-key space, so `find_callers`/`references`/`blast_radius`
would resolve none of a scip-imported TypeScript/JavaScript/Python service's
edges today. Filed as `.fathom/observations.md` O115; not fixed in this
reading (out of scope for CV-M7, needs its own dedicated pass). The scip
tier's own numbers below score `internal/scip.ImportIndex`'s round-trip
fidelity against its own decode (a real, useful self-consistency check —
precision 0.85/0.78, recall 1.00 for TS/Python) rather than an independent
oracle read, and that distinction is the headline, not a footnote.

## Why the SCIP tier could not be scored against an independent truth

`internal/scip.ImportIndex`'s `qualifiedName` derives a definition's
fathom-facing name from `SymbolInformation.DisplayName`, falling back to
the raw SCIP symbol string "when a producer omitted it" (its own doc
comment) — the committed fixture (`internal/scip/testdata/tsfixture/
index.scip`) has real display names, so `TestScipOracle_TSFixture` passes
today and always has. A raw protobuf scan of the two REAL indexes this
reading produced found **zero** `SymbolInformation` entries with a non-empty
`DisplayName`:

| Subject | `SymbolInformation` entries | with `DisplayName` | definition occurrences | resolved via `SymbolInformation` |
|---|---|---|---|---|
| zod (scip-typescript 0.4.0) | 23,583 | **0** | 23,583 | 0 |
| flask (scip-python 0.6.6) | 5,551 | **0** | 4,910 | 0 |

So every definition's qualified name IS the raw SCIP descriptor string
(e.g. `` scip-typescript npm zod 4.4.3 src/v4/core/`registries.ts`/$output# ``),
for both the truth edges `ImportIndex` returns AND the edges `fathom ingest
-scip` actually stores — the SAME degenerate namespace on both sides,
which is why the scip-tier numbers below read as near-perfect: they are
scoring `ImportIndex`'s decode against itself, not fathom's answer against
an independent oracle. Reproducible, filed as **O115**
(`.fathom/observations.md`) — not a version-pinning artifact (0.4.0/0.6.6
are the only published releases) and not a missing-dependency artifact
(zod's full pnpm install made no difference). Not fixed here: a real fix
means parsing the SCIP symbol descriptor's own grammar as a second
fallback, which cannot recover a name for an opaque `local N` symbol
either way, and deserves its own plan row and tests against both real
producers rather than a rushed edit inside this reading.

## O115 fixed — CV-M7 re-run (same day)

### The fix

`internal/scip.ImportIndex` (`ImportIndex(service, raw, nodes)`, a new
required `nodes` parameter) no longer derives a definition's fathom key
from `SymbolInformation.DisplayName` or index-internal geometry at all.
Each definition is mapped against the SAME service's own already-extracted
`core.SymbolNode` table by **position** — document path + the definition's
own `Range` start line, matched against a node's `FilePath`+`Line` — and,
only when that match is ambiguous (zero or more than one candidate at the
exact file+line), by parsing the SCIP symbol string's own descriptor
suffix (its last namespace/type/term/method name, per SCIP's published
grammar) and resolving that leaf name within the same file. A definition
neither path places contributes **no edge at all**, counted and disclosed
(`Report.Unmapped`, surfaced as `scip_imports[].unmapped` in `fathom
ingest --json` and a stderr warning) rather than silently dropped or
guessed — never conflated with a genuinely external reference
(`core.EdgeUnresolved`).

Re-running the L0 oracle against these SAME real clones (zod, flask;
`.scip` indexes unchanged, re-imported with the fixed binary) surfaced TWO
further mapping bugs, both hand-verified against real source before being
called bugs, both fixed with regression tests reproducing the exact real
shape:

1. **A parameter silently collapsed onto its enclosing function.** A
   Python/TypeScript function signature normally puts the function's own
   definition and every one of its parameters' definitions on the SAME
   source line; fathom's own extractors never mint a `SymbolNode` for a
   parameter. Position-matching a parameter's SCIP definition therefore
   found exactly one candidate — the enclosing FUNCTION's own node — and
   silently joined the two. Concretely: `flask`'s `Flask.
   raise_routing_exception` (which never calls itself) produced a
   `raise_routing_exception -> raise_routing_exception` edge for every
   reference to its own `self`/`request` parameters inside its body.
   Fixed: `descriptorIsParameterLike` refuses a Parameter (`(name)`) or
   TypeParameter (`[name]`) descriptor BEFORE position matching is even
   attempted — these have no fathom-level identity, full stop, regardless
   of what shares their line.
2. **A `local <id>` symbol treated as globally unique.** SCIP's own spec
   reserves `local <id>` for a symbol unique only WITHIN its enclosing
   document, freely reused by every other document (a file's first local
   is commonly `local 0` everywhere). The import's definition/reference
   tables were flat, scoped by the raw symbol string alone, so an
   unrelated document's `local 5` could satisfy a reference to a
   completely different document's own `local 5`. Concretely: a `zod`
   method referencing only its own destructured local variable ended up
   wired to an unrelated type in a different test file that happened to
   reuse the same local id. Fixed: `scopedSymbolKey` scopes a `local`
   symbol's key by document path on both the write and the read side (a
   reference to a local is always resolved in its own document, per
   SCIP's spec); every other symbol kind is unaffected (already globally
   unique by construction).

Both were found by hand-verifying real scip-typescript 0.4.0 / scip-python
0.6.6 output against these same calibration clones, not by inspection —
the same discipline O115 itself was found under. Tests: `internal/scip/
scip_import_test.go`'s `TestImportIndex_O115_ParameterNeverCollapsesOntoEnclosingFunction`,
`TestImportIndex_O115_LocalSymbolsAreDocumentScoped`, plus
`TestImportIndex_O115_ResolvesWithoutDisplayName`,
`TestImportIndex_O115_UnmappedEndpointNeverEmitsEdge`,
`TestImportIndex_O115_DescriptorFallback_AmbiguousPosition`, and
`TestImportIndex_FindCallers_ResolvesThroughImportedEdges` (an end-to-end
check that a caller now resolves through an imported edge via
`internal/analysis/callgraph`, the exact code `find_callers` uses).

### Re-running the oracle: methodology correction

Re-importing into the SAME stores the original reading used surfaced a
THIRD thing worth disclosing, though it is not an `internal/scip` bug:
`pkg/client.Client.ImportSCIP`/`store.PutTypedEdges` replace typed edges
**per package the new import touches**. A package that produced edges
under the old (broken) import but produces ZERO edges under the fixed,
stricter import is never touched by the new `PutTypedEdges` call, so its
stale, wrongly-keyed old rows survive in the store indefinitely — found
because a handful of sampled "direct" edges in a reused store still showed
raw SCIP symbol strings after the fix. This reading avoids it by ingesting
into FRESH stores; the gap itself is real and is a candidate for its own
observation (not filed as O115 — it is about `PutTypedEdges`'s
replace-granularity, not `ImportIndex`'s key mapping — filing it is left
to whoever picks up that thread).

### File-resolved tier vs. the now-independent scip truth

With the truth finally fathom-keyed, the file-resolved tier's edges (a
totally separate code path, `internal/fusion`'s per-file import/
module-scope resolver, SU-11) can be scored against it directly for the
first time. `internal/indexbench.ScipOracle`'s own `Correct`/`Precision`
counts each TRUTH edge against a DEDUPED predicted set (sound for Recall,
which stayed in the loop; not sound for Precision when truth carries
duplicate `(from,to)` pairs — a caller invoking the same callee at
multiple sites is exactly that, and pushed the raw reported Precision
above 1.0 for both languages' file-tier rows). This reading also computes
a plain deduped set-vs-set precision/recall to avoid publishing an
impossible number:

| Subject | Unique predicted (file-resolved) | Unique truth (direct) | True positive | Precision | Recall |
|---|---|---|---|---|---|
| zod (TypeScript) | 242 | 6,452 | 210 | 0.8678 | 0.0325 |
| flask (Python) | 138 | 1,062 | 131 | 0.9493 | 0.1234 |

Reading: the file-resolved tier is **high precision, low recall** against
a genuine SCIP oracle — when it emits an edge it is very likely correct
(consistent with, and now quantifying, the 26/26 hand-verified spot-check
above), but it attempts only 1.2–4.9% of what a type-aware indexer proves
exists, because it is exactly what its own name says: import-graph and
module-scope name matching, never a type checker. This is the number CV-M7
asks for; nothing here changes SU-11's own documented tier level
(`docs/languages.md`), since "heuristic, not typed" already means low
recall is expected.
