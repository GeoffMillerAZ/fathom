# The L0 oracle beyond Go: TypeScript and Python (CV-M7, SU-11/SU-12)

## Verdict, plainly

**The file-resolved tier (SU-11) is real and accurate: 26 of 26 hand-verified
edges, stride-sampled across the whole set, were correct for both languages
— 13/13 on zod (TypeScript) and 13/13 on flask (Python), 0 wrong calls, 0
wrong resolution targets, including one case where the resolver correctly
told apart two same-named nested functions in the same file by which one
actually referenced the target.** No precision/recall number against an
independent SCIP truth could be computed as planned, for a concrete,
verified reason that turned out to be the more important finding of this
reading: **`fathom ingest -scip` is silently non-functional against the
real, currently-published scip-typescript and scip-python releases** — every
edge it imports is keyed by the raw SCIP symbol string, which never matches
fathom's own symbol-key space, so `find_callers`/`references`/`blast_radius`
would resolve none of a scip-imported TypeScript/JavaScript/Python service's
edges today. Filed as `.fathom/observations.md` O115; not fixed in this
reading (out of scope for CV-M7, needs its own dedicated pass). The scip
tier's own numbers below score `internal/scip.ImportIndex`'s round-trip
fidelity against its own decode (a real, useful self-consistency check —
precision 0.85/0.78, recall 1.00 for TS/Python) rather than an independent
oracle read, and that distinction is the headline, not a footnote.

## What was measured, and how

**Subjects** (`calibration/corpus.yaml`'s own TypeScript/Python entries,
docs/languages.md's own SU-12 calibration procedure,
`docs/bench/scenarios.md` §"The SCIP typed-edge oracle"): **zod v4.4.3**
(TypeScript, pinned SHA `1fb56a5c18c27102dbc92260a4007c7732a0ccca`, matched
exactly) and **flask 3.1.3** (Python, pinned SHA
`8d05782cf7e01c815ceed85eac9d744533af4c44` — the live `3.1.3` tag now
resolves to `22d924701a6ae2e4cd01e9a15bbaf3946094af65`; `calibration/
clone.sh` itself only warns on this "tag may have moved" case rather than
hard-failing, so this reading proceeded the same way, on the tag's current
commit, and names the mismatch here rather than silently reporting against
a different commit than the corpus pin names).

**Tools**: `@sourcegraph/scip-typescript@0.4.0` and
`@sourcegraph/scip-python@0.6.6` — the only published versions of each
(`npm view <pkg> version`) — installed via `npm install --prefix
<scratch>/l0-tools/{npm,npm-py}`, never globally. zod's own dependencies
were installed too (`corepack pnpm install --frozen-lockfile`, a pnpm
monorepo; corepack downloads pnpm on demand, no global pnpm needed) to rule
out a missing-type-information explanation for what follows — it made no
difference to the finding below.

**Harness**: fathom's own `internal/indexbench.ScipOracle` /
`internal/scip.ImportIndex` — the exact code `cmd/indexbench scip-oracle`
(`task bench-l0-scip`) calls. Two clones per subject (`<repo>-file`,
`<repo>-scip`) so the file-resolved tier could be measured with NO scip
index anywhere near the ingest root (`fileresolve.go`'s own activation
condition: "where no `index.scip`/`.fathom/scip/*.scip` exists for the
service") and the scip tier with one, cleanly:

```sh
# file tier: plain ingest, scip index produced in a SEPARATE clone/location
fathom ingest --service zod-file  --path zod-file  --store zod-file.sqlite
fathom ingest --service flask-file --path flask-file --store flask-file.sqlite

# scip tier: index the -scip clone, then import it explicitly
scip-typescript index --output zod.scip      # in zod-scip/
scip-python index --output flask.scip .      # in flask-scip/
fathom ingest --service zod-scip  --path zod-scip  --store zod-scip.sqlite  -scip zod.scip
fathom ingest --service flask-scip --path flask-scip --store flask-scip.sqlite -scip flask.scip
```

`cmd/indexbench scip-oracle`'s own CLI has no way to separate a store's
file-resolved edges from its scip-imported ones when both are present (both
land in `typed_edges`, `EdgeConfidenceOf` treats file-resolved edges as
always-heuristic but the store query does not filter by that), so a small
throwaway program (not committed, deleted after this reading) called
`internal/indexbench.ScipOracle` and `internal/scip.ImportIndex` directly —
unmodified fathom scoring code — filtering `c.TypedEdges` by
`core.EdgeFileResolved` before handing each bucket to the oracle
separately. This is the one deviation from driving the shipped CLI, and it
exists only because the CLI has no filter flag, not because the scoring
logic changed.

## Why the SCIP tier could not be scored against an independent truth

`internal/scip.ImportIndex`'s `qualifiedName` derives a definition's
fathom-facing name from `SymbolInformation.DisplayName`, falling back to
the raw SCIP symbol string "when a producer omitted it" (its own doc
comment) — the committed fixture (`internal/scip/testdata/tsfixture/
index.scip`) has real display names, so `TestScipOracle_TSFixture` passes
today and always has. A raw protobuf scan of the two REAL indexes this
reading produced found **zero** `SymbolInformation` entries with a non-empty
`DisplayName`:

| Subject | `SymbolInformation` entries | with `DisplayName` | definition occurrences | resolved via `SymbolInformation` |
|---|---|---|---|---|
| zod (scip-typescript 0.4.0) | 23,583 | **0** | 23,583 | 0 |
| flask (scip-python 0.6.6) | 5,551 | **0** | 4,910 | 0 |

So every definition's qualified name IS the raw SCIP descriptor string
(e.g. `` scip-typescript npm zod 4.4.3 src/v4/core/`registries.ts`/$output# ``),
for both the truth edges `ImportIndex` returns AND the edges `fathom ingest
-scip` actually stores — the SAME degenerate namespace on both sides,
which is why the scip-tier numbers below read as near-perfect: they are
scoring `ImportIndex`'s decode against itself, not fathom's answer against
an independent oracle. Reproducible, filed as **O115**
(`.fathom/observations.md`) — not a version-pinning artifact (0.4.0/0.6.6
are the only published releases) and not a missing-dependency artifact
(zod's full pnpm install made no difference). Not fixed here: a real fix
means parsing the SCIP symbol descriptor's own grammar as a second
fallback, which cannot recover a name for an opaque `local N` symbol
either way, and deserves its own plan row and tests against both real
producers rather than a rushed edit inside this reading.

## File-tier numbers and hand spot-check (the real result)

| Language | Subject | Discovered files | Symbols | `file_resolved` edges |
|---|---|---|---|---|
| TypeScript | zod (pnpm monorepo, deps installed) | 595 | 3,620 | 251 |
| Python | flask | 235 | 1,770 | 141 |

Name-based comparison against the SCIP truth reads 0/0/0 for the SAME
reason as the scip tier: `ImportIndex`'s truth edges are keyed by raw
descriptor strings, and `fileresolve.go`'s edges are correctly keyed by
fathom's own clean `SymbolKey` (confirmed: every sampled `file_resolved`
`FromSymbol`/`ToSymbol` below is a normal dotted fathom key, e.g.
`zod-file::packages/zod/src/v4/core/util.safeExtend` — the two namespaces
simply never intersect). A 0% figure here would misreport a keying
mismatch as a fathom-quality defect, which the plan's own "never fabricate
numbers" rule forecloses — so instead of publishing that number, this
reading hand-verified precision by reading the real source at every
sampled edge's location, the same methodology
`test-certifications-suggest.md` already uses for its own 5/5 spot-check,
stride-sampled (every 20th zod edge, every 11th flask edge) rather than
cherry-picked, so it covers the file range, not just the first file:

**zod (TypeScript), 13/13 correct:**
`benchUtil.formatNumber→toFixed`, `generate.generate→randomStr`,
`v3/types.ZodSet._parse→finalizeSet`, `from-json-schema.convertBaseSchema→
convertSchema`, `classic/schemas.keyof→_enum`, `core/api._positive→_gt`,

base64ToUint8Array`, `core/util.safeExtend→mergeDefs`, `locales/en.error→

**flask (Python), 13/13 correct**, including one edge that required real

## What this changes

- `docs/languages.md`'s TypeScript/JavaScript/Python rows already say the
