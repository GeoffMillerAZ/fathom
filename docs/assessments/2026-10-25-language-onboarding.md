# Language onboarding assessment (2026-10-25)

The existing harness already covers upstream query reuse. The measured evidence here is 15 historical additions and 20 documented review finding groups, plus 21 observed revision/review rounds across six GPU-wave lanes. Named-round counts outside the six measured GPU lanes remain unknown. Individual reviewer-pass counts and end-to-end elapsed time remain unmeasured for all lanes. The public GPU sample repeatedly concerns oracle truth, measurement identity, test effectiveness and reading contracts. This supports an experiment, not a claim that a new preflight or importer saves time.

**Claim grades:** *measured* means read from the cited git objects, public issue reports or upstream source on this date. Counts are measured only within the explicitly included sources. Review/API gaps mean they are lower bounds on all findings. Savings and proposed check effectiveness are *hypothesis*. End-to-end elapsed time and review rounds without a recorded start/review trail are *unmeasured*. No worker-hour estimate is inferred from commit dates.

**Decision link:** this informs the proposed [language-onboarding design](../design/language-onboarding.md) and open [LH plan rows](../plans/language-onboarding.md). Governing accepted records are ADR-048, ADR-073 and ADR-075, with G15, I38, I54, I55 and I62. The new decision is a draft without an allocated record ID, awaiting maintainer review.

## Replay inventory and coverage

The [20-case inventory](data/2026-10-25-language-onboarding-cases.json) binds each finding group to its public report, published bad submission head where available, recipe step, expected check and missing inputs. All 20 are unmeasured. Five are candidate mechanical cases: C5-R2 and E2-R1/R2/R3/R5. Zero of those five has a documented repaired control in the collected sources. This is a blocker to a positive experiment result, not evidence that false blockers are zero. The bad trees are locally available, but no replay has run. Repo-wide reading checks and per-subject file selection have different scopes and must be measured separately.

The public issue review API was rate-limited (HTTP 403). Issue bodies and accessible comments supply the counted reports. This census does not claim complete PR-review coverage. The first-reading inclusion rule omits refinements and refusals, so it cannot estimate overall addition effort or failure rates. Controller-authorized private evidence supplies only the aggregate round census and historical outcomes above. No private operational identifiers are published.

## Current harness, before a new build

The [recipe](../design/language-breadth.md) §13.2 step 11 already orders a starter search: grammar `queries/tags.scm`, Aider's `*-tags.scm`, then nvim-treesitter `locals.scm`. It asks for pinned provenance, license checks, hand-written goldens, `lang-probe`, and independent calibration. `cmd/indexbench/langdraft.go` already converts a pinned `locals.scm` into `tags.scm` and optional `imports.scm`: one kept definition capture becomes `@name` plus an outer `@definition.<kind>`; it drops scopes, references, parameters, fields and other kinds, flags unsupported predicates, reports inheritance without following it, checks source revision/license, and optionally compiles against a dialect. It does **not** discover files, import grammar/Aider/Helix tags, validate semantic accuracy, or prove calibration. Its test fixture has 19 patterns: 11 kept, 1 import, 7 dropped, 2 flagged (`cmd/indexbench/langdraft_test.go`). This is parser behavior, not a real-language efficiency result.

Other reuse already implemented: `lang-pin` pre-fills grammar lock rows from `kreuzberg-dev/tree-sitter-language-pack` catalogue at `b7fc9ae9f7149697fb2ca320bad0156c18ee6519` (`docs/plans/language-breadth.grammars.json`, MIT catalogue claim, then per-grammar verdict); `lang-linguist` imports Linguist data at `5fbdfcb8133be2bed88bf3ce62b2335f50474525` (`docs/plans/language-breadth.linguist.json`, MIT). The Bash dialect starts from Aider's `bash-tags.scm` at `ff191affc6e1413f33dad914d9930a5993aad853`; its provenance documents an actual debugging pass because Aider's `@name.definition.*` captures compiled but were not read by fathom's `@name` matcher (`internal/extractor/dialects/bash/PROVENANCE.md`). Grammar tags also seed PHP, C++, C, Java, Rust and C# dialects; their headers record revisions. `lang-oracle -tags-query` already accepts independent pinned tags, locals and outline queries as tier-C *definition* oracles. It refuses the source used to draft the dialect, avoiding circular evidence (`docs/design/language-breadth.md` §1.5).

## Implication for a measured design

If the historical review inventory shows a recurring query-source or capture-convention finding, a **read-only candidate report** could print query path, commit, license basis, capture convention, unsupported predicates/inheritance and whether its source would conflict with the planned oracle. The Bash capture mismatch is one concrete class it could catch. The existing `lang-draft` conversion, `lang-pin` and `lang-linguist` already cover much of the proposed importer, so a new fetch/copy layer has no demonstrated benefit yet. Replay any candidate checks against historical branches and count review findings actually caught before proposing implementation. A check that merely restates existing `lang-probe`/`lang-oracle` failures adds no efficiency.

## Evidence limits

Public docs and repository source establish available formats and licenses; they do not establish reduced rounds, wall time, or accuracy for fathom. Some shell requests lacked external DNS; primary web sources and fetched license files establish the matrix. No complete upstream checkout or importer trial was run. The exact pins listed above come from existing committed fathom provenance or public release tags. Nvim queries and each new grammar/query require a fresh 40-hex pin and exact file license before copying. The newer `xberg-io` catalogue has not been compared against fathom's pinned `kreuzberg-dev` snapshot.
