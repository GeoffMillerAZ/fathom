# Future directions: F92 to F97

Records of the futures router, `../futures.md` (the confidence and horizon key, and every id with its member).

## F92. Job cost evidence for placement

- Confidence: plausible (ADR-078 D5, owner-architect decision, 2026-10-22). Horizon: later.
- Motivation: once attested receipts carry resource fields, a job's measured peak memory and duration can tell an external orchestrator where it fits. This is static cost evidence about a job, not live host telemetry.
- Do not build: scheduling, placement, cross-machine monitoring, host-load readers or background sampling. The orchestrator owns those tools; fathom adds no network calls (I14) or background job (ADR-049 decision 2).
- Preserve: source-identified receipts on the existing evidence carrier; resource fields themselves remain unbuilt here.
- Promote when: at least 30 attested runs carry resource fields AND an orchestrator asks for placement evidence in writing.
- Drop if: no orchestrator asks within 6 months (2027-04-22).

## F93. Compliance interchange: OSCAL assessment results and Gemara evaluation records from fact and join receipts

- Confidence: plausible (ADR-088, owner-architect rulings, 2026-10-28). Horizon: later. Evidence: OSCAL tooling is active (compliance-trestle v5.2.0, 2026-10-05), Gemara (OpenSSF, 2026-03-09) declares governance layers in CUE with evaluations as records, and an MCP pipeline produced schema-valid OSCAL plans by keeping retrieval deterministic.
- Motivation: a GRC tool or assessor reads fathom's evidence in a format it already imports, keyed by clause.
- Do not build: control catalogs, crosswalks, SSP or POA&M generation, or a "compliant" verdict (ADR-069 decision 5).
- Preserve: receipts keep stable fact ids, and `trace` requirement ids stay a key a clause id can join.
- Promote when: a named compliance consumer asks in writing for OSCAL or Gemara output from fathom's receipts.
- Drop if: no consumer asks by 2027-10-28.

## F94. The project map: computed components with their governing records, owners, coverage and levels

- Confidence: plausible (ADR-086 decision 4, owner-architect rulings, 2026-10-28). Horizon: later. Evidence: a controlled study across agents found repository overviews unhelpful (arXiv 2602.11988), and `repo_map` is orientation-only; the design deferred the map rather than build it before fathom's own reading.
- Motivation: an agent or a person asking "how does this system fit together" gets components from the repository graph, each with its central symbols, governing-record counts, owners, concern coverage, the language level its reading proves and its unknown residue, computed at request time. Component clustering by call density is its later refinement.
- Do not build: generated prose, a committed map file (K5, F65), per-component model summaries, or clustering before the map itself earns a place.
- Preserve: `fathom why --json` keeps record, row, symbol and receipt as separate keyed lines a map can aggregate; the repository graph's roles and entry points stay queryable per package.
- Promote when: the understanding bench's T2 (flow and orientation) reading, PU-M1 in `docs/plans/project-understanding.md`, shows A1 losing or tying A0 on T2 at the prereg's own T2 minimum detectable effect, with at least half of the missed T2 items naming the wrong component.
- Drop if: A1 wins T2 at adequate power without a map, or the program kill of ADR-084 fires.

## F95. A named meaning-search pairing in the adoption docs

- Confidence: plausible (ADR-085 arm A3, 2026-10-28). Horizon: next. Evidence: semantic search helps meaning questions and little else, best combined with grep (Cursor, vendor-claimed, 2025-11-06; Paparats, its own runs).
- Motivation: users who ask "where does feature X live" get a measured recommendation for a third-party meaning-search MCP server beside fathom.
- Do not build: embeddings, a vector store or a bundled search server (ADR-041, ADR-049 decision 8).
- Preserve: arm A3 names its server and version in the prereg, so the reading is attributable.
- Promote when: arm A3 beats A1 on T1 at its minimum detectable effect, and the owner answers Q40 yes.
- Drop if: A3 reads a powered null on T1.

## F96. Review-comment verification: another reviewer's anchors resolved against the index

- Confidence: plausible (ADR-088 decision models, 2026-10-28). Horizon: later. Evidence: a repository-grounded judge that gathers code evidence first told valid from plausible-but-invalid review comments at 76.6%, +19.8 pp over its base model (CRJudgeBench, arXiv 2609.37216, 2026-09-29, a preprint under review).
- Motivation: a reviewer bot's comment arrives with its file, symbol and claim checked against fathom's facts, so an author can discard the ones the code contradicts.
- Do not build: a fathom reviewer, comments of its own, or a model verdict served as a fact (I62).
- Preserve: review findings and imported findings keep file and line anchors at a revision.
- Promote when: PU-M7 reads KEEP and a reviewer integration exists on a local channel.
- Drop if: PU-M7 reads a powered null.
