## F2. Public release (H2): public repos, tagged binaries, brew tap, MCP registry, plugin bundle

- Confidence: plausible. Horizon: later.
- Motivation: "the release is the boundary event"; the falsifiable "best" claim is the published context-bench.
  Evidence: `docs/design/product-vision.md` §4 H2.
- Do not build: brew tap, registry listings, marketing, a hosted anything.
- Preserve: `fathom init` works on a cold clone; the in-tree kit mirror (ADR-019) keeps a kit-less build possible; no
  org-specific content (ADR-011); the kit mirrors (`third_party/agentic-kit`, the app-kit adoption) carry licences
  compatible with distribution inside an FSL-1.1-ALv2 work (ADR-052, amended 2026-09-29: the check holds, because both
  mirrors carry FSL-1.1-ALv2, agentic-kit from `53024ff` and app-kit from `d4512ca`, mirrored at `9fa58e6`; re-check
  on any pin bump that changes either licence); Q29 and Q30 are answered before any public release.
- Promote when: the H1 exit criteria are green (instrument valid ≥4 weeks; injection ≥90%; verify gate live in ≥2
  repos ≥4 weeks; surface pruned; portability passing; context-bench win).
- Drop if: the owner decides fathom stays a personal force-multiplier (`docs/vision/07` Q4).
- **Promoted in part 2026-09-27** (ADR-049 decision 3, vision 38): the plugin bundle (the rendered plugin with a
  default surface of at most eight tools, install-tested in Claude Code and one other client) is scope goal G16,
  `docs/plans/reach.md`. Publishing it (a marketplace listing, the brew tap, the MCP registry) stays here, under the
  Promote-when above and the owner's Q4 call.
- **Note 2026-09-29** (the Claude OS comparison, ADR-049 amendment): screenshots of the console up front in the
  README, and listings in MCP directories, wait here under the same Promote-when and Q4.
- **Promoted in part 2026-10-16** (ADR-072 decision 6): the rendered marketplace manifest and plugin trees are
  committed to the repository with a self-hosted install line in the README (`docs/plans/claude-code-mods.md` MOD-10,
  MOD-11). A catalog listing, the brew tap and the MCP registry stay here, under the Promote-when above, Q4 and Q30
  (Q-MOD-1 answered yes 2026-10-16: the self-hosted manifest is outside Q30, and the catalog listing and the brew tap
  stay blocked by it).
- **Reality check 2026-10-17** (`gh repo view`, `gh release list`): shipped are the public repository and 11 tagged
  prereleases, v0.11.0 (2026-10-11) to v0.15.3, darwin and linux tarballs for amd64 and arm64 plus `checksums.txt`.
  Not shipped: the brew tap, the MCP registry listing, the plugin bundle (MOD-10, MOD-11 open; the only `plugin.json`

## F3. Federation over portable stores (H3)

- Confidence: plausible. Horizon: someday.
- Motivation: one module = one store; orchestration composes above the engine.
  Evidence: `docs/design/product-vision.md` §4 H3, ADR-016 "federation composes above the engine".
- Do not build: a multi-tenant engine; the DuckDB `ATTACH` mechanism as written (engine gone; needs a SQLite re-check).
- Preserve: born-portable stores (ADR-017); `pkg/platform` as the join point.
- Promote when: ≥2 real external module consumers, or ≥100 external installs plus ≥60%
  internal fathom-share sustained four weeks.
- Drop if: no external module consumer appears after F2.
- Amended 2026-10-11 (ADR-069 decision 9; owner-architect, answering the owner's question of that day about live
  per-service instances): importing an operator-named index snapshot into one daemon (`import snapshot`) is not
  federation, and daemons connect by shipping index snapshots. Query-time federation between live daemons is also
  promoted when any one of these fires: (a) a service's imported dependency closure exceeds one reader's measured
  budget (`docs/plans/index-snapshots.md` IXS-M7: daemon RSS or disk); (b) a dependency's owner refuses in writing
  to let its snapshot leave its boundary; (c) an answer class needs on-demand compute that one process holding the
  imported snapshots cannot run, and a reading shows the precomputed fact sheet misses it. Do not build: query-time
  RPC fan-out before one fires; a fathom-operated, multi-tenant or writable federation even then.

## F4. Layer 2: the failure-mode playbook (incident precedent)

- Confidence: plausible. Horizon: later.
- Motivation: incident investigation with precedent, compiled from a non-git folder corpus.
  Evidence: `docs/design/product-vision.md` §3–4; `fathom findings status` tracks the entry condition.
- Do not build: the pack, the prompt, or a replay harness before the corpus exists.
- Preserve: findings persist as `kind:"finding"` claims; non-git watermarks (ADR-017).
- Promote when: the obligations gate has passed AND ≥15–20 resolved findings exist.
- Drop if: two replay attempts put the true root-cause class in the top-3 for <70% of a 20-incident set.
- Trigger status (2026-09-24, CV-M10 / docs/plans/refactor-conservation.md): still not fired, but half the condition
  cleared. The findings eval gate now passes (`docs/layers.md`'s `findings` row — `TestFindingsEval_Precision`:
  precision 1.00 / recall 1.00, 2 consecutive production-model runs,
  `schema/semantic/layers/findings/eval/RESULTS.md`); the ≥15–20 resolved-finding half is unmeasured here and, on a
  fixture-scale corpus, presumed well below the bar. The resolved-finding count is BuildStatus's own tally across
  every finding-kind claim regardless of origin, so an imported review-kit finding (once `fathom findings import`
  lands, FL-10) counts toward the same ≥15–20 threshold this future is watching — the findings loop widens the funnel,
  it does not promote anything by itself.
- Note (2026-09-29, incident maps, revised the same day): incident maps are not the form this future takes. They
  became committed declarations, not live maps, and moved to F56 (ADR-058, `docs/design/incident-maps.md`); an
  earlier note here that gated them on live maps and on rows XM-26 to XM-30 is withdrawn. This future stays
  precedent compiled from a non-git corpus, gated on the resolved-finding count above. Related: F52, F56.
- Note (2026-10-11, ADR-069; owner-architect): concern bundles are calibrated by a pre-registered replay at each
  culprit's parent commit (`docs/plans/well-architected-evidence.md` WAE-M5). That corpus is postmortem-shaped and
  git-visible; this future stays precedent compiled from a non-git corpus, gated on the resolved-finding count.
